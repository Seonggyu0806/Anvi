## 1. 무엇을 만드는가

> **웨이퍼 사진 한 장을 받아, 그 안의 die 수십 개를 하나씩 검사해서
> "어디에 무슨 결함이 있는지" 목록을 내는 프로그램.**

### 이 문제가 왜 어려운가

웨이퍼에는 **같은 칩(die)이 도장 찍듯 수십~수백 개** 찍혀 있다. 그중 몇 개에 흠이 있다.

당연한 접근은 "결함이 어떻게 생겼는지 배우자" 인데, 이 분야에서는 안 된다.

| 문제 | |
|---|---|
| 데이터가 없다 | 반도체 라인은 **정상이 수십만 장, 불량이 수십 장** |
| 새 결함은 배울 수 없다 | 처음 보는 종류의 결함은 **정의상 학습 데이터에 없다** |

그래서 질문을 뒤집는다.

> ### 결함이 뭔지 배우지 않는다. **정상이 뭔지 만들어 두고 뺀다.**

**비유** — 같은 도장을 종이 10장에 찍었는데 한 장에만 얼룩이 있다.
10장을 겹쳐 보면 **도장 무늬는 모든 장에 있으니 진하게 남고, 얼룩은 한 장뿐이라 흐려진다.**
이렇게 만든 "얼룩 없는 표준 도장" 을 의심스러운 한 장에서 빼면 — **얼룩만 남는다.**

이것이 **die-to-die 검사**다.

### 이 프로그램이 들어가는 자리

```
IceCore          장비 소프트웨어 플랫폼 (HAL · IPC · 스케줄러 · SECS/GEM · DB · GUI)
  └ Phase 7      Vision 알고리즘
       └ DiePipeline   ← 여기
```

## 2. 구조 — 3층

```
┌─────────────────────────────────────────────┐
│  Wafer    홀 매니저 — die 를 차례로 돌린다      │  OpenCV 모름
├─────────────────────────────────────────────┤
│  Core     주방 시스템 — 칠판·엔진·레시피       │  OpenCV 모름
├─────────────────────────────────────────────┤
│  Cv       요리사들 — 실제 알고리즘            │  OpenCV 씀
└─────────────────────────────────────────────┘
```

**아래가 위를 모르는 것이 핵심이다.** `Core`는 블러가 뭔지 모르고, `Cv`는 다음 노드가 누군지 모른다.

덕분에 **새 알고리즘을 추가할 때 고치는 파일이 "등록 1줄"뿐**이다.

### 칠판(blackboard)이라는 규칙

노드끼리 **직접 말을 걸지 않는다.** 할 말이 있으면 이름표를 붙여 칠판에 올려둔다.

요리사 1번이 "썬 양파" 를 만들어 `양파` 라는 이름표로 올리면, 3번이 그걸 가져다 쓴다.
**3번은 그게 누가 만든 건지 모른다.**

| | |
|---|---|
| 얻는 것 | **순서를 JSON이 정할 수 있다.** 값을 바꾸려고 다시 빌드할 필요가 없다 |
| 대가 | 이름표는 그냥 글씨라 **오타를 컴파일러가 못 잡는다** |
| 되사오는 법 | **레시피 검증기** — 실행 전에 이름표 배선을 전부 확인한다 |

### die 반복은 엔진 **밖**에 있다

```
Wafer 층 (바깥)     die 목록을 만들고, 하나씩 돌린다
    │
    └─ 각 die 마다 ─→  Core 엔진 (안쪽)   레시피대로 ①→②→…→⑦
```

**JSON 레시피에는 "손님 수만큼 반복한다" 를 적을 수 없다.** die 개수는 웨이퍼를 열어 봐야 안다.

## 3. 용어 사전

| 말 | 뜻 |
|---|---|
| **die** | 웨이퍼에 찍힌 칩 하나 |
| **die-to-die** | 이웃 die로 "정상" 을 만들어 놓고 빼서 결함을 찾는 방식 |
| **골든(golden)** | 이웃들을 겹쳐 만든 "얼룩 없는 표준" 이미지 |
| **미러 문제** | 이웃의 결함이 골든에 섞여, 내 차영상에 **부호만 반대로** 나타나는 것 |
| **피치(pitch)** | die와 die 사이 간격. die 크기보다 크다 (사이에 잘라내기용 여백이 있다) |
| **스크라이브 레인** | die 사이의 잘라내기용 여백 |
| **E1 / E0 존** | E1 = 안쪽 die (이웃이 다 있다) · E0 = 가장자리 die (이웃이 모자라다) |
| **레시피** | 어떤 노드를 어떤 순서로 어떤 값으로 돌릴지 적은 JSON 파일 |
| **노드** | 파이프라인의 한 단계 (Combine · Binarize · …) |
| **칠판** | 노드들이 결과를 이름표 붙여 올려 두는 곳 |
| **ROI** | 이미지에서 잘라 볼 네모 (x, y, 너비, 높이) |
| **오라클** | "정답이 무엇인지" 를 아는 근거. 없으면 잘 되는지 판단할 방법 자체가 없다 |
| **GrayF32** | 작업용 이미지 형식. 회색 한 채널, 값이 0~1 |

## 4. 검사 한 번이 어떻게 도나

```
이웃 die들 ──┐
             ▼
        ① Combine      겹쳐서 골든을 만든다
             │
        ② Normalize    골든과 검사 이미지를 같은 조건으로
             │
        ③ Align        몇 px 어긋난 걸 밀어서 맞춘다
             │
        ④ Difference   ★ 뺀다 — 검출의 심장부
             │
        ⑤ Filter       티끌 노이즈를 지운다
             │
        ⑥ Binarize     "결함이다 / 아니다" 를 정한다
             │
        ⑦ Label        흰 덩어리를 세어 목록으로
             ▼
        ⑧⑨⑩ 꼬리       모양으로 거르고 · 종류 붙이고 · 개수 제한
             ▼
        결함 목록
```

### 각 단계가 왜 있나

| | 왜 | 함정 |
|---|---|---|
| **① Combine** | 이웃을 겹쳐 "정상" 을 만든다 | 평균이면 이웃의 결함이 섞인다 → **중앙값**이면 안 섞인다 |
| **② Normalize** | 골든과 검사본을 같은 조건으로 | **한쪽만** 흐리게 하면 모든 경계가 차이로 남는다 |
| **③ Align** | 2~3px 어긋남이 모든 경계에 띠를 만든다 | 무늬가 규칙적이면 **틀린 답을 자신 있게** 낸다 → 가드 필요 |
| **④ Difference** | 뺀다 | **미러 문제** — 이웃의 결함이 부호만 반대로 나타난다 |
| **⑤ Filter** | 티끌을 지운다 | 크기가 아니라 **두께**로 거른다 |
| **⑥ Binarize** | 결함 여부가 여기서 확정된다 | 결함 **면적은 임계값의 함수**다. 임계값 없이 면적만 적으면 뜻이 없다 |
| **⑦ Label** | 흰 덩어리를 번호·위치·크기로 | — |
| **⑧⑨⑩ 꼬리** | 목록을 다듬는다 | **여기서부터는 이미지를 안 본다** |

### 미러 문제를 막는 법은 둘이고 서로 독립이다

```
골든을 중앙값으로 만든다   →  오염된 한 장이 가운데 값으로 안 뽑힌다
부호 있는 차이를 쓴다      →  어두운 쪽만 보면 밝게 되비친 것은 안 센다
```

## 5. 실데이터에서 잰 것

### 결과

| | |
|---|---|
| 진짜 결함 | **12개** |
| 오검 | **0개** |
| die 한 칸 | 268 ms (기본 레시피) / 967 ms (대안) |
| 검출 한계 | 지름 **4px** (어두운 결함) · 6px (밝은 결함) |
| 부분 읽기 | 1024×1024 한 칸 **168 ms** / 메모리 4.0 MB |

### 이웃끼리 얼마나 닮았나 (평균 차이, 작을수록 닮음)

| 이웃 | 값 |
|---|---|
| **같은 행 1칸** | **0.0368** ← 제일 닮음 |
| 같은 열 1칸 | 0.0520 |
| 같은 행 2칸 | 0.0555 |
| 대각 1칸 | 0.0687 |
| 같은 열 2칸 | 0.0788 |

### ★ 파라미터는 짝이다

```
골든 1.5장 → 3장, 두 배로 늘렸다   →  오검 24 → 22   (2개 줄었다)
합치는 법만 Mean → Median 으로     →  오검 24 →  0
```

**듣는 손잡이는 "몇 장 쓰느냐"가 아니라 "어떻게 합치느냐"다.**
끝 열(골든이 부족한 자리)에서는 장수를 늘리는 쪽이 **오히려 손해**다 (오검 8 → 14).

`Mean` 은 이웃을 전부 섞으니 **먼 이웃일수록 골든을 흐린다.**
`Median` 은 안 닮은 것을 버리니 멀리서 데려와도 손해가 없다.

> ⚠ **이 오검 숫자는 `DarkOnly` 를 뺀 값이다.**
> 교수님 짝은 둘이 아니라 **셋** — `1칸` + `Mean` + **`DarkOnly`** 이고,
> `DarkOnly` 로 보면 **전 전략이 오검 0**이다.
> **짝에서 하나를 떼어내고 비교하면 그 짝이 부당하게 나빠 보인다.**

### 어느 손잡이가 듣나

| 임계 | minArea | 검출 | 그중 진짜 |
|---|---|---|---|
| 0.12 ~ 0.30 | 500 | **12** (전부 같다) | 12 · 오검 0 |
| 0.12 | **5** | **488** | 12 · **오검 476** |

**임계값은 둔감하고 `minArea` 가 결정적이다.** 바꾸기 전에 어느 손잡이가 듣는지 먼저 봐야 한다.

## 6. 레시피 두 벌

| | `die.diff.json` (기본) | `die.diff.median.json` (대안) |
|---|---|---|
| 이웃 | 같은 행 **좌우 1칸** | 같은 행 **거리 늘려 3장** |
| 합치기 | `Mean` | `Median` |
| 차영상 | **`DarkOnly`** | `Absolute` |
| 미러를 막는 법 | **부호** | **중앙값** |
| 필요한 것 | 결함이 어느 쪽인지 **아는 것** | 이웃 **3장** |
| 못 보는 것 | **밝은 결함** | (없음) |
| 속도 | **268 ms** | 967 ms |

**기본은 빠르고 공정 지식을 쓰고, 대안은 느리지만 아무것도 몰라도 된다.**

> `DarkOnly` 는 요령이 아니라 **"이 공정의 결함은 어두워진다"는 지식을 레시피에 적은 것**이다.
> 알고리즘을 똑똑하게 만드는 대신 **아는 것을 조건으로 넣어 문제를 없앤다** — 검사 엔지니어의 사고방식이다.

## 8. 돌리는 법

레시피 한 벌을 이미지에 돌린다.

```bash
diepipe run -r samples/recipes/die.diff.json -i <이미지> --origin <x,y> --pitch <간격> --count <칸수> --cell <번호>
```

| 옵션 | 뜻 |
|---|---|
| `-r` | 레시피 파일 |
| `-i` | 이미지 파일 |
| `--origin` | 격자가 시작하는 자리 |
| `--pitch` | 칸 간격 |
| `--count` | 몇 칸을 자를까 |
| `--cell` | 그중 몇 번째를 검사할까 (나머지가 이웃이 된다) |

원본이 어떻게 생겼는지만 보고 싶을 때.

```bash
diepipe probe -i <이미지> --overview 2000 --out overview.png
```

| 옵션 | 뜻 |
|---|---|
| `--roi x,y,w,h` | 그 네모만 뜯어 본다 |
| `--overview n` | 긴 변이 n이 되게 줄인 전체 그림 |
| `--out` | 저장할 곳 |

**끝값** — `0` 결함 없음 · `3` 결함 있음 · `1` 오류 · `2` 레시피 오류

> 격자·이웃 고르기는 **웨이퍼 층에서 제대로 만든다.** `run` 의 `--pitch`/`--origin` 은
> "파이프라인이 진짜 웨이퍼에서 도는가" 를 눈으로 보려는 **진단용**이다.

## 9. 교수님 레포(VisionStack)와의 대응

**이름을 일부러 맞췄다.** 갈라지는 자리마다 "교수님은 어떻게 했나" 라는 답이 하나 있어야,
둘이서 그걸 기준으로 맞출 수 있기 때문이다.

| 우리 | 교수님 | |
|---|---|---|
| `Core/Pipeline/` | `Core/Pipeline/` | 같음 |
| `Core/Configuration/` | `Core/Configuration/` + `Configuration/` | 교수님은 로더를 따로 뺐다 |
| `Core/Registry/` | `Core/Registry/` | 같음 |
| `Core/Domain/Defect.cs` | `Core/Domain/Defect.cs` | 우리 쪽에 칸 셋이 더 있다 |
| `Cv/Algorithms/` | `Core/Algorithms/` (인터페이스) + 구현 | 교수님은 계약과 구현을 갈랐다 |
| `Wafer/Domain/Wafer.cs` | `Core/Domain/Wafer.cs` | 타입 이름 **동일** |
| `Wafer/Config/WaferSpec.cs` | `Wafer/Config/WaferJob.cs` | 우리는 형상만, 교수님은 작업 전체 |
| `Wafer/Execution/DieGridBuilder.cs` | `Wafer/Execution/DieGridBuilder.cs` | **동일** |
| (아직) | `Wafer/Execution/WaferRunner.cs` · `DefectCollector.cs` | 4주차에 만든다 |
| (아직) | `Wafer/Processing/AbsoluteTransform.cs` · `WaferSampler.cs` · `WaferClusterer.cs` | 4주차 |
| (안 만듦) | `Wafer/Observability/` · `Execution/ContentHash.cs` | 배운 범위 밖 |

### 일부러 다르게 한 것

| | 우리 | 교수님 | 왜 |
|---|---|---|---|
| 가장자리 존 | `EdgeRings` (**겹 수**) | `edgeExclusionPx` (픽셀) | 픽셀 값이 실제로는 켜고 끄는 스위치로만 쓰이고 있었다 |
| 존 기본값 | `Unknown = 0` 을 추가 | 없음 | **안 정했는데 "안쪽" 이 되어 버리는 것**을 막는다 |
| 좌표 정밀도 | `double` | `float` | 격자 계산이 누적되는 자리라 |

## 10. 지켜야 하는 것 — 회사 자료

**이 레포에 실데이터가 들어가면 안 된다.**

```
❌ 원본 이미지 · 잘라낸 타일 · 결함 주입 이미지
❌ 원본 파일 이름 · 해상도 · 용량 · 제품명
❌ 웨이퍼 격자 배치(열×행) · 피치 · 절대 경로
✅ 원래 자리에서 경로로만 읽는다
✅ 중간 산출물은 레포 밖 임시 폴더에
✅ 레포에 남기는 것은 방법과 숫자뿐
```

> **구분 기준** — 문제는 숫자 자체가 아니라 **원본과 묶이는 문장**이다.
> "2500×2500 합성 die 536.5 ms" 는 **성능 기록**이라 괜찮다.
> "원본에서 2500×2500 한 칸" 은 원본 사양을 말하는 것이라 안 된다.

`.gitignore` 는 2차 방어선이다. **애초에 레포 밖에 두는 것이 1차 방어선.**
