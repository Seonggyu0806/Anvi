## 1. 무엇을 만드나

**웨이퍼 사진 한 장을 받아, 그 위의 die 를 하나씩 검사해 "어느 die 의 어디에 결함이 있는지" 목록을 내는 프로그램.**

- **웨이퍼**: 반도체 칩을 만드는 둥근 실리콘 원판
- **die**: 웨이퍼 위에 같은 설계로 격자 모양으로 반복해 만든 칩 하나

### 왜 "결함을 배우는" 방식을 쓰지 않나

| 사정 | 결과 |
|---|---|
| 생산 라인에서 정상 이미지는 수십만 장, 불량 이미지는 수십 장이다 | 결함 모양을 학습할 데이터가 부족하다 |
| 처음 나타난 종류의 결함은 학습 데이터에 없다 | 학습한 모양만 찾는 방식은 새 결함을 놓친다 |

그래서 결함의 모양을 정의하지 않고, **정상의 모양을 만들어 두고 그것과 다른 곳을 결함으로 본다.**

### die-to-die 검사

1. 검사할 die 의 이웃 die 여러 장을 픽셀마다 하나의 값으로 합친다. 이렇게 만든 기준 이미지를 **골든**이라 한다
2. 이웃 die 는 같은 설계라 무늬가 같다. 결함은 die 마다 다른 자리에 드물게 있으므로, 합치는 방법에 따라 골든에서 빠지거나 약해진다
3. 검사할 die 에서 골든을 빼면 무늬는 사라지고 **골든과 다른 곳**만 남는다. 그것을 결함 후보로 본다

**미러 문제** — 골든을 이웃으로 만들기 때문에, 이웃 die 에 있는 결함이 골든에 섞이면 검사할 die 의 차이 이미지에 **반대 부호**로 나타난다. 막는 방법은 두 가지이고 서로 독립이다.

| 방법 | 원리 | 한계 |
|---|---|---|
| 차이의 부호를 정한다(`DarkOnly`) | 이 공정의 결함은 어두워진다. 미러는 검사 die 가 골든보다 **밝게** 나타나므로 버려진다 | 밝아지는 결함은 못 잡는다 |
| 중앙값으로 합친다(`Median`) | 픽셀마다 가운데 값을 고르므로, 이웃 중 **절반 미만**에만 있는 결함은 골든에 들어가지 않는다 | 이웃 3장 중 2장의 결함이 같은 자리에 겹치면 막지 못한다 |

## 2. 계기

### 학습한 기능을 하나의 프로그램으로 잇는다

C# 학습 과정(Lesson01~16)에서 검사 장비 소프트웨어의 기능을 하나씩 익혔다. Lesson15 에서 파이프라인 엔진과 JSON 레시피를, Lesson16 에서 웨이퍼 단위 검사를 다뤘다. 각 Lesson 은 개념을 확인하는 데서 끝났고, 이를 연결해 실제로 동작하는 프로그램은 없었다. 이 프로젝트는 그것을 잇는 작업이다.

| | 역할 |
|---|---|
| 동기 구현 (`AnDi/DiePipeline2`) | 같은 과제를 각자 구현했다. 이쪽은 엔진 · 레시피 구조에서, 동기는 알고리즘에서 출발했다 |
| 교수님 레포 (`visionstack_proto`) | 같은 문제의 참조 구현. 둘이 갈라질 때의 공통 기준 |
| `icecore_proto_md` | 장비 소프트웨어 플랫폼 설계. 이 프로젝트는 그중 Phase 7(비전 알고리즘)의 구현체 하나에 해당한다 |

### v1 을 접고 v2 를 만든 이유

첫 구현(v1, 2026-09-12~14)은 동작했고 테스트도 176개였다. 그러나 코드 6,621줄 중 1,535줄(23%)이 Lesson 에도 과제 브리핑에도 없는 기능이었다(부분 재실행 · 결과 봉투 · 내용 해시 · 메모리 풀 · 측정 도구). 작성자가 설명할 수 없는 코드였다.

v2 는 규칙을 하나 두고 다시 만들었다.

> **학습 범위와 브리핑 범위 안에서만 만든다. 새 기능은 실제 데이터에서 그 필요를 확인한 뒤에 넣는다.**
> 둘이 갈라지는 자리에서는 교수님 구현의 이름 · 구조 · 기본값을 따른다.

미룬 기능과 넣을 조건은 `docs/deferred.md` 에 있다.

## 3. 검사 한 번 — die 레시피

die 하나를 검사하는 처리는 **노드**(처리 단계 하나)를 순서대로 이은 것이다. 순서와 값은 **레시피**(JSON 파일)가 정한다.

### 노드 11종

| 노드 | 하는 일 |
|---|---|
| `Combine` | 이웃 die 여러 장을 픽셀마다 합쳐 골든을 만든다 — `Mean` · `Median` · `Min` · `Max` |
| `Normalize` | 골든을 평활한다 — `GaussianBlur` · `MedianBlur`. 골든에만 걸리므로 무늬 경계에 차이를 만들 수 있다 |
| `Align` | 골든과 검사 이미지의 평행 이동량을 위상상관으로 재서 맞춘다. 응답이 0.3 미만이거나 이동이 20px 를 넘으면 측정을 믿지 않고 보정하지 않는다 |
| `Difference` | 골든 주변 창(`windowSize`)에서 허용 범위를 만들고(`neighborMode`), 검사 픽셀이 범위를 벗어난 만큼을 차이로 낸다. 어느 방향 차이를 볼지는 `diffPolicy`(`Absolute` · `DarkOnly` · `BrightOnly` · `Signed`) |
| `Filter` | 순서 있는 필터 목록 — `Median` · `Gaussian` · `Morphology` · `Sobel` · `Laplacian` · `Bilateral` |
| `MaskApply` | 마스크가 0 인 자리를 정한 값(`fill`)으로 채운다. 원판 밖을 검사에서 빼는 데 쓴다 |
| `Binarize` | 차이를 결함 / 정상으로 나눈 0·255 마스크를 만든다 — `Threshold` · `Otsu` · `Range` · `Sigma` · `Adaptive` · `Hysteresis` |
| `Label` | 마스크에서 이어진 영역을 하나의 결함으로 세어 위치 · 면적(· 밝기 · 원형도)을 낸다. `minArea` 보다 작은 영역은 버린다 |
| `DefectFilter` | 결함 목록을 모양(종횡비 · 채움비 · 원형도)으로 거른다 |
| `DefectClassify` | 결함에 유형을 붙인다 |
| `DefectLimit` | 결함을 크기 · 개수로 제한한다 |

**결함의 면적은 임계값에 따라 달라진다.** 임계값을 올리면 같은 결함도 작게 잡힌다. 면적을 기록할 때는 임계값을 함께 적어야 비교할 수 있다.

### 지금 쓰는 레시피 5개

| 레시피 | 노드 | 용도 |
|---|---|---|
| `die.diff.json` (기본) | Combine `Mean` → Difference `DarkOnly` · `MinMax` → Binarize 0.2 → Label `minArea` 500 | E1 die. 좌우 이웃 1칸씩. 미러는 부호로 막는다 |
| `die.diff.median.json` (대안) | Combine `Median` → Difference `Absolute` · `MinMax` → Binarize 0.2 → Label 500 | E1 die. 이웃 3장. 미러는 중앙값으로 막는다. 밝은 결함도 본다 |
| `die.diff.align.json` (뷰어용) | Combine `Mean` → Align `Translation` → Difference `DarkOnly` · `MinMax` → Filter `Median` 3 → Binarize 0.2 → Label 500 | 뷰어에서 손으로 찍은 정상 die — 몇 px 어긋나도 무늬 윤곽이 남지 않게(동기 E1 처방) |
| `die.dark.json` | Binarize `Range` 0~0.15 → Label 200 | E0 die. 골든 없이 아주 어두운 영역을 결함으로 본다 |
| `die.dark.masked.json` | MaskApply(`fill` 1.0) → Binarize `Range` 0~0.15 → Label 200 | 원판에 걸친 E0 die. 원판 밖을 밝은 값으로 채워 결함에서 뺀다 |

`Normalize` · `Align` · `Filter` 는 3주차 실데이터 측정 뒤 기본 레시피에서 뺐다. `Normalize` 는 골든만 평활해 무늬 경계마다 오검을 만들었고, `Filter` 는 그 오검을 지우는 역할만 하고 있었고, `Align` 은 격자가 정확해 보정할 어긋남이 없었다(`doc_code/week-3.md` §9).

## 4. 구조

### 프로젝트 7개

| 프로젝트 | 하는 일 | 참조 |
|---|---|---|
| `Core` | 파이프라인 엔진 · 레시피와 검증 · 노드 명부 · 결함 도메인 · 원본 부분 읽기(바이트 단위) | 없음 |
| `Cv` | 알고리즘과 노드(OpenCvSharp) · 이미지 소스 · 합성 웨이퍼 | Core |
| `Wafer` | 격자 · 존 · 정렬 · 이웃 선택 · die 반복 실행 · 결과 처리 · 웨이퍼 검사 흐름 · 웨이퍼 레시피(블록 · 실행기) | Core · Cv |
| `Editor` | 블록 그래프 편집 규칙 · 그래프 ↔ 레시피 변환 · 자동 배치 · 편집 이력 · 목록 값 변환. 화면 없이 시험된다 | Core |
| `Viewer` | 원본 이미지 뷰어의 계산 — 화면 ↔ 원본 좌표 · 축소본 배율 · 보이는 영역 · 영역 끌기 · 도장. 화면 없이 시험된다 | Core |
| `Wpf` | 화면 — 작업공간 6개: 다이(블록 에디터 · 오버레이) · 웨이퍼(블록 에디터 · 오버레이 · 옵션 검사) · 원본(이미지 뷰어) | Core · Cv · Editor · Viewer · Wafer |
| `App` | 명령행 `diepipe` | Cv · Wafer |

참조는 위에서 아래로만 간다. `Core` 는 이미지 라이브러리를 모르고, `Wafer` 는 화면을 모른다. 그래서 `Core` · `Wafer` · `Editor` · `Viewer` 는 이미지 파일이나 화면 없이 테스트된다.

### 노드는 이름으로 데이터를 주고받는다

- 노드는 서로를 직접 호출하지 않는다. 결과를 이름을 붙여 공유 저장소(`PipelineContext`)에 넣고, 다음 노드는 그 이름으로 꺼낸다
- 그래서 노드의 순서와 연결을 코드가 아니라 레시피가 정할 수 있다. 값을 바꿀 때 다시 빌드하지 않는다
- 이름은 문자열이라 오타를 컴파일러가 잡지 못한다. 실행 전에 `RecipeValidator` 가 노드 종류 · 파라미터 범위 · 입력 이름의 연결을 전부 검사하고, 틀린 것을 한 번에 모아 알린다
- 종단 결과 이름은 `defectList` 로 고정이다

### die 반복은 엔진 밖에 있다

레시피는 정해진 노드를 정해진 순서로 실행하는 것만 적는다. die 의 개수는 웨이퍼마다 실행할 때 정해지므로, die 를 반복하는 일은 `Wafer` 층이 맡는다. 엔진은 die 하나를 레시피대로 처리한다. 교수님 구현도 같은 구조다.

### 새 알고리즘을 넣는 법

`Cv` 에 알고리즘 · 노드 · 팩토리를 추가하고 `CvBackend.cs` 에 등록 한 줄을 넣는다. 엔진과 `Core` 는 바뀌지 않는다.

## 5. 웨이퍼 층

```
정렬(선택) → 격자 · 존 판정 → die 마다 레시피 → 결함 모으기 → 절대 좌표 → 샘플링
```

| 단계 | 내용 |
|---|---|
| 정렬 | 웨이퍼의 정렬 표식 2개 이상을 찾아 회전 · 이동을 계산한다. 표식이 있을 법한 자리 주변만 읽는다. 결과를 믿을 수 없으면 검사를 시작하지 않는다 |
| 격자 | 원점 · 피치 · 열×행으로 die 마다 위치를 계산하고 정렬을 적용한다 |
| 존 | **E1** = 이웃이 모두 있는 die → die-to-die. **E0** = 웨이퍼 원판 가장자리에 걸친 die → 골든 없이 단일 임계. 원판(중심 · 반지름)을 주면 원으로 판정하고, 원판 밖 칸은 die 로 세지 않는다 |
| die 검사 | E1 은 이웃을 골라 골든을 만들고 E1 레시피를, E0 는 E0 레시피를 돌린다. 레시피가 원판 마스크(`waferMask`)를 요구하면 같이 넘긴다 |
| 결과 | die 별 결함을 한 목록으로 모으고, die 안 좌표를 웨이퍼 절대 좌표로 바꾼다. 결함이 많으면 보여 줄 것만 추린다(판정은 추리기 전 결과로 한다) |

결과가 틀렸는데 프로그램이 정상 종료하는 경우를 막는 장치가 있다.

| 장치 | 막는 것 |
|---|---|
| 골든 장수 검사 | 레시피가 요구하는 골든 장수보다 이웃이 적으면 그 die 를 실패로 기록한다. 차이 부호가 `Absolute` 이면 미러 경고를 낸다 |
| 정렬 거부 | 표식 점수 · 각도 · 배율 · 어긋남이 기준을 벗어나면 검사를 시작하지 않는다 |
| 기울기 한계 | 기울기가 0.05° 를 넘으면 검사를 시작하지 않는다(die 를 회전해 읽는 기능이 아직 없다) |
| 격자 경고 | 격자가 사진의 일부만 덮으면 알린다 |
| 원판 경고 | 원판을 줬는데 E0 레시피가 원판 밖을 가리지 않으면 알린다 |
| 실패 상태 | 검사하지 못한 die 를 깨끗한 die 와 다른 상태(`Failed`)로 남긴다 |

### 웨이퍼 레시피

격자 · 원판 · 수동 지정 · 정렬 표식을 명령줄에 매번 적지 않고 **파일 하나**(`*.wafer.json`)에 적는다. 파일은 블록 5개를 이은 것이다.

```
표식 찾기 → 자세 계산 → die 전부 검사 → 웨이퍼 좌표 → 결과 추리기
```

- 엔진은 블록을 한 번씩만 실행한다. 표식 찾기는 표식마다, die 검사는 die 마다 반복해야 하므로, 실행기가 레시피를 `die 전부 검사` 블록에서 나눠 각 부분을 필요한 횟수만큼 실행한다
- 명령행 옵션으로 돌리든 레시피 파일로 돌리든 같은 검사 흐름(`WaferInspection`)을 지난다. 두 방법이 같은 결과를 내는지 시험으로 확인한다
- 파일 안의 die 레시피 · 표식 조각 경로는 레시피 파일이 있는 폴더를 기준으로 읽는다
- 견본: `samples/wafer/demo.wafer.json`. 실데이터 레시피는 격자 · 원판 위치가 들어가므로 레포 밖에 둔다

상세는 `docs/doc_code/wafer.md`.

## 7. 돌리는 법

```bash
dotnet build DiePipeline.slnx
dotnet test  tests/DiePipeline.Tests
```

### 명령행 `diepipe`

| 명령 | 하는 일 |
|---|---|
| `demo -o <경로.bmp>` | 시험용 합성 웨이퍼를 그린다. 심은 결함 자리 · 정렬 표식 · 원판(`--round`)을 정답으로 같이 출력한다 |
| `wafer -i <이미지> --e1 <레시피>` | 웨이퍼 한 장을 검사한다. 격자 · 원판 · 정렬 옵션은 `diepipe` 를 인자 없이 실행하면 나온다 |
| `wafer -i <이미지> --recipe <웨이퍼레시피>` | 같은 검사를 웨이퍼 레시피 파일 하나로 한다. 다른 옵션과 같이 쓰지 않는다 |
| `run -r <레시피> -i <이미지>` | 가로로 이어진 칸을 잘라 그중 하나를 레시피로 검사한다(진단용) |
| `run -r <레시피> --case <케이스>` | 원본 뷰어에서 저장한 케이스(`*.case.json`, 교수님 형식)의 사진 · ROI · 정상 die 로 검사한다 |
| `probe -i <이미지>` | 원본의 일부(`--roi`)나 축소본(`--overview`)을 본다 |

합성 웨이퍼로 처음부터 끝까지:

```bash
mkdir out
dotnet run --project src/DiePipeline.App -- demo -o out/wafer.bmp --grid 4,3 --pitch 100 --defects 3 --seed 1
dotnet run --project src/DiePipeline.App -- wafer -i out/wafer.bmp --e1 samples/recipes/die.diff.json --grid 4,3 --pitch 100 --mark out/wafer.mark.bmp --expect -40,-40 --expect 410,310
```

같은 검사를 웨이퍼 레시피 견본으로:

```bash
dotnet run --project src/DiePipeline.App -- demo -o out/wafer.bmp
dotnet run --project src/DiePipeline.App -- wafer -i out/wafer.bmp --recipe samples/wafer/demo.wafer.json
```

`demo` 가 출력한 심은 결함 자리와 `wafer` 가 찾은 자리가 같으면 정상이다.

**끝값** — `0` 결함 없음 · `3` 결함 있음 · `4` 검사하지 못한 die 있음 · `5` 정렬을 믿을 수 없음 · `1` 오류 · `2` 레시피 오류

### 일부러 다르게 한 것

| | 우리 | 교수님 | 이유 |
|---|---|---|---|
| 가장자리 존 | 원판(`--circle`) 또는 겹 수(`--edge-rings`) | 격자 테두리 die 를 E0 로 | 교수님은 원 기반 판정을 장비 통합 때로 미뤘다. 우리는 원판 전체 실데이터를 받아 원으로 판정했다 |
| 원판 가장자리 여유 | `edgeExclusionPx`(`--edge-exclusion`) — 원판 가장자리에서 안쪽으로 뺄 폭(px) | 문서는 같은 뜻, 코드는 테두리 한 겹 스위치로 씀 | 문서의 뜻을 따랐다. 겹 수는 `edgeRings` 로 따로 받는다 |
| 표식 찾는 범위 | 표식마다 있을 법한 자리 둘레 창만 읽는다 | 사진 전체 한 번(창은 "후속") | 원판 원본은 통째로 읽으면 수 GB 다 |
| 정렬 값 적는 자리 | 표식 설계 자리 · 판정 기준은 `SolveAlignment` 한 곳 | 표식 자리를 두 블록에, 판정 기준은 `InspectDies` 에 | 같은 값을 두 곳에 적으면 언젠가 어긋난다 |
| 표식 겹침 반경 `nmsRadiusPx` | 기본 0 = 조각 짧은 변의 절반 | 기본 8 | 교수님 문서가 "템플릿 크기의 절반 이상" 을 권한다. 큰 조각에서 8 이면 한 표식이 여러 개로 잡힌다 |
| 입구 | 명령행 옵션 · 화면 입력 · 레시피 파일 — 속은 하나 | 레시피 · 작업 파일 | 화면은 die 레시피를 메모리로 들고 있어 파일로 바꾸지 않았다 |
| 존 · 상태 기본값 | `Unknown = 0` | 없음 | 초기화하지 않은 값이 E1 이나 정상으로 읽히는 것을 막는다 |
| 좌표 | `double` | `float` | 격자 계산이 누적되는 자리라 |
| 골든 장수 | 레시피에서 읽어 모자라면 실패 | 없음 | 이웃 수와 합치는 법이 어긋나 미러가 나는 것을 막는다 |
| `MaskApply` | `fill` 값을 받는다 | 0 으로 채운다 | 원판 밖을 밝은 값으로 채워야 어두운 결함 임계에 안 걸린다. 기본값 0 은 교수님과 같다 |

## 9. 지켜야 하는 것 — 회사 자료

**이 레포에 실데이터와 그 정보가 들어가면 안 된다.**

```
❌ 원본 이미지 · 잘라낸 조각 · 결함을 심은 이미지
❌ 원본 파일 이름 · 해상도 · 용량 · 거래처 · 제품명 · 사양
❌ 웨이퍼 격자 배치(열×행) · 피치 · 원판 위치 · 절대 경로
✅ 원본은 레포 밖에 두고 명령행 인자로 경로만 넘긴다
✅ 중간 산출물은 레포 밖 임시 폴더에 둔다
✅ 화면에서 원본으로 만든 파일(케이스 · 골든 · 표식 조각 · 보고서)은 레포 안이면 저장을 거부한다
✅ 문서에는 방법과 상대값(피치의 몇 %, 수 px)만 적는다
```

기준은 숫자 자체가 아니라 **원본과 연결되는 문장**이다. "합성 큰 die 536 ms" 는 성능 기록이지만, "원본의 die 한 칸이 몇 px" 는 원본 사양이다. `.gitignore` 는 두 번째 방어선이고, 첫 번째 방어선은 원본을 애초에 레포 밖에 두는 것이다.

## 10. 배운 것

| 주차 | 내용 |
|---|---|
| 1 | 기능을 하나씩 익혀도 연결해 보기 전에는 드러나지 않는 문제가 있다 |
| 2 | 가장 위험한 실패는 오류 없이 틀린 값을 내는 실패다. 측정을 믿을 수 없으면 멈춘다 |
| 2 | 성능을 고칠 때는 고치기 전후를 재고, 결과가 바뀌지 않았는지 함께 확인한다 |
| 3 | 작성자가 설명할 수 없는 코드는 유지할 수 없다 |
| 3 | 축소한 이미지로 낸 결론은 원본 해상도에서 뒤집힐 수 있다 |
| 3 | 파라미터는 독립이 아니다 — 이웃 선택 · 합치는 법 · 차이 부호는 함께 정해야 한다 |
| 3 | 값을 바꾸기 전에 어느 파라미터가 결과에 영향을 주는지 먼저 잰다 |
| 4 | 함께 정해야 하는 값이 서로 다른 곳에 있으면 언젠가 어긋난다 — 한쪽에서 다른 쪽을 유도하게 만든다 |
| 4 | 점수가 가장 높은 답이 맞는 답은 아니다 — 기하 관계(표식 사이 거리)로 확인한다 |
| 4 | 검사하지 못한 것과 검사해서 깨끗한 것을 같은 결과로 보이게 하면 안 된다 |
| 5 | 사람이 옵션을 맞춰 넣던 명령행에서는 안 보이던 오류가 화면에서 실데이터를 돌리자 드러났다 |
| 5 | 미러를 막는 것은 골든 장수가 아니라 차이의 부호다 |
| 5 | 기록만 해 두고 미룬 문제(잘린 die 의 좌표)는 조건이 바뀌면 실제로 나타난다 |
| 5 | 자동 판정을 늘리기보다 파라미터로 받고 사람이 고칠 수 있게 한다(교수님 방향) |
| 7 | 흉내 낸 입력으로 통과한 화면 검사도 실제 입력과 조건이 다르면 틀린다 — 고치기 전에 증상부터 재현한다 |
