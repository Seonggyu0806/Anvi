## 1. 성능 — 어디에 쓰고 있었나

`wafer_tile_1.png`(1024×1024) 기준, 골든 3장, 결함 0개.

```
전                                      후
  Combine      24.95 ms  27.9%           Difference   15.55 ms  33.0%
  Difference   23.45 ms  26.2%           Combine       8.51 ms  18.1%
  Filter       12.67 ms  14.2%           Binarize      6.42 ms  13.6%
  Binarize      8.03 ms   9.0%           Filter        5.53 ms  11.7%
  Label         6.16 ms   6.9%           Label         3.87 ms   8.2%
  Align         5.72 ms   6.4%           Normalize     3.33 ms   7.1%
  Normalize×2   8.40 ms   9.4%           Align         2.06 ms   4.4%
  ───────────────────────                Normalize     1.82 ms   3.9%
  합계            90 ms                  ───────────────────────
                                         합계            44 ms
```

### 단서가 된 것 — 아무것도 안 하는 노드가 5.72ms를 썼다

`Align`의 `method`가 `None`이었다. 아무것도 안 하는데 5.72ms가 나왔다면
**복사가 일어나고 있다**는 뜻이다.

찾아보니 노드마다 이렇게 하고 있었다.

```
알고리즘이 새 Mat을 만든다  →  풀에서 버퍼를 빌린다  →  거기로 복사한다  →  원본을 버린다
```

알고리즘은 독립적으로 쓸 수 있게(테스트가 파이프라인 없이 부를 수 있게) 새 Mat을 돌려주고,
파이프라인 중간 버퍼는 풀이 관리해야 재사용된다. **그 둘을 잇느라 복사가 끼어 있었다.**

### 고친 것 ① — 복사 대신 넘기기

풀에 `Adopt`를 넣었다. 이미 만들어진 Mat의 **소유권을 풀이 넘겨받는다.**

```csharp
IImage buffer = pool.Adopt(produced);   // 복사 없음. 반납·재사용은 그대로
```

알고리즘 시그니처를 하나도 안 바꾸고 **90 → 58 ms**.

### 고친 것 ② — 자주 쓰는 경우에 지름길

`Combine`이 28%를 쓰고 있었다. 어떤 N에도 되는 **정렬 네트워크**를 쓰는데,
그건 N장을 전부 클론하고 N²/2번 비교한다.

실무에서 가장 흔한 두 경우에 지름길을 냈다.

| 경우 | 전 | 후 |
|---|---|---|
| 중앙값 3장 (기본 설정) | 클론 3 + 비교 3쌍 = 9연산 | `max(min(a,b), min(max(a,b),c))` = **4연산, 클론 0** |
| Min · Max | 정렬 후 양 끝 | 두 개씩 접기 = **N−1연산, 클론 0** |

**58 → 44 ms.** 일반 경로(Percentile, N≥4 중앙값)는 그대로 두었다.

### 더 하지 않은 이유

남은 프로필은 `Difference` 33% · `Combine` 18% · `Binarize` 14%로 **고르게 퍼져 있다.**
한 곳을 반으로 줄여도 전체는 15% 남짓 줄어든다. 지금은 위험 대비 이득이 작다.

> 더 큰 이득은 다른 층에 있다 — WPF에서 임계값 슬라이더를 움직일 때
> **파이프라인 전체가 아니라 Binarize부터** 다시 돌리면 44ms가 10ms가 된다.
> 지금 구조로 가능하다(칠판에 중간 결과가 이름표로 남아 있다).

## 2. 누수 — 예외가 났을 때

### 찾은 것

이런 형태가 9곳 있었다.

```csharp
Mat dst = new();
Cv2.무언가(src, dst);   // ← 여기서 던지면 dst가 아무에게도 안 잡힌 채 남는다
return dst;
```

한 번이면 무시할 만하다. 그런데 **WPF에서 슬라이더를 드래그하다 잘못된 값이 들어가면
매 틱마다 샌다.** Mat은 관리 힙 밖이라 GC도 바로 못 거둔다.

### 고친 것

```csharp
return MatOps.Produce(dst => Cv2.무언가(src, dst));
```

`Produce`가 실패 시 해제하고 다시 던진다. 9곳 전부 적용.

### 확인

같은 검사를 **100번 반복**해도 결과가 같고 관리 메모리가 늘지 않는 것을 테스트로 고정했다
(`Repeating_the_same_inspection_is_stable`). WPF가 실제로 할 일이 이것이다.

## 3. 잘못된 입력에 어떻게 답하나

WPF에서 나올 법한 실수 넷을 넣어 봤다.

| 넣은 것 | 답 |
|---|---|
| 크기가 다른 골든 | `골든 이미지 [0]가 검사 이미지와 크기가 다릅니다 — 검사 100×100, 골든 1024×1024` |
| 없는 파일 | `이미지 파일이 없습니다: <전체 경로>` |
| 이미지를 레시피로 | `레시피를 읽지 못했습니다: <경로>` + JSON 위치 |
| 골든 없이 die-to-die | `'chipRegions'를 요구하는데 골든용 이미지를 주지 않았습니다` |

### 고친 것 ① — 크기 검사를 앞으로

크기 불일치가 `Difference`까지 가서야 잡혔다. 그때는 이미 골든을 만들고 정합까지 한 뒤다.
**ROI를 잘못 잡는 것은 가장 흔한 실수**라 입구로 옮겼다.

### 고친 것 ② — 예외 타입을 사용자에게 보이지 않기

```
전   [오류] ArgumentException: ... (Parameter 'chipRegions')
후   [입력 오류] ...
```

사용자가 고칠 수 있는 오류(`입력 오류`·`파일 오류`)와 우리가 예상 못 한 오류를 나눴다.
후자만 타입 이름을 남긴다 — 그건 우리가 추적해야 할 것이니까.

## 4. WPF를 위해 확인해 둔 것

| 물음 | 답 |
|---|---|
| 백그라운드 스레드에서 돌려도 되나 | **된다.** 실행마다 풀·컨텍스트를 새로 만든다. 명부만 공유하고 그건 읽기 전용 |
| 같은 이미지를 두 스레드가 동시에? | **안 된다.** 입력은 호출자 소유이고 잠그지 않는다 |
| 슬라이더 드래그처럼 반복 실행해도 되나 | **된다.** 명부를 한 번만 만들도록 고쳤고, 100회 반복 테스트로 고정 |
| 중간 이미지를 화면에 띄울 수 있나 | **된다.** `RecordingDiagnostics(captureImages: true)`가 노드마다 `{id}.{key}`로 복사해 둔다 |
| 노드별 시간을 보여줄 수 있나 | **된다.** `InspectionResult.Timings` |
| 부분 재실행(임계값만 바꿀 때) | 구조상 가능. 아직 안 만들었다 |

## 5. 남은 것

- **부분 재실행** — 슬라이더가 움직일 때 Binarize부터만 다시 돌리기. 44ms → 10ms
- **Difference 최적화** — 지금 33%. 침식·팽창을 매번 다시 하는데, 골든이 안 바뀌면 밴드도 안 바뀐다
- **큰 이미지** — 2500×2500이면 44ms × 6 ≈ 260ms. 기가픽셀은 타일 단위로 나눠야 한다
