# 결과 봉투 — 결과와 출처를 같이 남기기

검사 결과만 있으면 반년 뒤에 답할 수 없는 질문이 있다.

> 이 결함 3개는 **어느 레시피**로 나온 건가? 그 레시피는 지금 이 파일과 같은가?
> 임계값을 0.12에서 0.10으로 바꾼 게 이 결과 **이전인가 이후인가**?

결과 파일에 `recipeId`만 적어 두면 이 질문에 답하지 못한다. 레시피 **이름**은 그대로 둔 채
내용을 고치는 것이 가장 흔한 작업이기 때문이다. 그래서 결과와 출처를 한 덩어리로 묶는다 — 이것이 봉투다.

---

## 1. 왜 한 칸이 아니라 세 칸인가

봉투에 시각을 넣는 순간 **골든마스터가 죽는다.**

골든마스터는 "같은 입력이면 같은 출력"을 글자 단위로 비교하는 테스트다.
결과 안에 실행 시각이 있으면 매번 달라지니, 결국 둘 중 하나를 하게 된다.

- 비교를 포기한다 → 회귀를 못 잡는다
- 출처를 통째로 무시하고 결함 목록만 비교한다 → **레시피가 바뀐 것도 못 잡는다**

둘 다 손해다. 그래서 기준 하나로 칸을 나눴다. **같은 입력이면 같은 값인가.**

| 칸 | 결정적? | 무엇 |
|---|---|---|
| `defects` | ✅ | 검사 결과 그 자체 |
| `provenance` | ✅ | 무엇으로 돌렸나 — 버전 · 레시피 해시 · 이미지 크기/해시 |
| `run` | ❌ | 언제 · 어디서 · 얼마나 — 시각 · 기계 · 파일 경로 · 소요 시간 |

앞 두 칸만 비교하면 둘 다 얻는다. 결함이 같아도 `recipeSha`가 달라졌으면 그때 알 수 있다
(**참조 드리프트** — 결과 diff 없이 일어나는 변경이라 이게 없으면 영영 모른다).

> 교수님 레포 `doc/developer/웨이퍼_결과_계약.md` #4와 같은 구조다.
> 그쪽 `provenance`에도 시각이 없고, "timestamp·elapsedMs는 이벤트 스트림에만"이라고 못 박아 뒀다.
> 우리는 WPF 이력 화면이 "언제 돌렸나"를 보여줘야 해서 그것을 버리는 대신 **옆 칸(`run`)으로 옮겼다.**

## 3. 왜 경로가 아니라 **내용**의 해시인가

`recipeSha`는 레시피 **원문**의 SHA-256 앞 16 hex다.

경로를 적으면 두 방향으로 다 틀린다.

| 일어나는 일 | 경로 | 내용 해시 |
|---|---|---|
| 레시피 파일을 옮기거나 이름을 바꿈 | 달라진다 (거짓 경보) | 그대로 |
| 같은 경로의 파일 내용을 고침 | **그대로** (놓친다) | 달라진다 |

우리가 묻는 질문은 "어느 파일이었나"가 아니라 **"그때 그 레시피가 지금 이 파일이 맞나"**다.
경로는 기계마다 달라서 어차피 비결정 칸(`run.recipePath`)으로 간다.

### 파싱된 객체가 아니라 텍스트를 해시한다

주석과 공백까지 해시에 들어간다. 그게 맞다 — 이 프로젝트의 레시피는 주석을 허용하고,
거기에 **"왜 이 값인가"**가 적혀 있다. 그것도 레시피의 내용이다.

### 줄바꿈만 예외

`\r\n`을 `\n`으로 맞춘 뒤 해시한다. git이 CRLF로 체크아웃하는 것은 **운반 방식이지 내용이 아니다.**
정규화하지 않으면 같은 레시피가 윈도우와 리눅스에서 다른 해시로 나와,
있지도 않은 드리프트를 매번 보고하게 된다.

### 왜 64자를 다 안 쓰나

화면과 로그에서 안 읽힌다. 16 hex = 64비트면 우연한 충돌은 사실상 없고(생일 한계 ~40억 개),
우리는 이걸 **보안이 아니라 드리프트 감지**에 쓴다 — 누가 일부러 충돌을 만드는 상황이 아니다.

## 4. 픽셀 해시는 기본이 꺼져 있다

```bash
diepipe run ... --hash-images       # 켜야 계산한다
```

1024×1024 F32 한 장이 4MB다. 해시가 몇 ms 붙는데, WPF에서 슬라이더를 드래그하면
초당 수십 번 도는 경로라 그 비용을 매 틱 낼 이유가 없다.
**"정확히 이 픽셀이었다"를 증명해야 하는 보고용 실행에서만** 켠다.

껐을 때 `sha` 필드는 아예 나오지 않는다(null 생략). 크기·포맷은 항상 남는다.

### 두 가지 함정을 피해 뒀다

**① 크기도 해시에 넣는다.** 픽셀만 해시하면 16×2와 2×16이 같은 값을 받는다.

**② 행 단위로 읽는다.** ROI로 잘라낸 `Mat`은 연속이 아니다 — 행과 행 사이에 원본의 나머지가 끼어 있다.
통째로 읽으면 **검사하지도 않은 픽셀이 해시에 섞인다.**
`A_cropped_view_hashes_only_its_own_pixels` 테스트가 잘라낸 뷰와 복사본이 같은 값을 내는지 확인한다.

## 5. 골든마스터가 실제로 비교하는 것

```csharp
string baseline = InspectionResultJson.SerializeDeterministic(result);
```

시각·기계·경로·소요시간을 뺀 텍스트다. 같은 입력이면 **글자 단위로 같아야** 한다.
달라졌다면 둘 중 하나이고, 둘 다 사람이 봐야 할 일이다.

> **⚠ 정확히는 실측이지 보장이 아니다.** `Cv2.PhaseCorrelate`가 멀티스레드 DFT라
> 같은 입력에도 1e-3 수준으로 흔들린다(`Phase_correlation_is_not_bit_exact`).
> 같은 검사 30회에 결과가 1가지였던 것은 임계와 정수 라벨링이 그 흔들림을 흡수하기 때문이고,
> **임계 경계에 걸린 결함은 흔들릴 수 있다.** 정합을 안 쓰는 레시피는 영향이 없다.
> 경위는 [comparison-andi.md](comparison-andi.md) §7.

- 결함이 달라졌다 → 진짜 회귀
- 레시피·버전이 달라졌다 → 참조 드리프트

테스트 3개가 이 성질을 잡아 둔다.

| 테스트 | 고정하는 것 |
|---|---|
| `The_deterministic_part_is_identical_across_runs` | 두 번 돌려도 같은 텍스트 |
| `The_deterministic_part_has_no_clock_and_no_machine` | 시계가 결정적 칸에 새어 들어오지 않음 |
| `Paths_go_to_the_run_record_not_the_provenance` | 폴더만 옮겨도 회귀로 보이지 않음 |

### 파생 값은 저장하지 않는다

`Count`·`Right`·`Bottom`·`Aspect`처럼 계산해서 나오는 값에는 `[JsonIgnore]`를 붙였다.
저장하면 원본과 어긋난 채 굳을 수 있고, 읽는 쪽이 다시 계산하면 그만이다.

## 6. `frameworkVersion`은 손으로 올린다

`Directory.Build.props`의 `<Version>`이 그대로 들어간다. 지금은 `0.1.0`.

**알고리즘의 출력이 달라지는 변경**(임계 처리·정합 규칙 등)을 하면 올린다.
옛 결과 파일과 새 결과 파일을 구별하는 유일한 표시라서, 안 올리면
"코드가 바뀌었는데 결과 파일만 보고는 알 수 없는" 상태가 된다.

## 7. 웨이퍼로 올라갈 때

지금 구조를 그대로 둔다. 이유는 두 가지다.

### 봉투의 세 칸은 층이 바뀌어도 같다

웨이퍼 결과도 같은 기준으로 나누면 된다 — **같은 입력이면 같은 값인가.**

```jsonc
{
  "dies": [ { "col": 1, "row": 0, "zone": "E1",
              "defects": { "items": [...], "inspectionRoi": ..., "recipeId": ... },
              "absOrigin": { "x": 158, "y": 8 } } ],
  "provenance": { "frameworkVersion", "jobSha", "dieCount", "dieRecipeSha" },   // 결정적
  "run":        { "startedAt", "elapsedMs", "machineName" }                     // 비결정
}
```

### die 결과는 고쳐 쓰지 않고 **통째로 품는다**

`defects`를 배열이 아니라 객체로 둔 이유가 이것이다(안쪽이 `items`인 이유도).
`inspectionRoi`·`recipeId`가 같이 들어 있어서 **die당 하나씩 그대로 끼워 넣을 수 있다.**
배열로 납작하게 펴면 그 둘이 갈 곳이 없어져, 웨이퍼 층에서 die마다 다시 만들어 붙여야 한다.

### 절대좌표는 `Defect` 안으로 들어가지 않는다

`Defect.Bounds`·`Centroid`는 **ROI 상대** 좌표다. 웨이퍼 절대좌표는 그 옆에(`absOrigin`) 붙이고,
변환은 상위 층 한 곳에서만 한다. 덮어쓰면 "원래 무엇이었나"를 잃는다.

> 교수님 계약 §3과 같다 — *"절대좌표 계산을 클라이언트에서 재수행하지 말 것 — 어긋난다."*

## 8. 남은 것

- **기대 해시 선언** — 레시피에 "이 템플릿의 해시는 이것이어야 한다"를 적고, 로더가 불일치를 경고.
  교수님 계약도 #4 후속(미구현)으로 같은 것을 적어 뒀다
- **이력 조회** — 지금은 파일 하나씩이다. DB에 넣으면 `recipeSha`로 "이 레시피로 돌린 검사 전부"를 물을 수 있다
- **WPF 연결** — 이력 화면이 보여줄 것은 대부분 `run` 칸이고(언제·얼마나),
  "왜 이 결과인가"를 눌렀을 때 펼칠 것이 `provenance` 칸이다
