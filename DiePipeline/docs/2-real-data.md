# 실데이터 검증 기록

`2026-09-16` · [← 개요](0-overview.md) · [보류 목록](1-deferred.md)

> 합성 이미지가 아니라 **실제 장비에서 취득한 웨이퍼**로 파이프라인을 돌려 본 기록.
> 오검이 나는지, 잡아야 할 것을 잡는지, 얼마나 작은 것까지 잡는지.

---

## 0. 결론

| 물음 | 답 |
|---|---|
| 깨끗한 실데이터에서 오검이 나는가 | **0개** (타일 3장 × 셀 6칸 = 18칸 전부) |
| 심은 결함을 잡는가 | **지름 6px까지 1개씩 정확히** |
| 검출 한계 | 지름 6px ≈ **3µm** (어두운 결함은 4px ≈ 2µm) |
| 한 셀 처리 시간 | **40~60 ms** (100×100, 이웃 5장) |

그리고 **파이프라인의 구멍을 하나 찾았다** — `Difference`가 너무 단순해서
`Normalize`를 켜면 오검이 13개 났다(§4).

## 1. 안전 규칙 — 먼저 정한 것

쓴 이미지는 `visionstack_proto/samples/images/wafer_tile_*.png`이고, 그 README에 이렇게 적혀 있다.

> 원본: 장비에서 취득한 대용량 BMP. **원본 자체는 커밋하지 않는다.**
> (구체적인 파일 이름·해상도는 회사 자료라 옮겨 적지 않는다.)

이 타일들은 **회사 자료에서 잘라낸 파생물**이다. 그래서:

```
❌ DiePipeline 레포에 복사하지 않는다
❌ 잘라낸 셀·결함 주입 이미지도 레포에 넣지 않는다
✅ 원래 자리에서 경로로만 읽는다
✅ 중간 산출물은 레포 밖 임시 폴더에
✅ 레포에 남기는 것은 방법과 숫자뿐
```

**이 문서에 이미지는 한 장도 없다.** 숫자와 방법만 있다.

## 2. 대상 — 그리고 격자를 어떻게 찾았나

| | |
|---|---|
| 파일 | `wafer_tile_1~4.png` (1024×1024, 8-bit gray) |
| 내용 | 라인&스페이스·체커보드 **캘리브레이션 레티클** 패턴 |
| 배율 | 0.5 µm/px (`wafer_sample_2400x1600.raw.json`의 `micronsPerPixel`) |

### 격자는 손으로 고르지 않았다

die-to-die는 **이웃이 닮아야** 성립한다. 그래서 "가장 닮은 이웃쌍"을 **찾아서** 썼다 —
피치 후보마다 모든 시작점을 훑어 `평균 |셀A − 셀B|`가 제일 작은 자리를 고른다.

| 타일 | 피치 100에서 가장 닮은 시작점 | 평균 차이 |
|---|---|---|
| tile_1 | (450, 90) | 0.0111 |
| tile_2 | (35, 10) | 0.0116 |
| tile_3 | (35, 250) | 0.0116 |
| tile_4 | (395, 160) | 0.0094 |

> **처음엔 손으로 골랐다가 헤맸다.** tile_1의 (50,312) 구역은 이웃끼리 차이합이 **577**로
> 다른 구역(128)의 네 배였다. 거기서 나온 "오검"은 검사기 잘못이 아니라
> **die-to-die가 성립하지 않는 자리**를 고른 것이었다.

## 4. 찾은 구멍 — `Normalize`를 켜면 망가진다

같은 구역에서 `Normalize`만 바꿔 봤다.

| Normalize | 결과 |
|---|---|
| `None` | **오검 0** |
| `GaussianBlur` k3 σ1.2 | 오검 **13개** — 전부 폭 2~7 × 높이 84의 **세로 띠** |
| `GaussianBlur` k5 σ1.2 (교수님 기본값) | 전부 이어져 **1개, 면적 8334** (셀 거의 전체) |

### 왜

```
검사 이미지 (날카로움)   ▐█▌▐█▌▐█▌
골든 (σ1.2로 뭉갬)       ▗▓▖▗▓▖▗▓▖
                         ─────────
차이                     ▌ ▐▌ ▐▌ ▐   ← 모든 선 양쪽에 띠
```

골든만 흐리게 하니 **모든 패턴 경계가 차이로 남는다.** 이 타일은 라인&스페이스 레티클이라
세로선이 유난히 촘촘해서 더 심하다.

### 교수님 레시피는 왜 되나 — `neighborMode`

`case1.golden.diff.json`의 Difference를 보면:

```jsonc
"params": { "windowSize": 3, "diffPolicy": "Absolute", "neighborMode": "MinMax" }
```

픽셀 대 픽셀이 아니라 **골든의 근방에서 허용 띠 [최소, 최대]를 만들고** 그 밖으로 나간 만큼만 센다.
우리는 `neighborMode`를 §4 보류로 미뤄 놨었는데, **Normalize와 짝**이었다.
보류 기준 ①(실데이터에서 문제를 겪었고 이게 그 답)에 걸려 바로 만들었다.

### ⚠ 그런데 그것만으론 부족했다

`neighborMode: MinMax`를 넣고 창을 키워도 `Normalize`를 못 켠다.

| Normalize | 창 3 | 창 5 | 창 7 | 창 9 |
|---|---|---|---|---|
| `None` | **0** | **0** | **0** | **0** |
| `GaussianBlur` | 1 | 7 | 31 | 3 |

**블러가 봉우리를 낮추고 골짜기를 올려 허용 띠 자체를 좁히기 때문**이다.
흐려진 골든에서 최소·최대를 뽑아 봐야 원래 범위를 못 되찾는다. **순서 문제다.**

**결론: 우리 레시피는 `Normalize: None`으로 간다.**
(합성 테스트에서는 MinMax가 한 칸 밀림을 완전히 흡수하는 것을 확인했다 — `DifferenceTests`.)

## 5. 검출 한계 — 지름 6px ≈ 3µm

실데이터에는 "여기에 결함이 있다"는 정답표가 없다. 그래서 **답을 아는 결함을 심었다.**

심는 자리는 셀 안에서 **가장 평평한 어두운 자리**를 찾아서 골랐다(13×13 범위폭이 최소인 곳).

| 반지름 | 지름 | 물리 | 심은 면적 | 밝은 결함(+80) | 어두운 결함(−60) |
|---|---|---|---|---|---|
| 6 | 12px | 6µm | 113 | ✅ | ✅ |
| 4 | 8px | 4µm | 49 | ✅ | ✅ |
| **3** | **6px** | **3µm** | 29 | ✅ | ✅ |
| 2 | 4px | 2µm | 13 | ❌ | ✅ |
| 1 | 2px | 1µm | 5 | ❌ | ❌ |

**어두운 결함이 한 단계 더 작은 것까지 잡힌다.** 이 웨이퍼는 밝은 쪽이 포화돼 있어
어두워지는 쪽이 더 도드라지기 때문이다(§6).

> 검출된 면적은 심은 면적보다 작다(예: 49 → 26). `Filter`의 중앙값이 모서리를 깎고,
> 심은 원이 기존 패턴과 겹치기 때문이다. **놓치지는 않지만 면적은 작게 잡힌다.**

---

## 6. 도중에 배운 것 — 심은 게 안 심어졌다

처음 심은 결함이 **밝은 쪽 5개 전부 검출 0개**로 나왔다. 원인은 검사기가 아니라 **심는 쪽**이었다.

```
심은 자리 (85,60) 원래 값 = 255   ← 이미 포화
```

**255에 +70을 더해도 255다.** 아무것도 안 심은 것이었다.

타일의 값 분포를 보면 왜 그런지 보인다.

```
  0~63    0.7%
 64~127  63.3%   ← 배경
128~249   3.8%   ← 가운데가 비어 있다
250~255  32.1%   ← 포화된 구조물
```

**3분의 1이 포화**이고 두 덩어리로 갈라져 있다.

> **배운 것** — 결함을 심어 검사기를 시험할 때 **심은 게 진짜 심어졌는지를 먼저 확인**해야 한다.
> 안 그러면 *"검사기가 못 잡는다"* 와 *"애초에 없다"* 를 구별할 수 없다.

이 분포는 `Binarize`의 `Otsu`가 왜 이 데이터에서 무너지는지도 설명한다([1-deferred.md](1-deferred.md) §6).

## 7. 정합 — 정상 die를 복제해 시험했다

실데이터에서는 **정합이 한 번도 실행되지 않았다.** 네 구역 전부 거부됐다.

```
구역 A  shift=(25.3,  0.0)  거부   ← 한계 20px 초과
구역 B  shift=(47.8,-36.0)  거부
구역 C  shift=(49.7, -0.1)  거부
구역 D  shift=(50.1, -0.1)  거부
```

셀 주기가 100px이라 위상상관이 **반주기 50px에 잠기기** 때문이다. 가드가 막은 것은 맞는데,
그러면 *"정합이 실제로 되긴 하는가"* 를 확인할 수가 없다.

### 그래서 답을 아는 어긋남을 만들었다

**정상 die를 복제해 일부러 민 뒤**, 정합이 그 양을 되찾는지 봤다.
실데이터 셀(`wafer_tile_2` 셀 0, 100×100)이라 무늬는 진짜 회로 무늬다.

| 민 양 | 잰 양 | 응답 | 판정 | 차이 줄어듦 |
|---|---|---|---|---|
| (0, 0) | (−0.000, −0.000) | 0.999 | 받음 | — |
| (1, 0) | **(1.000, 0.000)** | 0.999 | 받음 | **100.0%** |
| (0.5, 0) | (0.822, 0.001) | 0.975 | 받음 | 37.5% |
| (2, 1) | (1.975, 0.963) | 0.981 | 받음 | 98.4% |
| (3.5, −2.5) | (3.296, −2.163) | 0.869 | 받음 | 93.8% |
| (7, 4) | (6.885, 3.889) | 0.731 | 받음 | 97.6% |
| (15, 0) | (14.964, −0.026) | 0.838 | 받음 | 98.9% |
| (25, 0) | (25.018, 0.020) | 0.740 | **거부** | 0% |
| (50, 0) | (49.954, 0.095) | 0.613 | **거부** | 0% |

**① 정확하다.** 1px 밀림을 `1.000`으로 되찾고 차이를 **100% 없앤다.**

**② 가드가 20px에서 정확히 끊는다.** 25px·50px은 **답을 맞게 냈는데도** 거부했다.
그게 가드의 뜻이다 — *"맞는 것 같아도 이웃 die가 25px씩 밀릴 리 없다."*
실제로 그런 값이 나온다면 정합으로 덮을 게 아니라 **스테이지를 봐야 한다.**

**③ 주기 무늬에서는 더 일찍 포기한다.** 같은 (7,4)인데:

| | 보통 무늬(tile_2) | 주기 무늬(tile_1) |
|---|---|---|
| 응답 | 0.731 → 받음 | **0.229 → 거부** |

`minResponse = 0.3`이 그 사이를 갈랐다.

### ⚠ 서브픽셀은 절반만 된다

```
0.5px 밀림  →  0.822로 잼  →  차이가 37.5%만 줄어든다
```

보간으로 만든 그림이라 원래 정보가 없고, 되밀 때 보간이 한 번 더 들어가 흐려진다.
**고칠 것이 아니라 알고 있어야 할 성질**이다 —
서브픽셀 어긋남은 정합으로 다 못 없애고, 그래서 `Difference`의 `neighborMode`가 필요하다.
**두 장치가 같은 문제를 나눠 맡는다.**

## 7.5 die-to-die가 **원리적으로 못 잡는 것**

실데이터를 보고 나서 분명해진 것들. 검사기를 더 잘 만들어도 안 되고, **층이 하나 더 있어야** 한다.

| 못 잡는 것 | 왜 |
|---|---|
| **반복 결함**(reticle·mask 결함) | 모든 die에 똑같이 있으면 **골든에도 들어간다.** 빼면 사라진다 |
| **웨이퍼 전체 무늬** | 코팅 링·척 자국·스크래치 — die 하나만 보면 "배경이 좀 어둡네" 정도라 임계를 못 넘는다 |
| **가장자리 die** | 이웃이 모자라다 |
| **군집** | die마다 1개씩이면 다 통과하는데, **지도로 보면 한쪽에 몰려 있는** 경우 |
| **공정 드리프트** | 모든 die가 같이 변하면 서로 닮았으니 차이가 0 |

교수님 레포의 웨이퍼 층 노드들이 이 답이다 —
`WaferDefectCluster`(지도에서 군집) · `DefectCluster`(die 안 군집) ·
`Sampling`(어느 die를 볼지) · `TransformAbs`(die→웨이퍼 좌표) · `InspectDies`(die들을 돌린다).

> **비유** — 학생 한 명씩 채점하면 "이 학생은 통과"가 나온다.
> 그런데 **반 전체가 같은 문제를 틀렸다면** 학생 문제가 아니라 가르친 쪽 문제다.
> 채점만으로는 안 보이고 **성적표를 모아 봐야** 보인다.

## 8. 어떻게 돌렸나

```bash
diepipe run -r samples/recipes/die.diff.json \
            -i <타일 경로> \
            --pitch 100 --origin 35,10 --count 6 --cell 0
```

`--origin`에서 시작해 `--pitch`씩 가로로 `--count`칸을 자르고,
그중 `--cell`번을 검사, 나머지를 이웃으로 쓴다.

**격자·이웃 고르기는 웨이퍼 층에서 제대로 만든다.** 이건 *"파이프라인이 진짜 웨이퍼에서 도는가"* 를
눈으로 보려고 만든 **진단용 러너**다.

끝값: `0` 결함 없음 · `3` 결함 있음 · `1` 오류 · `2` 레시피 오류
