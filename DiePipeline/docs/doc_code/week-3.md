## 1. 왜 다시 만들었나 — 이 주의 시작

처음 계획은 **각자 파이프라인을 만들어 보고 서로 돌려보는 것**이었다.
만들어서 돌려봤고, 두 가지가 드러났다.

### ① 서로 너무 달랐다

같은 die-to-die 검사인데 구조가 달라서, **상대 코드를 읽으려면 처음부터 다시 읽어야 했다.**

| | 이쪽 | 동기 |
|---|---|---|
| 출발점 | Lesson15·16 (구조부터) | 브리핑 문서 (알고리즘부터) |
| 외부 라이브러리 | OpenCvSharp | 없음 — FFT·BMP·PNG를 직접 구현 |
| 노드가 결과를 주는 법 | 칠판에 올린다 | 스테이지가 반환한다 |
| 알고리즘 수 | 7 + 꼬리 3 | 15 |

둘 다 맞는 설계다. 문제는 **합칠 때 기준이 없다**는 것이었다.

### ② 내가 이해하지 못한 채로 만들고 있었다

이게 더 큰 이유다. **처음 보는 개념이 너무 많았다.**
돌아가긴 하는데 **왜 돌아가는지 설명할 수가 없었다.**

줄 수로 세어 보니 눈에 보였다.

```
v1 전체 6,621줄
  ├ Lesson15·16에서 온 것       내가 배운 것
  ├ 브리핑에서 온 것             동기가 배운 것
  └ 1,535줄 (23%)  ← 어디에도 없는 것
```

그 1,535줄이 무엇이었냐면 — 부분 재실행 · 결과 봉투 · 내용 해시 · 메모리 풀 · 성능 측정 도구.
**엔지니어링으로는 옳지만, 브리핑에도 Lesson에도 없는 것들이었다.**

> **설명할 수 없는 코드가 레포의 4분의 1을 차지하고 있었다.**

배운 것을 거스른 자리도 있었다. 1주차 Lesson09에서
"허용오차로 비교한다, 완전일치는 쓰지 않는다" 를 배웠는데,
v1은 결과를 **글자 단위로 완전일치** 비교하고 있었다.
(나중에 정합 측정이 비트 단위로 재현되지 않는다는 걸 발견하고 정정했다.)

### 그래서 방향을 바꿨다

> **학습한 Lesson을 중심으로 다시 짜되, 동기도 읽을 수 있어야 하므로
> 교수님이 주신 파일을 합쳤다.**

| 무엇을 | 어디서 | 왜 |
|---|---|---|
| **뼈대와 순서** | Lesson15·16 | 내가 이해한 것이어야 설명할 수 있다 |
| **타입 이름 · 파일 이름 · 기본값** | 교수님 자료 | 둘 다 아는 **공통 기준**이 된다 |

이렇게 하면 갈라지는 자리마다 **"교수님은 어떻게 했나"** 라는 답이 하나 있다.
둘이서 그걸 기준으로 맞출 수 있다.

### v2의 규칙

```
배운 것과 브리핑 범위 안에서만 만든다.
좋아 보이는 기능이라도 "이걸 어디서 배웠나"에 답할 수 없으면 넣지 않는다.
```

**v1을 버린 게 아니라, v1에서 재서 얻은 것만 가져왔다.**

| 가져온 것 | 왜 |
|---|---|
| **Align 가드** (`minResponse` · `maxShiftPx`) | 코드 30줄로 오검 11개를 막았다. 측정으로 확인된 사실이다 |
| 검출 한계 지름 4px | 주입 결함으로 실제로 쟀다 |
| Align이 제일 무겁다 | 나중에 최적화할 자리 |

**뺀 것** — 부분 재실행 · 결과 봉투 · 내용 해시 · 메모리 풀 · 성능 측정 도구.
필요해지면 그때 넣는다. **"좋아 보인다"는 이유로는 안 넣는다.**

## 2. 다시 만들었다

### 갈라지는 자리에서 교수님 구현을 따랐다

그 결과 둘이 바뀌었다.

| | 바뀐 내용 |
|---|---|
| **Filter** | 방법 하나를 고르는 게 아니라 **순서 있는 체인**. 모폴로지도 그 안의 한 스텝이다 |
| **Binarize** | 6종 그대로 (Threshold · Otsu · Range · Sigma · Adaptive · Hysteresis), **기본값도 그대로** |

> **기본값을 우리가 재서 정하지 않는다.** 한 번 그러다 틀렸다 —
> 합성 데이터로 재고 확정했는데 실웨이퍼에서 다른 답이 나왔다.
> 재는 것은 계속하되, **결과는 판단 근거로 문서에 남기고 기본값은 교수님 값을 쓴다.**

### 만든 것

| 단계 | 내용 | 출처 |

| 0 | 프로젝트 뼈대 | vision_stack |
| 1 | 칠판 · 노드 · 엔진 | Lesson15 |

| 3 | 알고리즘 10종 | 브리핑 + 교수님 |
| 4 | 꼬리 3종 | 브리핑 |
| 7 | 대용량 BMP 부분 읽기 | 새로 |

**왜 엔진이 알고리즘보다 먼저인가** — 요리사도 레시피도 없이 "칠판과 순서만" 먼저 만든다.
이상하게 들리지만, **가짜 노드로 테스트하면 알고리즘 없이도 파이프라인이 도는지** 확인할 수 있다.
여기서 고정한 성질(순서대로 돈다 · 중복 이름표를 막는다 · 끝나면 메모리를 놓는다)은
진짜 알고리즘이 들어와도 그대로 유지된다.

## 3. ★ 막힌 것 — Normalize를 켜면 망가진다

실데이터를 처음 돌렸다. 깨끗한 구역 18칸에서 **오검 0개**가 나왔다.
그런데 `Normalize`만 바꿔 보니 —

| Normalize | 결과 |
|---|---|
| `None` | **오검 0** |
| `GaussianBlur` k3 | 오검 **13개** — 전부 폭 2~7의 **세로 띠** |
| `GaussianBlur` k5 (교수님 기본값) | 전부 이어져 **1개, 면적 8334** (셀 거의 전체) |

### 왜

```
검사 이미지 (날카로움)   ▐█▌▐█▌▐█▌
골든 (뭉갬)              ▗▓▖▗▓▖▗▓▖
                         ─────────
차이                     ▌ ▐▌ ▐▌ ▐   ← 모든 선 양쪽에 띠
```

**골든만 흐리게 하니 모든 패턴 경계가 차이로 남는다.**
이 데이터는 세로선이 유난히 촘촘한 캘리브레이션 무늬라 더 심했다.

### 교수님 레시피는 왜 되나 — `neighborMode`

교수님 Difference는 픽셀 대 픽셀로 빼지 않는다.
**골든의 근방에서 허용 띠 [최소, 최대]를 만들고 그 밖으로 나간 만큼만** 센다.

우리는 이걸 "나중에" 로 미뤄 놨었는데, **`Normalize`와 짝**이었다. 바로 만들었다.

### ⚠ 그런데 그것만으론 부족했다

`neighborMode`를 넣고 창을 키워도 `Normalize`를 못 켠다.

| Normalize | 창 3 | 창 5 | 창 7 | 창 9 |
|---|---|---|---|---|
| `None` | **0** | **0** | **0** | **0** |
| `GaussianBlur` | 1 | 7 | 31 | 3 |

**블러가 봉우리를 낮추고 골짜기를 올려 허용 띠 자체를 좁히기 때문**이다.
흐려진 골든에서 최소·최대를 뽑아 봐야 원래 범위를 못 되찾는다. **순서 문제다.**

## 4. ★ 막힌 것 — 심은 게 안 심어졌다

### 왜 이걸 하게 됐나

검사기가 **얼마나 작은 결함까지 잡는지**를 알아야 한다. 그래야 "이 정도는 놓칠 수 있다" 를 말할 수 있다.

그런데 실데이터에는 **"여기 결함이 있다" 는 정답표가 없다.**
그래서 **답을 아는 결함을 우리가 직접 만들어 넣었다.** 이것을 "심는다" 고 부른다.

```
깨끗한 die 이미지를 하나 고른다
      ↓
그 안의 한 자리에 동그라미를 그린다
      ↓
밝은 결함 = 그 자리 밝기에 +70   /   어두운 결함 = −60
      ↓
지름 12 · 8 · 6 · 4 · 2px 다섯 가지로 만든다
      ↓
검사기에 넣고 "몇 개까지 잡나" 를 센다
```

### 무슨 일이 있었나

**어두운 결함 5개는 잘 잡혔는데, 밝은 결함은 5개 전부 검출 0개**로 나왔다.

처음에는 검사기가 밝은 결함에 약한 줄 알았다. 그런데 심은 자리의 **원래 픽셀 값**을 찍어 보니 —

```
심은 자리의 원래 값 = 255   ← 이미 꽉 찬 값
```

8비트 이미지에서 **255가 최댓값**이다. 거기에 +70을 더해도 여전히 255다.

> **아무것도 안 심겨 있었다.** 검사기는 없는 것을 못 잡은 것뿐이다.

### 왜 하필 그 자리였나 — 히스토그램을 봤다

> ⚠ 여기부터는 **검사 과정이 아니다.** *"왜 심은 게 안 심겼지"* 를 파헤치려고
> 이미지를 들여다본 것이다. 검사할 때는 이런 걸 안 본다.

**히스토그램**은 픽셀을 **밝기별로 통에 나눠 담아 센 것**이다.
8비트 회색 이미지에서 픽셀 하나는 `0`(완전한 검정) ~ `255`(완전한 흰색) 값을 갖는다.

```
  0~63    0.7%   ▏
 64~127  63.3%   ████████████████████████████████
128~249   3.8%   ██
250~255  32.1%   ████████████████
```

#### 이 모양이 말하는 것 — 봉우리가 둘, 가운데가 비었다

보통 사진은 이렇게 안 생긴다. 인물이나 풍경은 밝기가 **완만하게 이어져** 넓게 퍼진다.
그런데 이 그림은 **두 덩어리로 갈라져** 있고 사이가 텅 비었다.

| 통 | 무엇인가 |
|---|---|
| 64~127 · **63%** | **배경** — 아무것도 없는 어두운 바탕 |
| 250~255 · **32%** | **구조물** — 밝게 찍힌 무늬 |
| 128~249 · **3.8%** | 거의 전부 **둘 사이의 경계선 픽셀** |

**가운데 3.8%가 핵심이다.** 배경에서 구조물로 넘어갈 때 딱 몇 픽셀만 중간 밝기를 거친다.
즉 **경계가 칼같이 떨어지는 그림**이다.

> **비유** — 수채화가 아니라 **스텐실**이다.
> 물감이 번지는 게 아니라 **칠한 데와 안 칠한 데**만 있다.

검사기를 점검하려고 만든 **테스트 무늬**라서 그렇다. 일부러 대비를 최대로 올려 찍는다.

#### 그래서 문제였다 — 32%가 "꽉 찬" 값이다

250~255 구간에 픽셀 3분의 1이 몰려 있고, 그중 상당수가 **정확히 255**다.

```
저울의 최대 눈금이 100kg이다
  ↓
120kg인 사람이 올라가도 → 100
140kg인 사람이 올라가도 → 100
  ↓
"원래 몇 kg이었는지" 는 저울에 안 남는다
```

이것을 **포화(saturation)** 라고 한다. 밝기가 255를 넘으면 **넘은 만큼은 기록되지 않고 잘린다.**
그 자리에 `+70` 을 더해 봐야 여전히 255다.

**심을 자리를 아무 데나 골랐으니 3분의 1 확률로 여기 걸린다.** 실제로 다섯 개 다 걸렸다.

고친 방법은 심는 자리를 고르는 것이었다 —
**주변이 평평하면서 어두운 자리**(작은 범위 안에서 밝기 폭이 제일 작은 곳)를 찾아 거기 심었다.

### 제대로 심고 나서 다시 쟀다

| 심은 지름 | 밝은 결함 | 어두운 결함 |
|---|---|---|
| 12px | ✅ | ✅ |
| 8px | ✅ | ✅ |
| 6px | ✅ | ✅ |
| **4px** | ❌ | **✅** |
| 2px | ❌ | ❌ |

밝은 쪽이 한 단계 일찍 놓친다. 위의 분포가 그 이유다 —
**이미 꽉 찬 자리가 많아서 밝아지는 변화는 잘 안 드러나고, 어두워지는 변화는 도드라진다.**

> 검출된 **면적**(결함으로 잡힌 픽셀 수)은 심은 것보다 작게 나온다 — 예: 49 → 26.
> `Filter` 가 모서리를 깎고, 심은 동그라미가 원래 무늬와 겹치기 때문이다.
> **놓치지는 않지만 크기는 작게 잡힌다.**

### 결론

```
이 검사기는 지름 4px(어두운 결함)까지 잡는다. 밝은 결함은 6px까지다.
```

> **배운 것** — 결함을 심어 검사기를 시험할 때는 **심은 게 진짜 심어졌는지를 먼저 확인**해야 한다.
> 안 그러면 **"검사기가 못 잡는다"** 와 **"애초에 없다"** 를 구별할 방법이 없다.
> 하마터면 멀쩡한 검사기를 고치러 갈 뻔했다.

## 5. 정합 가드가 진짜 되는지 확인했다

### 정합이 무엇이고, 왜 가드를 달았나

die를 잘라낼 때 **몇 픽셀 어긋나는** 일이 있다. 그대로 빼면 **배선 경계마다 얇은 띠**가 남고
그게 전부 결함으로 잡힌다. 그래서 **얼마나 밀렸는지 재서 되밀어 놓는 것**이 정합(Align)이다.

2주차에 여기서 사고가 났다. 무늬가 규칙적이면 "가장 닮은 자리" 가 여러 개라
재는 도구가 **엉뚱한 답을 자신 있게** 내놓는다. 그것 때문에 깨끗한 die에서 **오검 11개**가 났다.

그래서 **못 믿을 때 멈추는 가드** 두 개를 달았다.

| 손잡이 | 뜻 |
|---|---|
| `minResponse` (0.3) | **응답**(얼마나 확실하게 한 자리를 짚었나, 0~1)이 이보다 낮으면 **잰 값을 안 쓴다** |
| `maxShiftPx` (20) | 이웃 die가 20px씩 밀릴 리 없다. 그런 값이 나오면 **거부한다** |

### 문제 — 실데이터에서는 한 번도 안 돌았다

가드를 달고 실데이터를 돌렸더니 **네 구역 전부 거부**됐다.

```
구역 A  shift=(25.3,  0.0)  거부   ← 한계 20px 초과
구역 B  shift=(47.8,-36.0)  거부
구역 C  shift=(49.7, -0.1)  거부
구역 D  shift=(50.1, -0.1)  거부
```

**47.8 · 49.7 · 50.1** — 셋이 약속이나 한 듯 50 근처다.
이 무늬는 일정 간격으로 반복되는데, **그 간격의 절반만큼 밀어도 무늬가 겹쳐 보인다.**
재는 도구가 거기에 걸려 있었다.

가드가 막은 건 옳다. 그런데 **한 번도 실행이 안 되니 "정합이 실제로 되긴 하는가" 를 확인할 수가 없다.**

> 소화기를 달아 놨는데 불이 한 번도 안 났다. **작동하는지는 아직 모른다.**

### 그래서 답을 아는 어긋남을 만들었다

**정상 die를 복제해 일부러 정해진 양만큼 민 뒤**, 정합이 **그 양을 되찾는지** 봤다.
민 양을 우리가 아니까 **맞았는지 틀렸는지 채점할 수 있다.**

| 민 양 | 잰 양 | 응답 | 판정 | 차이가 줄어든 정도 |
|---|---|---|---|---|
| (0, 0) | (−0.000, −0.000) | 0.999 | 받음 | — |
| (1, 0) | **(1.000, 0.000)** | 0.999 | 받음 | **100.0%** |
| (0.5, 0) | (0.822, 0.001) | 0.975 | 받음 | 37.5% |
| (2, 1) | (1.975, 0.963) | 0.981 | 받음 | 98.4% |
| (3.5, −2.5) | (3.296, −2.163) | 0.869 | 받음 | 93.8% |
| (7, 4) | (6.885, 3.889) | 0.731 | 받음 | 97.6% |
| (15, 0) | (14.964, −0.026) | 0.838 | 받음 | 98.9% |
| (25, 0) | (25.018, 0.020) | 0.740 | **거부** | 0% |
| (50, 0) | (49.954, 0.095) | 0.613 | **거부** | 0% |

> **"차이가 줄어든 정도"** 는 되민 뒤 두 이미지의 차이가 얼마나 사라졌는지다.
> 100%면 어긋남이 완전히 없어진 것이고, 0%면 아무것도 못 고친 것이다.

**① 재는 것 자체는 정확하다.** 1px 밀림을 `1.000` 으로 되찾고 차이를 **100% 없앤다.**

**② 가드가 20px에서 정확히 끊는다.** 25px·50px 줄을 보면 **답을 맞게 냈는데도 거부**했다.
얼핏 손해 같지만 그게 가드의 뜻이다 —

> *"맞는 것 같아도 이웃 die가 25px씩 밀릴 리 없다."*
> 그런 값이 진짜로 나온다면 정합으로 덮을 게 아니라 **장비 스테이지를 봐야 한다.**

**③ 무늬가 반복되면 더 일찍 포기한다.** 똑같이 (7,4)만큼 밀었는데 —

| | 보통 무늬 | 반복 무늬 |
|---|---|---|
| 응답 | 0.731 → 받음 | **0.229 → 거부** |

`minResponse = 0.3` 이 정확히 그 사이를 갈랐다. **2주차에 오검 11개를 냈던 상황이 여기서 막힌다.**

### ⚠ 알고 있어야 할 성질 — 서브픽셀은 절반만 된다

```
0.5px 밀림  →  0.822 로 잼  →  차이가 37.5%만 줄어든다
```

1px 밀림은 100% 고치는데, **0.5px처럼 픽셀 사이에 걸친 어긋남은 절반밖에 못 고친다.**
0.5px 민 그림은 보간(옆 픽셀을 섞어 만든 값)이라 **원래 정보가 이미 없고**,
되밀 때 보간이 한 번 더 들어가 더 흐려지기 때문이다.

**이건 고칠 것이 아니라 알고 있어야 할 한계다.**
그래서 뺄 때 **허용 띠**(골든 근방의 최소~최대 범위)를 따로 둔다 —
정합이 못 없앤 나머지를 그쪽이 흡수한다. **두 장치가 같은 문제를 나눠 맡는다.**

### ✅ 결론

```
가드는 제대로 동작한다.
맞는 어긋남(1~15px)은 받아서 거의 완전히 고치고,
말이 안 되는 값(25px 이상)과 못 믿을 측정(응답 0.3 미만)은 거부한다.
```

> 이 데이터에서는 결국 **정합이 한 번도 안 쓰인다.** 격자가 정확해서 밀린 게 없기 때문이다.
> 그래서 최종 레시피에서는 `Align` 을 **뺐다**(§9).

## 6. 대용량 원본을 다루는 법을 만들었다 — BMP ↔ raw

지금까지는 잘라 놓은 작은 타일로 돌렸다. **원본은 통째로 메모리에 못 올린다.**
그래서 **필요한 부분만 파일에서 뜯어 읽는 리더**를 직접 만들었다. 실제 장비가 하는 방식이다.

### 무엇을 만들었나

```
Roi                     읽을 네모 (x, y, 너비, 높이)
ImageGeometry           "그 픽셀은 파일의 몇 번째 바이트인가" 계산기
IByteReader             바이트를 읽는 통로 — 배열용 / 실제 파일용 둘
MemoryMappedByteReader  파일을 주소만 잡아 두고, 건드린 곳만 OS가 올려 준다
BmpHeader               BMP 앞머리를 읽어 폭·높이·비트수·팔레트를 알아낸다
IImageSource            "네모 하나 다오" / "축소본 하나 다오"
```

### BMP 파일이 어떻게 생겼나

```
0 ┌────────────────┐
  │ 파일 헤더 14바이트 │  'BM' · 파일 크기 · 데이터 시작 위치
14├────────────────┤
  │ DIB 헤더 40바이트 │  폭 · 높이 · 비트수 · 압축 방식
54├────────────────┤
  │ (팔레트)        │  8비트 회색이면 1024바이트
  ├────────────────┤
  │ 픽셀 데이터      │
  └────────────────┘
```

**함정 둘.**

| | |
|---|---|
| 높이가 **음수**일 수 있다 | 음수면 위에서 아래로 저장된 것 (보통은 아래에서 위로) |
| 한 줄이 **4의 배수**로 맞춰진다 | 폭 × 비트수를 그대로 쓰면 틀린다. 남는 자리를 채운다 |

> **비유** — 큰 지도책에서 한 동네를 보는 데 책을 통째로 외울 필요가 없다.
> **몇 쪽 몇 번째 칸**인지만 계산하면 그 쪽만 펴면 된다.
> `ImageGeometry`가 그 "몇 쪽 몇 번째 칸" 계산기다.

### 쟀더니

| | |
|---|---|
| 1024×1024 한 칸 읽기 | **168 ms** / 메모리 **4.0 MB** |
| 더 큰 네모 — 두 번째부터 | **23 ms** |
| 축소본 한 장 | 0.7 초 |

**제대로 읽었는지를 세 가지로 확인했다.**

1. 직접 만든 BMP를 읽어 OpenCV 결과와 **완전히 같음**
2. 실제 파일의 헤더가 말하는 크기와 **실제 파일 크기가 일치**
3. 우리가 만든 축소본과 교수님이 따로 만든 축소본의 차이 **0.0010**

3번이 제일 값어치 있다. **완전히 다른 경로로 만든 결과가 같다**는 뜻이기 때문이다.

## 7. ★ 막힌 것 — 축소본이 거짓말을 했다

이웃 die끼리 얼마나 닮았는지를 축소본으로 쟀었다. **전체 해상도로 다시 재니 결론이 뒤집혔다.**

| 이웃 | **전체 해상도** | 축소본 |
|---|---|---|
| 같은 행 1칸 | **0.0368** ← 제일 닮음 | 0.0134 |
| 같은 열 1칸 | 0.0520 | **0.0084** ← 제일 닮음 |
| 같은 행 2칸 | 0.0555 | 0.0176 |
| 대각 1칸 | 0.0687 | 0.0165 |
| 같은 열 2칸 | 0.0788 | 0.0134 |

축소본에서는 "세로가 1.6배 더 닮았다" 고 적었었다.
전체 해상도에서는 **가로가 1.4배 더 닮았다.** 반대다.

### 왜

```
크게 줄이면  →  한 픽셀이 수십 픽셀의 평균이 된다
                       ↓
   행마다 다른 조명·스캔 차이가 그 평균에 묻힌다
                       ↓
        세로 이웃이 실제보다 닮아 보인다
```

> ### 줄인 이미지는 "작은 원본"이 아니다.
> 무엇이 지워졌는지 모르면 거기서 낸 결론도 못 믿는다.

전에 그 결론에 **단서를 셋 달아 뒀었다.** 그중 둘이 실제로 결론을 뒤집었다.

> **단서를 달았다는 것이 결론을 믿어도 된다는 뜻은 아니다.**

## 8. ★★ 제일 값어치 있는 교훈 — 파라미터는 짝이다

### 무엇을 비교했나

골든(이웃을 겹쳐 만든 "정상" 이미지)을 만들 때 **정할 것이 둘**이다.

| | 고를 수 있는 것 |
|---|---|
| **누구를 이웃으로 쓸까** | 같은 행 좌우 **1칸** / 거리를 늘려 **3장** / 상하좌우 **3장** · **5장** / 같은 열 **3장** |
| **어떻게 겹칠까** | **Mean**(평균) / **Median**(중앙값) |

여섯 가지 조합을 **모든 die에** 돌렸다. 임계 0.2 · `minArea` 500 고정.

### 표를 읽기 전에 — 열이 무슨 뜻인가

| 열 | 뜻 |
|---|---|
| **골든 장수** | 그 die의 골든을 몇 장으로 만들었나 (평균) |
| **Absolute** | 차이의 **절댓값**으로 봤을 때 잡힌 개수 — 어두워진 것과 밝아진 것 둘 다 |
| **DarkOnly** | **어두워진 쪽만** 봤을 때 잡힌 개수 |
| **Bright(=오검)** | `Absolute` − `DarkOnly`. **밝아진 쪽** — 이 데이터에서는 전부 오검이다 |
| **미러 증가** | 아래 미러 시험에서 늘어난 개수 |

> **왜 밝은 쪽이 전부 오검인가** — 이 공정의 결함은 **어두워진다.**
> 그래서 "밝아진 자리" 는 결함이 아니라 무언가 잘못돼서 생긴 것이다.

### 결과

| 이웃 · 합치기 | 골든 장수 | Absolute | **진짜 결함** | **오검** | 미러 증가 |
|---|---|---|---|---|---|
| 같은 행 1칸 · **Mean** | 1.5 | 36 | **12** | 24 | **+26** |
| 같은 행 3장 · **Mean** | 3.0 | 34 | **12** | 22 | 0 |
| 같은 행 3장 · **Median** | 3.0 | **12** | **12** | **0** | **0** |
| 상하좌우 3장 · Median | 3.0 | 14 | **12** | 2 | 0 |
| 상하좌우 5장 · Median | 5.0 | 12 | **12** | 0 | 0 |
| 같은 열 3장 · Median | 3.0 | 14 | **12** | 2 | 0 |

> **골든 장수가 1.5인 이유** — 좌우 1칸이면 안쪽 die는 이웃이 2장인데
> 맨 끝 die는 한쪽이 없어 1장뿐이다. 그래서 평균이 1.5다.

**진짜 결함 12개는 여섯 조합 전부 같다.** 달라지는 것은 오검뿐이다.

### 읽는 법

```
이웃을 1.5장 → 3장, 두 배로 늘렸다    →  오검 24 → 22    2개밖에 안 줄었다
합치는 법만 Mean → Median 으로 바꿨다  →  오검 24 →  0    한 번에 사라졌다
```

**듣는 손잡이는 "몇 장 쓰느냐" 가 아니라 "어떻게 합치느냐" 였다.**
장수를 늘리는 것은 **읽기 비용을 두 배로 치르고 거의 못 얻는다.**

### 왜 그런가

```
Mean    이웃을 전부 섞는다     →  먼 이웃일수록 덜 닮았으니
                                  섞을수록 골든이 흐려진다
Median  안 닮은 것은 버린다    →  멀리서 데려와도 손해가 없다
```

실제로 이웃이 얼마나 닮았는지 재 보면 **가까울수록 닮았다.**

| 이웃 | 평균 차이 (작을수록 닮음) |
|---|---|
| 같은 행 **1칸** | **0.0368** |
| 같은 행 **2칸** | 0.0555 |

`Mean` 은 이 **0.0555짜리 먼 이웃도 그대로 섞어 넣는다.**
`Median` 은 가운데 값을 고르므로, 멀리서 데려온 장이 튀면 **안 뽑힌다.**

### 가장자리에서는 오히려 나빠진다

맨 끝 열(골든이 부족한 자리)만 따로 세어 보면 뚜렷하다.

| | 골든 장수 | Absolute | 오검 |
|---|---|---|---|
| 1칸 Mean | 1.0 | 12 | **8** |
| **3장 Mean** | 3.0 | **18** | **14** ← 이웃을 더 줬는데 나빠졌다 |
| 3장 Median | 3.0 | **4** | **0** |

**이웃을 더 주는 것이 공짜가 아니다.** `Mean` 에서는 손해가 될 수 있다.

### 미러 시험 — 표의 마지막 열은 어떻게 쟀나

**미러 문제**란 이것이다.

```
골든을 이웃으로 만든다
      ↓
이웃에 결함이 있으면 그것도 골든에 섞인다
      ↓
내 die는 멀쩡한데, 그 자리가 "골든보다 밝다" 로 나온다
      ↓
결함이 부호만 반대로 되비친다
```

이걸 재려고 **이웃 하나에 일부러 결함을 심고, 손대지 않은 가운데 die를 검사했다.**
늘어난 개수가 곧 "이웃의 결함이 되비친 것" 이다.

| | 결과 |
|---|---|
| `Mean` + 이웃 1~2장 | **+26** — 이웃의 결함이 골든의 절반을 차지하니 당연하다 |
| `Median` 3장 | **0** — 오염된 한 장이 가운데 값으로 안 뽑힌다 |
| `DarkOnly` 로 보면 | **전 조합 0** — 되비친 것은 밝은 쪽이라 부호가 막는다 |

#### ⚠ 이 시험을 한 번 잘못 만들었다

처음에 주입 세기를 **0.35**로 넣었다. 그런데 이웃 2장을 평균 내면 `0.35 ÷ 2 = 0.175`가 되어
**임계값 0.2를 못 넘었다.** 그래서 `Mean` 이 미러에 강한 것처럼 보였다.

세기를 **0.6**으로 올리고 나서야 **+26**이 드러났다.

> **시험이 통과했다고 안전한 게 아니라, 시험이 그 문제를 건드리지 못한 것일 수 있다.**

### ⚠ 그리고 이 오검 숫자는 `DarkOnly` 를 뺀 값이다

미러를 막는 법은 **둘이고 서로 독립**이라, 두 조합이 각각 다른 쪽을 골랐다.

| | 막는 법 | 어디서 막나 |
|---|---|---|
| **우리 조합** | `Median` 으로 겹친다 | 골든을 만들 때 **앞에서** |
| **교수님 조합** | `DarkOnly` — 어두워진 쪽만 본다 | 뺀 다음 **뒤에서** |

```
교수님 조합은 둘이 아니라 셋이었다 —  1칸  +  Mean  +  DarkOnly
```

표의 `DarkOnly` 열을 보면 **여섯 조합 전부 12**다. 진짜 결함만 나오고 오검은 0이다.
위의 24·22는 *"만약 `Absolute` 를 썼다면"* 이라는 가정값이고,
**교수님 레시피를 그대로 쓰면 오검 0이다.**

> **짝에서 하나를 떼어내고 비교하면 그 짝이 부당하게 나빠 보인다.**
> 처음에 이 표를 "교수님 짝은 오검 24" 로 읽었는데, 그건 `DarkOnly` 를 떼어낸 숫자였다.

## 9. ★ 막힌 것 — 두 실수가 서로를 가리고 있었다

### 왜 이걸 하게 됐나

우리 레시피는 노드를 **여덟 개** 이어 붙여 놓은 것이었다.

```
Combine → Normalize → Align → Difference → Filter → Binarize → Label
```

결과는 맞게 나왔다 — 결함 12개, 오검 0개. **그런데 각 노드가 실제로 무슨 일을 하는지는 몰랐다.**
그냥 다 켜 놓고 답이 맞으니 넘어간 것이다.

그래서 **하나씩 떼어 보기로 했다.**

### 어떻게 했나

`Combine → Difference → Binarize → Label` 만 남긴 것을 **바탕**이라 하고,
거기에 나머지 노드를 하나씩 얹어 가며 결과를 비교했다.

| 구성 | Absolute | 오검 |
|---|---|---|
| **바탕만** | **12** | **0** |
| 바탕 + `Normalize` | 52 | **40** |
| 바탕 + `Align` | 12 | 0 |
| 바탕 + `Filter` | 12 | 0 |
| 바탕 + `Normalize` + **`Filter`** | **12** | **0** |
| **예전 우리 레시피 = 셋 다** | **12** | **0** |

> `Absolute` 는 밝아진 것과 어두워진 것을 **둘 다** 센 개수다.
> 이 공정의 결함은 어두워지므로 **밝아진 것은 전부 오검**이다. 즉 `오검 = Absolute − 12`.

### 무슨 일이 있었나

두 번째 줄과 다섯 번째 줄을 나란히 보면 보인다.

```
Normalize 를 켜면      →  오검 40개가 생긴다
거기에 Filter 를 켜면  →  그 40개가 사라진다
```

- **`Normalize`** 는 골든을 흐리게 만든다. 그래서 **모든 무늬 경계에 얇은 자국**이 남는다 → 오검 40개
- **`Filter`** 는 얇은 것을 지우는 노드다. 그래서 **그 자국을 도로 지운다** → 0개
- **`Align`** 은 아예 아무 영향이 없다. 격자가 정확해서 밀린 게 없기 때문이다

> **예전 레시피가 맞는 답을 낸 것은 실력이 아니라 두 실수가 서로 상쇄돼서였다.**
> 흐리게 만들고, 그 자국을 다시 지우고. **둘 다 빼면 같은 답이 더 빨리 나온다.**

세 노드를 빼고도 결과는 그대로 **결함 12 · 오검 0**이었고, 대신 빨라졌다.

### 왜 그런 값을 쓰고 있었나 — 출처를 거슬러 올라갔다

교수님 레포에 레시피가 **두 벌** 있었다. 우리는 그중 하나를 베꼈는데, **합성 데모용**이었다.

| | Normalize | 임계 | minArea | 쓰라고 만든 데이터 |
|---|---|---|---|---|
| 데모용 (우리가 베낀 것) | 있음 | 0.12 | 5 | 합성 이미지 |
| **실데이터용** | **없음** | **0.2** | **500** | **진짜 웨이퍼** |

**교수님이 틀린 게 아니라, 우리가 데모용을 실데이터에 쓴 것**이었다.
합성 이미지는 깨끗하고 무늬가 단순해서 `Normalize` 를 켜도 자국이 안 남는다.

그리고 **문서와 코드가 어긋나 있었다** — 며칠 전에
*"`Normalize` 를 켜면 망가진다"* 고 적어 놓고 **레시피는 켜진 채로 커밋돼 있었다.**

### ✅ 결론

```
Normalize · Align · Filter 셋을 뺐다. 결과는 그대로, 속도는 빨라졌다.
```

> **배운 것 둘**
> 1. **답이 맞다고 과정이 맞는 게 아니다.** 떼어 보기 전까지는 알 수 없다
> 2. **남의 설정을 가져올 때는 "무엇을 위해 만든 값인가" 를 봐야 한다.**
>    같은 사람이 만든 같은 형식의 파일이라도 **쓰라고 한 데이터가 다르다.**

## 10. 어느 손잡이가 실제로 듣는가

### 왜 이걸 하게 됐나

§9에서 레시피를 손보고 나니 **조절할 값이 둘** 남았다.

| 손잡이 | 하는 일 |
|---|---|
| **임계값** | 차이가 이보다 크면 "결함" 으로 친다 (0~1) |
| **`minArea`** | 잡힌 덩어리가 이 픽셀 수보다 작으면 **버린다** |

둘 다 올리면 덜 잡히고 내리면 더 잡힌다. **그런데 어느 쪽을 얼마나 움직여야 하는지 감이 없었다.**
그래서 **하나씩 바꿔 가며 전부 돌려 봤다.**

### 결과

| 임계 | minArea | 검출(Absolute) | 그중 진짜 | 오검 |
|---|---|---|---|---|
| 0.12 | **5** | **488** | 12 | **476** |
| 0.12 | 500 | 12 | 12 | 0 |
| 0.15 | 500 | 12 | 12 | 0 |
| **0.20** | 500 | 12 | 12 | 0 |
| 0.25 | 500 | 12 | 12 | 0 |
| 0.30 | 500 | 12 | 12 | 0 |

### 무슨 일이 있었나

**아래 다섯 줄이 전부 똑같다.** 임계값을 0.12에서 0.30까지 **2.5배** 움직였는데 결과가 안 바뀐다.

> 진짜 결함은 **완전한 검정**(밝기 0.000)이라 골든과의 차이가 압도적이다.
> 임계값을 어디에 두든 이 차이는 넘는다. **그래서 임계값이 안 듣는다.**

**듣는 것은 `minArea` 하나였다.** 5로 두면 **476개**가 잡힌다.
잡힌 것이 전부 티끌만 한 덩어리라, **크기로 한 번만 걸러도** 다 사라진다.

```
minArea  5    →  검출 488  (진짜 12 + 오검 476)
minArea 500   →  검출  12  (진짜 12 + 오검   0)
```

### ✅ 결론

```
임계값 0.20 · minArea 500 으로 정했다.
```

임계값 **0.20** 은 0.12~0.30이 전부 같은 결과이므로 **그 한가운데**를 골랐다.
어느 쪽으로 데이터가 조금 변해도 여유가 있다.

> **배운 것** — **바꾸기 전에 어느 손잡이가 실제로 듣는지부터 확인해야 한다.**
> 오검 476개를 보고 "임계값이 낮아서 그렇겠지" 하고 임계값을 붙들었으면
> 0.12에서 0.30까지 올려도 476개가 그대로 있는 걸 보며 **하루를 버렸을 것이다.**

## 11. 정답표가 없을 때 무엇을 믿는가

이 데이터에는 "여기 결함이 있다" 는 답안지가 없다. 그래서 이렇게 판단했다.

1. 결함 수가 **여섯 전략에서 전부 같았다** (12개) → 전략과 무관한 것이니 진짜다
2. 찾은 것들의 밝기가 전부 **0.000**(완전한 검정)이고 크기가 거의 같은 사각형 → 일부러 심어 둔 시험용 결함이다
3. 분포가 **웨이퍼의 한쪽 절반에만** 몰려 있었다 → 알고 있던 정답 오라클과 맞는다

**셋이 서로를 받쳐 준다. 하나만으로는 근거가 안 된다.**

## 12. 레시피를 두 벌 남겼다

| | `die.diff.json` (기본) | `die.diff.median.json` (대안) |
|---|---|---|
| 이웃 | 같은 행 **좌우 1칸** | 같은 행 **거리 늘려 3장** |
| 합치기 | `Mean` | `Median` |
| 차영상 | **`DarkOnly`** | `Absolute` |
| 미러를 막는 법 | **부호** — 어두운 쪽만 본다 | **중앙값** — 이상치를 버린다 |
| 필요한 것 | 결함이 어느 쪽인지 **아는 것** | 이웃 **3장** |
| 못 보는 것 | **밝은 결함** (덧붙은 이물질) | (없음) |
| 속도 | **268 ms** | 967 ms |
| 결과 | 결함 12 · 오검 0 | 결함 12 · 오검 0 |

**기본은 빠르고 공정 지식을 쓰고, 대안은 느리지만 아무것도 몰라도 된다.**

기본을 교수님 쪽으로 둔 이유 둘.

- `DarkOnly` 는 요령이 아니라 **"이 공정의 결함은 어두워진다"는 지식을 레시피에 적은 것**이다.
  알고리즘을 똑똑하게 만드는 대신 **아는 것을 조건으로 넣어 문제를 없앤다** — 검사 엔지니어의 사고방식이다.
- 대안의 장점(밝은 결함도 본다)은 **이 데이터로 확인하지 못했다.** 여기엔 밝은 결함이 하나도 없다.
  **재보지 않은 장점으로 기본값을 정하지 않는다.**

## 13. 배경은 왜 안 빼도 되고, 무엇은 빼야 하나

### 배경을 따로 처리하지 않는다

사진을 검사한다고 하면 *"배경은 빼고 봐야 하는 것 아닌가"* 싶다. **die-to-die 에서는 안 그래도 된다.**

이 방식은 **결함이 어떻게 생겼는지를 안 본다.** 오직 **이웃과 다른지**만 본다.

```
검사 die     배경 100  │  구조물 255  │  배경 100
골든         배경 100  │  구조물 255  │  배경 100
──────────────────────────────────────────────────
차이              0    │       0      │      0      ← 아무것도 안 남는다
```

**배경은 이웃 die에도 똑같이 배경**이라 빼면 0이 된다. 구조물도 마찬가지다.

> **비유** — 같은 도장을 두 번 찍고 겹쳐 보면 **잉크가 있든 없든 똑같이 겹쳐서** 아무것도 안 보인다.
> 한쪽에만 얼룩이 있어야 그것만 튀어나온다.

따로 "배경 빼기" 를 안 하는 게 아니라, **배경을 신경 쓸 필요가 없는 구조**다.
정상을 따로 정의하지 않아도 되는 것이 die-to-die 를 쓰는 이유다.

### 오히려 배경도 검사해야 한다

배경을 검사 대상에서 빼면 **이물질을 못 잡는다.**

```
먼지 한 톨이 배경 위에 앉았다
  → 회로 위가 아니니 당장은 안 망가진다
  → 그런데 다음 공정에서 움직이면 회로 위로 간다
  → 라인 어딘가가 더럽다는 신호이기도 하다
```

**배경이 깨끗한지가 오히려 중요한 정보**다.

### 그런데 빼야 할 자리는 따로 있다

배경이 아니라 **다른 이유로** 검사에서 빼야 하는 영역들이다.

| 빼야 할 곳 | 왜 |
|---|---|
| **스크라이브 레인** | die 사이 잘라내는 여백. 원래 지저분하고, 불량이어도 상관없다 |
| **정렬 마크** | 장비가 보는 표식. die마다 미세하게 달라 **차이가 항상 남는다** |
| **글자 · 번호** | 웨이퍼마다 다르게 찍힌다 → die끼리 비교하면 무조건 다르다 |
| **die 테두리 몇 px** | 잘라내는 자리라 항상 흔들린다 |

**이런 자리는 이웃과 달라도 결함이 아니다.**
그런데 die-to-die 는 "다르면 결함" 이라서 **전부 잡아 버린다.**

그래서 *"여기는 보지 마라"* 를 그림으로 그려 주는 장치가 필요하다 — **마스크(mask)** 다.

### 우리는 아직 안 만들었다

교수님 레포에는 있다.

```
Core/Algorithms/IMaskApplier.cs
OpenCv/Algorithms/MaskApplier.cs      BinaryMaskApplier
OpenCv/Stages/Factories.cs            "MaskApply" 노드
```

**이번 데이터에서는 안 필요했다.** 검사용 테스트 무늬라 글자도 마크도 없고,
격자가 정확해서 테두리도 안 흔들린다.

지금은 **`minArea 500` 이 그 역할을 어설프게 대신**하고 있다 —
"작은 건 다 무시" 라서 마크나 테두리 자국이 작으면 같이 걸러진다.
하지만 **크기로 거르는 것과 위치로 거르는 것은 다르다.**
큰 글자가 찍혀 있으면 `minArea` 로는 절대 못 막는다.

> **진짜 제품 웨이퍼로 가면 반드시 필요해진다.** 거기엔 글자도 마크도 다 있다.
> 보류 목록에 올려 둔다 — 그 데이터를 만나면 그때 만든다.

## 14. die-to-die가 원리적으로 못 잡는 것

실데이터를 보고 나서 분명해진 것들. 검사기를 더 잘 만들어도 안 되고, **층이 하나 더 있어야** 한다.

| 못 잡는 것 | 왜 |
|---|---|
| **반복 결함** (마스크 결함) | 모든 die에 똑같이 있으면 **골든에도 들어간다.** 빼면 사라진다 |
| **웨이퍼 전체 무늬** | 코팅 링 · 척 자국 — die 하나만 보면 "배경이 좀 어둡네" 정도라 임계를 못 넘는다 |
| **가장자리 die** | 이웃이 모자라다 |
| **군집** | die마다 1개씩이면 다 통과하는데, **지도로 보면 한쪽에 몰려 있는** 경우 |
| **공정 드리프트** | 모든 die가 같이 변하면 서로 닮았으니 차이가 0 |

> **비유** — 학생 한 명씩 채점하면 "이 학생은 통과" 가 나온다.
> 그런데 **반 전체가 같은 문제를 틀렸다면** 학생 문제가 아니라 가르친 쪽 문제다.
> 채점만으로는 안 보이고 **성적표를 모아 봐야** 보인다.

**이것이 4주차에 웨이퍼 층을 만드는 이유다.**
