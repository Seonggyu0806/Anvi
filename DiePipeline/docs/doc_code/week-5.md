# 5주차 — 화면 (WPF)

`2026-09-25 ~ 10-02` · **진행 중** — 화면(die 탭 · 웨이퍼 탭)은 섰다. **WPF + 파이프라인 보수** 중(§11)

> 이 주는 **계획**이라 "할 것" 과 "미리 확인해 둔 것" 을 적는다.
> **웨이퍼 층이 끝난 뒤 다시 손봤다** — 화면이 쓸 재료가 die 한 장에서 웨이퍼 한 장으로 늘었다.

---

## 한 줄

**지금은 명령행으로만 돌아간다. 사람이 보면서 값을 조절할 수 있는 화면을 얹는다.**

## 1. 왜 화면이 필요한가

검사 프로그램의 값은 **책상에서 정할 수 없다.** 3주차에 그걸 겪었다.

```
임계값 0.12 ~ 0.30 → 결과가 전부 같다
minArea 5 → 500    → 오검 476개가 사라진다
```

**어느 손잡이가 듣는지는 돌려 봐야 안다.** 그런데 지금은 한 번 돌릴 때마다
명령을 다시 치고 숫자를 읽어야 한다.

> **비유** — 라디오 주파수를 맞추는데 다이얼이 없고
> "95.7 을 입력하고 전원을 껐다 켜세요" 만 있는 것과 같다.
> **돌려가며 듣는 것**이 다이얼이다.

## 2. 할 것

| | 무엇 | 아래층 준비 | 화면 |
|---|---|---|---|
| 1 | 이미지 열기 · 레시피 열기 | ✅ | ✅ 레시피 열기·내보내기 + 좌표 곁다리 파일 |
| 2 | 파이프라인 실행 · 결과 표시 | ✅ | ✅ 미리보기 — 값을 바꾸면 저절로 다시 돈다 |
| 3 | **결함 오버레이** — 원본 위에 찾은 자리를 네모로 | ✅ 절대 좌표가 나온다 | ✅ 검사 조각 위에 네모 |
| 4 | **중간 결과 보기** — 각 단계가 무엇을 만들었나 | ✅ 칠판에서 꺼낸다 | ✅ 단계별 썸네일, 실행 순서대로 |
| 5 | **슬라이더** — 임계값을 끌면서 결과가 바뀌는 걸 본다 | ✅ 부분 재실행 **없이** 됐다(§8) | ✅ 끝이 둘 다 있는 값에만 |
| 6 | **웨이퍼 맵** — 어느 die가 불량인지 한눈에 | ✅ die별 결과가 그대로 있다 | ✅ 웨이퍼 탭 — 깨끗함·결함·실패 3색 |
| 7 | **정렬 결과 표시** — 각도·원점·표식 자리 | ✅ 숫자와 까닭이 다 나온다 | ✅ 각도·배율·die(0,0)·짝·어긋남·점수 |
| 8 | **결함 목록** — 골라서 그 자리로 이동 | ✅ 샘플링으로 개수를 제한한다 | ◐ 맵 칸을 누르면 그 die 의 결함 표. 결함 → 원본 자리 이동은 아직 |

7·8은 **웨이퍼 층이 끝나면서 새로 생긴 항목**이다. 처음 계획을 쓸 때는 없던 재료다.

> 처음엔 화면이 **die 한 장**(합성 조각)만 봤다. 6·7·8은 웨이퍼 한 장을 올려야 의미가 있어서,
> 합성 웨이퍼 생성을 Cv 층으로, 웨이퍼 검사 흐름을 Wafer 층으로 먼저 꺼냈다(§9). 그 위에 웨이퍼 탭을 얹었다.

## 3. 1주차에 배워 둔 것 — MVVM

Lesson08에서 만들어 본 것들이 그대로 재료다.

```
MainViewModel       화면이 보여줄 값과 명령
RelayCommand        버튼 하나 = 객체 하나
ObservableObject    값이 바뀌면 화면에 알린다
IDialogService      대화상자를 인터페이스로 빼 둔다
BitmapConvert       OpenCV 이미지 → 화면이 그릴 수 있는 형식
```

**`IDialogService` 를 인터페이스로 빼 두는 이유**가 이 중에 제일 중요하다.

> "파일을 못 열었습니다" 대화상자가 코드에 박혀 있으면 **테스트를 돌릴 수가 없다** —
> 테스트 중에 창이 떠서 사람이 누를 때까지 멈춰 버린다.
> 인터페이스로 빼 두면 테스트에서는 **"눌렀다고 치는 가짜"** 를 끼워 넣으면 된다.

## 4. 미리 확인해 둔 것 — 2주차 점검에서

WPF를 얹고 나면 아래층을 고치기 어렵다. 그래서 **얹기 전에** 세 가지를 확인해 뒀다.

### ① 느리면 슬라이더를 못 만든다

슬라이더를 드래그하면 **초당 수십 번** 검사가 돈다.

| 합성 die 크기 | 전체 실행 | 부분 재실행 | |
|---|---|---|---|
| 1024×1024 | 86.1 ms | **4.1 ms** | 21배 |
| 큰 die | 536.5 ms | **22.0 ms** | 24배 |

**임계값을 바꿨을 때 실제로 달라지는 것은 뒤의 두 단계뿐**이다.

```
Combine → Normalize → Align → Difference → Filter │ Binarize → Label
└──────── 임계값과 무관. 지난 결과를 그대로 쓴다 ────┘ └─ 이것만 다시 ─┘
```

앞을 다시 안 돌면 **21배**가 빨라진다.

> 2주차에 "1024×1024 44 ms" 라고 적은 것과 여기 86.1 ms 는 **다른 설정**이다.
> 44 ms 는 실데이터 타일에 노드 8개, 86.1 ms 는 합성 die에 노드가 더 많은 레시피다.
> **시간을 적을 때는 무엇을 어떻게 쟀는지 같이 적어야 한다.**

> **답이 같은지부터 확인했다.** 부분 재실행과 전체 실행의 결함을 면적·중심까지 대조했다.
> **빨라지려고 답이 달라지면 아무 의미가 없다.**

⚠ **이 구조는 v2에 안 들어가 있다.** 3주차 규칙(배운 범위 안에서만) 때문에 뺐다.
슬라이더를 만들 때 **다시 필요해지면 그때 넣는다** — 그때는 "왜 넣는지" 에 답할 수 있다.

> **→ 슬라이더를 만들고 재 봤다. 지금은 필요 없었다(§8).** 넣을 조건도 거기 적었다.

### ② 예외가 나도 메모리를 놓아야 한다

화면에서는 **잘못된 입력이 계속 들어온다.** 파일을 잘못 고르고, 값을 이상하게 넣는다.
예외가 날 때마다 메모리를 안 놓으면 **쓸수록 무거워진다.**

| | 전 | 후 |
|---|---|---|
| 예외 경로 메모리 누수 | 9곳 | **0** |
| 100회 반복 시 메모리 증가 | — | **없음** (테스트로 고정) |

### ③ 오류 메시지가 사람 말이어야 한다

명령행에서는 예외 이름이 그대로 떠도 된다. **화면에서는 안 된다.**

```
❌  System.ArgumentOutOfRangeException: Specified argument was out of...
✅  이미지 크기가 서로 다릅니다 (1024×1024 와 512×512)
```

그래서 예외 타입을 사용자에게 보이지 않도록 정리해 뒀다.

## 5. 화면이 쓸 자리는 이미 있다

| 화면이 필요한 것 | 지금 있는 것 |
|---|---|
| 각 단계가 얼마나 걸렸나 | 엔진이 단계별 시간을 낸다 |
| 각 단계의 중간 이미지 | **칠판에서 이름표로 꺼낸다** — 따로 만들 필요가 없다 |
| 노드 끄기 체크박스 | 레시피의 "끄기" 와 **1:1 대응**되게 만들어 뒀다 |
| 취소 | 취소 토큰이 파이프라인을 관통한다 |

**칠판 구조가 여기서 값을 한다.** 중간 결과를 보려고 따로 저장할 필요가 없다 —
이미 이름표를 달고 칠판에 올라가 있기 때문이다.

> 2주차에 동기 구현과 비교하면서 **"이건 나중에 못 넣는다"** 고 판단했던 것들이
> 전부 이 자리에서 쓰인다.

### 웨이퍼 층이 끝나면서 재료가 더 늘었다

| 화면이 필요한 것 | 지금 있는 것 |
|---|---|
| **웨이퍼 맵 칸 색칠** | die별로 `존 · 결함 수 · 상태` 가 한 줄 요약(`DieResult`)으로 나온다 — ⚠ 아래 |
| **결함을 원본 위에 찍기** | 결함마다 **웨이퍼 절대 좌표**가 채워져 있다 — 화면이 다시 계산할 필요가 없다 |
| **결함이 너무 많을 때** | 샘플링 3종(큰 순서 · 면적대 · 무작위). **씨가 고정**이라 같은 목록이 다시 나온다 |
| **정렬이 됐는지 보여주기** | 각도 · 원점 · 짝 개수 · 어긋남 · 배율추정 · 평균 점수까지 숫자로 |
| **정렬이 안 됐을 때** | 거부 까닭이 **사람 말 한 줄**로 들어 있다 |
| **시험용 그림** | `demo` 명령 — 데이터 없이 그림을 만든다. **정답표도 같이 찍는다** |

> ★ **화면은 계산을 다시 하지 않는다.** 좌표도 색칠 근거도 아래층이 이미 내놓는다.
> 화면이 좌표를 다시 구하기 시작하면 **아래층과 어긋나는 순간**이 반드시 온다 —
> 그때 증상은 "지도의 점이 살짝 밀렸다" 뿐이라 원인을 못 찾는다.

### ★ 실패를 색으로 구분해야 한다

웨이퍼 맵에서 **"결함 0개" 와 "검사를 못 했다" 는 다르다.** 아래층은 이미 셋을 구분한다.

```
깨끗함        검사했고 결함이 없다
결함 N개      검사했고 N개를 찾았다
검사 실패 ×   못 봤다 — 결함 0개로 보이지만 안 본 것이다
```

명령행도 끝값을 나눠 둔다 — `0` 결함 없음 · `3` 결함 있음 · `4` 터진 die 있음 · `5` 정렬을 못 믿음.
**화면도 이 셋을 다른 색으로 보여야 한다.** 한 색으로 합치면 제일 위험한 상태가 숨는다.

> ⚠ **처음 이 계획을 쓸 때 "아래층은 이미 셋을 구분한다" 고 적었는데, 반만 맞았다.**
> 웨이퍼 맵을 만들려고 열어 보니 맵용 요약 `DieResult` 에 **실패를 적을 칸이 없었다.**
> 터진 die 의 요약 = `{ DefectCount: 0 }` — 깨끗한 die 와 **글자 하나 안 다르다.**
> 주석은 *"검사했는데 깨끗했다와 검사를 안 했다는 다르다"* 고 약속하는데, 타입이 그걸 못 담았던 것이다.
>
> 명령행 맵(`×`)은 `DieInspection.Failed` 를 직접 봐서 맞게 나왔다. 그래서 4주차 내내 안 드러났다.
> **"웨이퍼 맵에 찍을 요약"** 이라는 이름을 믿고 화면이 그걸 그대로 썼다면, 완료 기준 7번이
> 막으려던 칸이 바로 생겼을 것이다.
>
> `DieState`(Clean · Defective · **Failed**)와 실패 까닭을 요약에 넣고, 테스트
> *터진_die는_요약에서도_깨끗함과_구분된다* 로 박았다. **화면을 붙여 보기 전엔 안 보이는 구멍이었다.**

## 6. 예상되는 어려움

| | |
|---|---|
| **큰 이미지를 화면에 어떻게** | 원본은 통째로 못 올린다. 3주차의 부분 읽기를 화면 확대/축소에 연결해야 한다 |
| **드래그 중 취소** | 슬라이더를 끌면 이전 실행이 아직 도는 중이다. 취소하고 새로 시작해야 한다 |
| **웨이퍼 맵의 크기** | die가 수백 개면 네모 수백 개를 매번 다시 그릴 수 없다 |
| **웨이퍼 한 장은 오래 걸린다** | die 한 장은 수 ms 지만 웨이퍼는 그 N배다. 슬라이더처럼 즉각 반응할 수 없다 — **진행 표시**가 필요하다 |
| **기울어진 웨이퍼** | 정렬은 풀리는데 `warp read` 가 없어 **0.05° 넘으면 좌표를 못 믿는다.** 화면이 그 상태를 숨기면 안 된다 |

### ⚠ `warp read` 숙제

기울기가 `0.05°` 를 넘으면 지금은 **검사를 시작조차 안 한다.** 정렬은 제대로 풀리는데
die 를 펴서 읽는 단계가 없어서다.

```
짝 A   warp read 로 편다  +  R(θ) 로 되돌린다   ← 목표
짝 B   축정렬로 자른다    +  아무것도 안 건다   ← 지금
```

**화면을 만들면 이 상태가 바로 드러난다** — 사용자가 삐뚤게 놓인 웨이퍼를 열면 아무것도 안 돈다.
`warp read` 를 붙이는 날 `AbsoluteTransform` 의 회전 가드도 **같이** 지워야 한다. 둘은 짝이다.

## 7. 얹기 전에 메운 구멍 — 노드 끄기(`Enabled`)

블록 에디터의 **체크박스 하나**가 아래층에 없던 개념이었다. 화면을 붙이기 전에 먼저 뚫었다.

### 끄면 뒷 노드가 없는 이름표를 읽는다

노드를 실행에서 빼면 그 노드의 출력이 안 생긴다. 그런데 **뒷 노드는 그 이름표를 계속 읽는다.**

그래서 빼는 대신 **별칭**을 건다 — "이 노드의 출력 = 이 노드의 입력".

```
켜짐   roi → [Normalize] → normed → [Difference]
꺼짐   roi ┄┄┄┄┄┄┄┄┄┄┄┄┄→ normed → [Difference]   ← normed 를 roi 로 바꿔 읽는다
```

> **비유** — 정수기를 떼면서 **수도관을 그 자리에 바로 이어 붙이는 것**이다.
> 싱크대 쪽 배관은 한 군데도 안 건드린다. 물만 안 걸러질 뿐 흐르긴 흐른다.

**레시피 파일을 한 글자도 안 고친다**는 게 핵심이다. 화면에서 껐다 켤 때마다 파일을 다시 쓰면,
사용자가 손으로 고쳐 둔 것과 뒤섞여 무엇이 원본인지 알 수 없게 된다.

### 그래서 입력 1개·출력 1개만 끌 수 있다

입력이 둘이면 **어느 쪽을 물려줄지가 정해지지 않는다.** 검증기가 미리 막는다.

| 고친 곳 | 무엇 |
|---|---|
| `NodeConfig` | `Enabled` 한 줄 |
| `NodeRegistry.CreateAll` | 꺼진 노드를 빼고 별칭을 건다. 연달아 꺼져도 **끝까지** 따라간다 |
| `RecipeValidator.CheckDisabled` | 입력 1·출력 1 강제 + 종류 물려주기 |

### ★ 교수님 쪽 검증기와 실행기가 서로 다른 걸 본다

여기가 이번에 찾은 것이다. 교수님 코드에서 **종류 검사는 검증기에 있고, 별칭은 실행기에 있다.**

```
검증기(RecipeValidator)   producedBy[키].Port  ← 노드가 '선언한' 출력 포트를 본다
실행기(RecipeRunner)      alias[출력] = 입력    ← 꺼진 노드를 실제로 건너뛴다
```

**둘이 안 만난다.** 검증은 끝난 뒤에 별칭이 걸리기 때문이다.

우리 `Combine` 이 정확히 그 틈에 빠진다 — **개수는 1:1 인데 종류가 바뀌는** 노드다.

```
Combine   ImageList(chipRegions) ──받아──→ Image(golden) ──내놓는다
```

끄면 `golden` 자리에 `chipRegions` 가 흘러가서, **한 장을 기다리는 `Difference` 에 여러 장이 간다.**
교수님 검증기는 `golden = Image` 라는 선언만 보므로 **통과시킨다.** 실행 중에 터진다.

> **비유** — 믹서기를 껐는데 **주스 대신 사과 다섯 알이 컵에 담겨 나오는 것**이다.

**교수님이 막아 두지 않은 게 아니라 안 마주친 자리다.** 레포 전체에서 `enabled: false` 가 나오는 곳은
`Normalize` 한 군데뿐인데, 이건 Image 받아 Image 내놓는 노드라 종류가 안 바뀐다.

**우리는 그 둘을 맞췄다.** 꺼진 노드의 출력 이름표에 *선언된* 종류가 아니라
**입력이 실제로 물고 있는 종류**를 올린다. 그러면 뒷 노드의 종류 검사가 **이미 있는 그물로** 잡는다.

```
교수님   체크박스 끈 순간 조용함  →  검사 돌리면 터진다
우리     체크박스 끈 순간 잡힌다  →  검사가 시작되지 않는다
```

새 검사를 만든 게 아니라 **어긋남을 흘려보내 기존 검사에 걸리게 한 것**이다. 4줄이다.

> ⚠ 교수님 코드는 **읽고 따진 것이지 실행해서 확인하지 않았다.** 세 곳(검증기 2차 패스 ·
> 화면 체크박스 · `Combine` 디스크립터)의 코드 경로로 낸 결론이다.

### 남겨 둔 것 — 포맷 검사

교수님 `PortDescriptor` 에는 종류(`Kind`) 말고 **포맷**이 하나 더 있다.

```csharp
PixelFormat? ExpectedFormat = null,
```

*"둘 다 이미지인데 하나는 8비트, 하나는 실수"* 를 잡는 검사다. 우리는 작업 포맷이 하나로
고정이라 지금은 필요 없다. **필요해지는 날 붙인다.**

## 8. 슬라이더 — 부분 재실행은 재 보고 안 넣었다

### 재 본 것

슬라이더를 끌면 값이 바뀔 때마다 미리보기가 **전체를 처음부터** 다시 돈다. 그 시간을 상태줄에 찍었다.

```
미리보기 (40×40 합성 조각, 노드 6개, 썸네일 6장 인코딩 포함)   1 ~ 3 ms
끊김 없이 따라오려면 (초당 60번)                               16 ms 이하
```

**기준의 5분의 1도 안 된다.** 부분 재실행을 넣어도 사람이 느낄 차이가 없다. 그래서 **안 넣었다.**

> **비유** — 집 앞 편의점에 가는데 지름길을 찾는 것과 같다. 2분 걸리는 길을 1분으로 줄여 봐야
> 아무도 모른다. 지름길이 값어치를 하는 건 **멀리 갈 때**다.

### ★ 넣어야 하는 날

같은 일을 **큰 그림**으로 하면 얘기가 다르다. 2주차에 잰 숫자가 있다.

```
1024×1024 die   전체 86.1 ms   부분 4.1 ms
큰 die          전체 536.5 ms  부분 22.0 ms
```

**미리보기가 합성 조각 대신 실제 크기 die 를 돌리기 시작하면 그날 넣는다.** 86 ms 면 초당 열 번
겨우라 슬라이더가 끊긴다. 상태줄의 ms 숫자가 16 을 넘기 시작하면 그게 신호다.

> 2주차에 *"필요해지면 그때 넣는다 — 그때는 왜 넣는지에 답할 수 있다"* 고 적었다.
> 이번엔 **"왜 안 넣는지"** 에 숫자로 답한 것이다. 둘 다 같은 원칙이다 — **추측하지 말고 잰다.**

### 슬라이더가 붙는 값과 안 붙는 값

슬라이더는 **위아래 끝이 둘 다 디스크립터에 적힌 값**에만 뜬다(`PropertyField.HasRange`).

| | 끝 | 슬라이더 |
|---|---|---|
| `Binarize.value` | 0 ~ 1 | ✅ 100칸 |
| `Binarize.blockSize` | 3 ~ 99, 홀수 | ✅ **2칸씩** — 짝수에 못 멈춘다 |
| `Label.minArea` | 0 ~ (없음) | ❌ |

`minArea` 에 안 붙는 건 **일부러다.** 화면이 "면적은 1000까지" 를 지어내면 디스크립터 밖에 규칙이 생긴다.
필요하면 디스크립터에 `Max` 를 적는 게 맞다 — 그러면 검증도 같이 따라온다.

"붙일지·몇 칸씩인지" 는 판단이라 **WPF 가 아니라 Editor 층**(`PropertyField.HasRange`·`Step`)에 두고 테스트로 박았다.

### 끌어 보면 보이는 것

합성 조각에서 `Binarize.value` 를 끌면 **0 에서 0.46 까지 결과가 계속 1개**다. 결함의 밝기 차이가 0.46 이라서다.

3주차 실데이터에서 *"임계값 0.12~0.30 결과가 전부 같다"* 고 했던 그 모양이다.
**결함이 또렷하면 임계값은 넓은 구간에서 안 듣는다.** 말로 적어 둔 것을 이제 손으로 끌어서 본다.

## 9. 웨이퍼 쪽 준비 — 그림과 흐름을 명령행 밖으로

화면에 웨이퍼를 올리려고 보니 **필요한 것 둘이 명령행 안에 `private` 으로 갇혀 있었다.**

```
DemoCommand.cs   542줄   합성 웨이퍼를 그리는 코드
WaferCommand.cs  652줄   웨이퍼 검사 흐름(정렬 → 격자 → die 마다 레시피 → 모으기)
```

화면이 쓰려면 **베끼거나 꺼내거나**다. 베끼면 둘이 조용히 갈라진다 — 특히 *"정렬을 못 믿으면
검사를 시작하지 않는다"* 가드가 한쪽에만 남으면, 화면에서 **안 봤는데 깨끗해 보이는** 웨이퍼가 생긴다.
그래서 둘 다 꺼냈다.

> **비유** — 수도꼭지가 하나일 땐 정수기를 꼭지에 달아도 된다. 꼭지가 둘이 되면
> **정수기를 본관에 달아야** 두 꼭지가 같은 물을 받는다.

| 꺼낸 것 | 어디로 | 남은 것 |
|---|---|---|
| 합성 웨이퍼 그리기 | `Cv/Imaging/SyntheticWafer` | `DemoCommand` 542 → 229줄 — 옵션·파일·정답 출력 |
| 웨이퍼 검사 흐름 | `Wafer/Execution/WaferInspection` | `WaferCommand` 652 → 538줄 — 옵션·글자 출력·끝값 |

### ★ 웨이퍼 층이 OpenCV 를 알게 됐다 — 교수님 쪽으로 맞췄다

검사 흐름은 사진을 읽고 die 레시피를 돌려야 해서 **Cv 를 알아야** 한다. 그런데 4주차에
*"웨이퍼 층은 Core 만 참조한다"* 고 정해 뒀다. 교수님은 반대였다(`Wafer → OpenCv`).

교수님 문서를 다시 읽고 이유를 찾았다. **교수님도 처음엔 우리처럼 `refs Core` 로 설계했다가,
구현하면서 바꿨다**(Phase 8 §2.2 → 8.4b-2). 바꾼 기록이 이렇다 — *"UI 무의존이지 백엔드 무의존이 아님"*.
웨이퍼 라이브러리가 **흐름 전체를 가져야 쓰는 쪽(CLI·화면·제품)이 여럿이어도 같은 걸 돌린다**는 것이다.

우리가 지금 딱 그 자리에 왔다. 쓰는 쪽이 명령행 하나일 땐 4주차 판단이 맞았고, 화면이 들어오면서
교수님이 부딪힌 지점에 똑같이 닿았다. 그래서 `Wafer → Cv` 참조를 더했다.

| | 4주차 | 5주차 |
|---|---|---|
| 웨이퍼 층 참조 | Core | Core + **Cv** |
| 지키는 경계 | OpenCV 를 모른다 | **화면을 모른다** |
| `WaferRunner` | 검사 함수를 받는다 | **그대로** — 사진 없이 테스트된다 |
| 흐름 | 명령행 안 | `WaferInspection` — CLI·화면이 같이 부른다 |

> 처음엔 반대로(`Cv → Wafer`) 두자고 했었다. **아래층(사진)이 위층(웨이퍼 흐름)을 아는 거꾸로 된 방향**이라
> 교수님 방향이 맞다. 위가 아래를 쓰는 쪽이 자연스럽다.

### ★ 옮긴 뒤 같은지 — 재서 확인했다

옮기기 **전에** 결과를 떠 두고, 옮긴 **뒤**에 같은 옵션으로 다시 돌려 대조했다.

```
합성 웨이퍼 그림     반듯 · 0.7° 기울임 · 표식 틀     sha256 지문 3개 전부 같음
wafer 명령 8가지     출력 · 오류 문장 · 끝값          전부 같음 (실행마다 다른 '시간' 줄만 뺐다)
  a 표식 정렬  b 원점 직접  c 0.7° → 멈춤(5)  d 샘플링  e E0 레시피  f 기대위치 틀림 → 거부(5)  g 정렬 없음  h nearest
```

> 옮긴 뒤 시간이 절반쯤 나왔지만(52 → 28 ms) **옮긴 덕이 아니다.** 첫 실행은 디스크·JIT 가 데워지기 전이라
> 늘 느리다. 그래서 비교에서 뺐다 — 4주차에 *"시간을 적을 때는 무엇을 어떻게 쟀는지 같이 적는다"* 고 한 그것이다.

테스트도 붙였다 — `SyntheticWaferTests` 9개(★ *결함 없는 die 끼리는 픽셀이 똑같다* — die-to-die 의 전제)와
`WaferInspectionTests` 6개(★ *정렬을 못 믿으면 결과가 아예 없다* — "0개" 로 안 보이게). 430 → 445.

## 11. WPF + 파이프라인 보수 — 실데이터 E0 존을 검사하려고

### 계기

**목표는 실데이터의 E0 존을 검사하는 것이다.** E0 는 웨이퍼 **원판 가장자리**에 걸친 die 다.
지금까지 쓴 실데이터는 웨이퍼 **안쪽을 부분 촬영**한 것이라 die 가 전부 E1 이었고,
E0 는 합성 데이터로만 돌려 봤다. E0 존이 실제로 있는 원본을 검사하려면 두 단계가 필요했다.

```
① 화면에서 실데이터가 제대로 돈다      ← 웨이퍼 탭에 실데이터를 올려 보니 고장 넷이 드러났다   §11.1 ✅
② 원형 웨이퍼의 가장자리를 다룬다       ← E0 존이 있는 원본을 받아 보니 지금 형식으로는 안 된다  §11.2 ⬜
```

이번 주의 남은 작업을 **WPF + 파이프라인 보수**로 부른다. 새 기능보다 **이미 있는 것이 실데이터에서 틀리게 도는 자리**를 메우는 일이 대부분이었다.

---

### 11.1 보수 — 화면에서 실데이터를 돌리며 드러난 것 ✅

넷 다 **프로그램이 죽지 않고 그럴듯하게 틀린** 고장이다. 화면이 없을 때는 명령행 옵션을 사람이 맞춰 넣었기 때문에 안 드러났다.

| | 증상 | 진짜 원인 | 고친 것 |
|---|---|---|---|
| 1 | 실데이터 결함 **0개** | 웨이퍼 탭은 die 탭의 **지금 그래프**를 레시피로 쓴다. 앱을 켠 직후 그 그래프는 **미리보기용 시드**(Median)라, 같은 행 좌우(최대 2장)로는 골든 3장을 못 채워 **전 die 가 검사 실패** | [결과] 칸 맨 위에 **실제로 쓴 레시피 이름**(`recipeId` + 설명) — 시드면 *"미리보기용 시드 · 실데이터 값 아님"* 이 뜬다 |
| 2 | 실데이터에서 결과가 **그럴듯하게** 나옴 | 이미지를 열어도 격자 칸은 **합성용 값 그대로**라 사진 귀퉁이만 검사 | **격자 경고** — 격자 밖 어느 한쪽에 die 가 **한 칸 이상 더 들어갈 자리**가 남으면 결과보다 먼저 알린다 |
| 3 | 합성 웨이퍼에 3개 심었는데 **4개** | 미러 — 아래 | `GoldenContract` 가 **부호를 한 번만** 본다 |
| 4 | 주석이 **없는 파일**을 가리킴 | 레시피의 `recipeId` 를 파일 이름처럼 적었다 | `SampleGraph` 주석 수정 |

#### ★ 3 — `Median` 도 넘어간다

```
심은 것   c0r2 · c2r2 · c1r5
찾은 것   c0r2 면적 900 · c1r2 면적 728 · c2r2 면적 900 · c1r5 면적 900
                         ↑ 하나만 900 이 아니다
```

**728 = 이웃 두 결함이 die 안에서 겹친 넓이**(26 × 28)다. `c1r2` 는 심은 둘 사이에 끼인 칸이고,
"가까운 순 3장" 이면 골든이 `c0r2` · `c2r2` · `c1r1` 이다.

```
겹친 자리에서   골든 3장 = { 어두움, 어두움, 정상 }  →  Median = 어두움
               검사 die = 정상  →  |정상 − 어두움| 이 큼  →  Absolute 는 이걸 결함이라 부른다
```

**`Median` 이 막는 것은 "셋 중 하나" 가 결함일 때까지다.** 둘이 겹치면 중앙값이 넘어간다.
`DarkOnly` 로 바꾸면 미러는 *"검사 die 가 더 밝음"* 이라 버려져 정확히 3개가 나온다.
피치를 25배로 키운 같은 그림에서도 같은 일이 났다 — 가짜의 면적이 또 **겹친 넓이**와 정확히 같았다.

**구멍은 `GoldenContract` 에 있었다.** 4주차엔 부호를 `Mean` 갈래 **안에서만** 봤다. 그래서 `Median` + `Absolute` 는
*"3장이면 됩니다"* 하고 경고가 없었다. 게다가 `Mean` 경고는 *"DarkOnly 를 쓰거나 **Median 으로 합치세요**"* 라고 **틀린 조언**을 하고 있었다.

```
전   부호 판정이 Mean 갈래 안에만        →  Median·Percentile·Min·Max 는 무방비
후   부호 판정을 맨 앞에서 한 번          →  Absolute(또는 안 적음)면 합치는 법과 무관하게 경고
     조언은 "장수가 아니라 부호가 막는다 — 결함이 어두우면 DarkOnly"
```

3주차의 **★ 파라미터는 짝이다** 가 이 모양으로 다시 드러났다. 이웃 수 · 합치는 법은 맞췄는데 **부호** 하나를 안 맞춘 것이다.

> **시드는 `Absolute` 그대로 둔다.** 교수님 시드도 `Absolute` 다. 교수님 미리보기 그림에는 결함이
> **밝은 것 셋 + 어두운 것 하나**가 섞여 있어, 극성을 모르는 시연에는 양쪽을 다 잡는 `Absolute` 가 맞다.
> 우리 die 탭 미리보기 결함도 **밝다** — `DarkOnly` 로 바꾸면 die 탭이 0개가 된다.
> **문제는 시드가 아니라 die 시연용 레시피로 웨이퍼를 검사한 것**이고(용도가 다른 값을 섞음), 그건 1·3 이 이제 화면에 드러낸다.

#### 2 — 격자 경고의 기준

처음엔 *"격자가 사진 넓이의 절반도 못 덮으면"* 을 생각했다. 그런데 합성 웨이퍼는 테두리에 여백(피치의 절반쯤)이 있어
**격자가 맞는데도** 비율이 낮게 나온다. 그래서 기준을 바꿨다.

> **격자 밖 어느 한쪽에 die 가 한 칸 이상 더 들어갈 자리가 남으면 경고**

| 경우 | 경고 |
|---|---|
| 격자가 맞음 · 합성 웨이퍼의 여백 | 없음 (한쪽 여백 < 한 칸) |
| 합성용 격자를 실데이터에 그대로 | **오른쪽에 n열 · 아래에 n행** |
| 행을 하나만 덜 넣음 | **아래에 1행** |

**검사는 멈추지 않는다** — 일부러 일부만 볼 때도 있다. 판정은 **웨이퍼 층 한 곳**(`WaferInspection`)에서 하고
명령행과 화면은 같은 문장을 띄운다. 화면에만 넣으면 명령행에는 같은 실수를 막는 장치가 없게 된다.

### 11.2 원형 웨이퍼 E0 존 — 로드맵 ⬜

#### 받은 원본에서 본 것

웨이퍼 **전체를 찍은 원형 원본**이다. 사진에서 숫자로만 쟀다(그림은 열어 보지 않았다).
지금 형식(**사각형 격자** + `EdgeRings` = 사각형 테두리 몇 겹)으로 검사하면 세 군데에서 어긋난다.

```
 ┌──┬──┬──┬──┬──┐
 │░░│▓▓│▓▓│▓▓│░░│   ░░ 원판 밖 — die 가 아니다
 ├──┼──┼──┼──┼──┤   ▓▓ 원판에 걸침 — E0
 │▓▓│  │  │  │▓▓│      원판 안 온전 — E1
 ├──┼──┼──┼──┼──┤
 │░░│▓▓│▓▓│▓▓│░░│
 └──┴──┴──┴──┴──┘
```

1. **귀퉁이 칸은 원판 밖**인데 die 로 검사한다. 원판 밖에는 웨이퍼가 아닌 물체도 찍혀 있었다
2. **가장자리는 계단 모양**인데 `EdgeRings` 는 사각형 바깥 줄만 E0 로 만든다
3. ★ **원판 밖 배경은 E0 레시피의 임계(0.15)보다 어둡다.** 걸친 칸을 E0 레시피에 넣으면 원판 밖 부분이 **통째로 결함**이 된다

#### 교수님 문서로 정해지는 것

| | 교수님 방향 | 근거 |
|---|---|---|
| ① E0 의 뜻 | **원판 밖과 겹치는 die**. 이미지 테두리 ≠ 웨이퍼 가장자리 | 새_원본_레시피_만들기 |
| ② E0 를 어떻게 | **빼지 않고** 골든 없이 단일 임계로 검사. 결과는 E1 과 따로 | 레시피_해설 · 결과 계약 |
| ③ 원으로 칸 나누기 | 다음에 할 일로 정해 둠 — *"원 기반 존 자동판정(엣지 die 의 원형 경계)"*. 원 정보는 노치·스테이지 좌표와 함께 **장비가 주는 값** | Phase 5 |
| ④ 검사 영역 줄이기 | **러너가 아니라 레시피 블록** `MaskApply` 로 — *"검사영역 한정/제외용"* | Phase 4 · `IMaskApplier` |

②가 처음 생각과 달랐다. 처음엔 *"걸친 칸은 검사에서 뺀다"* 로 정했다가, 교수님 방향을 따라 **검사한다**로 바꿨다.
④도 그렇다. *"러너가 원판 밖 픽셀을 채워서 넘긴다"* 를 먼저 생각했는데 교수님 방식이 아니라서 버렸다.
**검사 영역은 레시피가 정한다** — 그래야 레시피 파일만 보고 무엇을 검사했는지 알 수 있다.

#### 문서에 없는 것 둘 — 그리고 절충

교수님이 직접 적었다 — *"E0 존이 실제로 있는 원본이 오면 쓰는 견본으로 유지"*. **원형 원본으로 E0 를 돌려 본 적이 없다.**
그래서 `MaskApply` 와 E0 레시피를 **같이 써 본 적도 없다**(쓰는 샘플·시험이 하나도 없다).

**(1) die 마다 "원판 안" 마스크를 누가 만드나**

교수님 러너가 die 레시피에 넘기는 것은 `roi` · `chipRegions` 뿐이다.

→ 러너가 **예약 입력을 하나 더** 넘긴다 — `waferMask`(이 die 의 원판 안 = 255, 밖 = 0).
교수님이 정렬을 붙일 때 `alignSrc` · `alignTemplate` 을 예약 입력으로 **추가한 것과 같은 방식**이다.

**(2) `MaskApply` 는 가린 곳을 0(검정)으로 채운다**

그런데 E0 레시피는 **0 ~ 0.15 를 결함**으로 본다. 그대로 이으면 가린 곳이 결함이 된다.

```
roi → MaskApply(원판 밖 = 0) → Binarize(0~0.15 = 결함) → 원판 밖이 통째로 결함   ✗
```

→ `MaskApply` 에 **`fill`(가린 곳을 채울 값)** 매개변수를 더한다. **기본값 0 이면 교수님 동작과 똑같다.**
교수님이 이 블록에 `invert` 를 매개변수로 붙인 것과 같은 결이다.

```
roi → MaskApply(waferMask, fill 1.0) → Binarize(0~0.15) → Label         ← E0 레시피
      원판 밖 = 흰색이라 결함이 아니다 · 원판 안의 진짜 어두운 결함은 그대로
```

> **비유** — 시험지 채점에서 **문제가 없는 칸을 흰 종이로 덮고** 채점하는 것과 같다.
> 검정으로 덮으면 "빈칸 = 오답" 규칙에 걸려 전부 틀린 것으로 채점된다.

#### 순서

### 11.3 원형 실데이터로 돌려 본 것 ✅

> 원본과 묶이는 숫자(해상도·원의 크기와 자리·격자·피치·칸 수·파일 이름)는 적지 않는다.
> 길이는 **피치에 대한 비율**이나 **수 px** 로만 쓴다. 넣은 숫자는 명령줄에만 썼다.

#### 격자와 원을 어떻게 알아냈나

| | 방법 | 결과 |
|---|---|---|
| **격자 위상** | 부분 촬영 원본의 die 조각을 원판 원본에 맞대 봤다. die 무늬가 전부 같아서 **어느 die 에 맞든 위상(피치로 나눈 나머지)은 같다** | 조각 대부분이 **3~4px 안**에 모였다 |
| **원** | 원판 가장자리 점을 원본 해상도로 100개 남짓 모아 원을 맞췄다. 원판 밖 물체가 있는 아래쪽은 뺐다 | 맞춤 오차 중앙 **1px** · 최대 수 px |
| 가장자리 | 밝기가 바뀌는 폭을 쟀다 | **2px 안팎** — 칼같이 끊긴다. 가장자리 안쪽에 E0 임계보다 어두운 띠는 없었다 |

- 처음엔 부분 촬영 원본이 원판 원본을 **잘라 낸 것**인 줄 알았다. 맞대 보니 아니었다 — 같은 제품을 **따로 찍은** 사진이다.
  그래도 위상은 알 수 있었다. 앞서 원판 원본에서 찾아 둔 어두운 띠가 바로 그 위상 앞에서 끝나서, 둘이 서로 맞았다.
- 원의 첫 추정은 아래쪽의 원판 밖 물체에 끌려 **피치의 3% 쯤** 어긋나 있었다. 그쪽을 빼고 다시 맞추자 오차가 1px 로 줄었다.
- 원본에서 숫자를 뽑는 스크립트는 **레포 밖**에 두고 그림은 열어 보지 않았다. 중간에 만든 배열도 지웠다.

#### 결과

die **전부** 검사했고 **실패는 0**. 칸은 온전 · 걸침 · 원판 밖 셋으로 나뉘었고, 숫자로 미리 어림한 범위와 맞았다.
die 하나에 0.15초 남짓.

| 가장자리 여유 | 결과 |
|---|---|
| 0 (잰 원 그대로) | E0 에서만 결함 — **가장자리 실금** 여럿 + **노치** |
| **피치의 1% 미만** | 노치만 남는다 |
| **피치의 6%** | **0개** |

E1(온전한 칸) 쪽은 세 경우 모두 0개였다.

**가장자리 실금** — 원을 수 px 오차로 맞추니, 그 틈의 배경이 원 가장자리를 따라 **가는 호**로 남았다.
전부 원 가장자리에서 **수 px ~ 20px 안쪽**이다. 수학적인 원으로는 원판 경계를 픽셀까지 맞출 수 없어서 생긴다.

**노치** — 원판 아래쪽의 V 홈이다. 폭은 원 둘레의 **1.4% 쯤**, 가장 깊은 곳이 **피치의 5% 남짓**이다.
원으로 보면 '원판 안' 인데 실제로는 배경이라 E0 레시피가 결함으로 잡았다. 교수님도 노치·플랫은 *"장비 통합 시"* 로 미뤄 뒀다.

→ 둘 다 **가장자리 여유**로 가린다. 실제 장비도 원판 가장자리 일정 폭은 검사하지 않는다(edge exclusion).
반지름을 줄여 넣지 않고 따로 받는 까닭 — "원판이 어디인가(잰 원)" 와 "어디까지 안 보나(여유)" 가 한 숫자에 섞이지 않게.

> ⚠ **0개의 한계.** 이 원본에는 정답(심어 둔 결함)이 없다. 그래서 *"원판 안쪽 E0 의 진짜 결함을 잡는다"* 는 실데이터로
> 확인하지 못했다 — 합성 시험(`걸친_칸의_원판_안쪽_결함은_잡힌다`)이 맡는다.

#### 돌리다 발견한 것

| | 무엇 | |
|---|---|---|
| 1 | **잘린 die 의 절대 좌표가 밀렸다.** 격자를 원판 끝까지 덮으려고 사진 왼쪽·위 **밖**에서 시작하자, 잘린 첫 열의 결함이 원판 밖 **천 px 넘게** 찍혔다. die 안 좌표는 '잘라 읽은 자리' 기준인데 절대 좌표에는 '잘리기 전 자리' 를 더했다. 4주차에 *"기록만 해 둔 것 — 잘린 die 의 기준점"* 으로 미뤄 둔 바로 그것이다. 결함 개수는 맞았고 **좌표만** 틀렸다 | ✅ 고침 — 고치기 전 동작으로는 새 시험 둘이 실패한다 |
| 2 | **표식 정렬이 원본 전체를 한 번에 읽는다.** 원판 원본이면 작업 포맷으로 **수 GB** 라 `--mark` 를 쓸 수 없었다. 이번엔 위상을 숫자로 재 `--origin` 으로 넣었다 | ✅ 표식 근처만 읽게 고침 — §11.4 |
| 3 | **우리 이미지 읽기는 `.raw`(사이드카) 를 못 읽는다** — 교수님 쪽엔 있다. 같은 원판의 BMP 를 썼고, 두 파일의 같은 자리 밝기가 소수 넷째 자리까지 같은 것을 확인했다 | ⬜ |
| 4 | **노치를 원판 모양으로** 다루기 — 지금은 여유로 가릴 뿐이다 | ⬜ 교수님도 *"장비 통합 시"* |

### 11.4 정렬 창 — 표식 근처만 읽는다 ✅

**계기.** 원판 원본에서는 격자 원점을 손으로 재야 했다. 사진마다 바뀌는 값을 손으로 잴 수는 없다 —
원래 **정렬**이 할 일이다. 그런데 정렬이 표식을 찾으려고 원본 **전체**를 읽어서 쓸 수가 없었다.

**교수님 방향.** Phase5 #5.10 *"러너 정렬 윈도잉"* 에 그대로 있다 — 기대 위치 주변 창만 `ReadRegion` 으로 읽는다.
블록이 아니라 러너 조립(경계) 변경이고, 전체 검색은 남겨 둔다.

| | 무엇 |
|---|---|
| `MarkAlignment.SearchPadding` | 있으면 표식마다 **있을 법한 자리 ± 여유** 창만 읽는다. 없으면 전처럼 사진 전체 |
| 있을 법한 자리 | **대략 원점 + 설계 자리(`--expect`)**. 대략 원점 = `WaferSpec` 의 원점 = 교수님 `firstDieX/Y` |
| die(0,0) 의 실제 자리 | 풀린 변환으로 대략 원점을 옮긴 곳 — 교수님 `Origin = transform.Apply(firstDieOrigin)` 과 같다 |
| 격자 | 정렬했으면 대략 원점을 **또 더하지 않는다**. 전에는 이게 무서워 `--mark` 와 `--origin` 을 같이 못 쓰게 막았다 |
| 창 안에 표식이 없을 때 | 정렬을 거부하고, **창에서만 찾았다**는 걸 문장에 같이 적는다 |

교수님 문서의 앞 단계(축소본으로 자리 가설 세우기)는 안 넣었다 — 있을 법한 자리를 대략 원점으로 이미 받기 때문이다.
대략 원점이 0 이고 창을 안 주면 전과 **똑같이** 돈다(기존 시험 그대로 통과).

**실데이터(원판 원본).**

- 정렬이 읽은 것은 **창 두 개** — 원본의 **1% 미만**.
- 표식 점수 0.98 넘게 둘 다 찾았고, 각도는 warp 가드(0.05°)보다 작았다.
- 정렬이 찾은 원점은 손으로 잰 위상과 **수 px** 차이 — 조각을 맞대 잴 때의 흩어짐(3~4px)과 같은 크기다.
- 대략 원점을 **피치의 10% 남짓** 일부러 틀리게 줘도 **같은 답**이 나왔다.
- 검사 결과(결함 개수·존)는 손으로 잰 원점일 때와 같았다.

> ⚠ **한계 — die 번호.** 이 원본의 표식(십자)은 die 마다 반복된다. 정렬은 대략 원점의 오차를 **피치의 절반 안**에서만 고친다.
> 그보다 틀리면 옆 표식에 붙어 격자는 맞아 보이는데 **die 번호가 통째로 밀린다** — 창으로도 못 막는다.
> 교수님 문서(특징 탐색 §2.1)의 같은 한계다. 대응은 유일한 표식 · 스테이지 좌표 · 특징 앵커 — 전부 *"인라인 트리거"*.

### 11.5 미팅 때 여쭤볼 것

검사 기계는 원판·E0 존까지 돈다(§11.3). 남은 것은 **사진마다 바뀌는 값**을 어디서 받느냐다.

| 값 | 언제 바뀌나 | 지금 |
|---|---|---|
| 열×행 · 피치 · 레시피 · 원판 반지름 · 가장자리 여유 | 제품마다 한 번 | 명령줄에 넣는다 |
| 격자 원점 | 사진마다 | **정렬이 찾는다**(§11.4) — 단 대략 원점은 줘야 한다 |
| 원판 중심 | 사진마다 | **손으로 쟀다** |

**Q1. 원판 중심은 어디서 받나요?**

| | 방법 | 생각 |
|---|---|---|
| 가 | 장비(스테이지 좌표)가 준다 | 교수님이 *"장비 통합 시"* 로 미뤄 둔 쪽 |
| 나 | 제품 레시피에 **격자 기준 원판 중심의 상대 위치**를 고정으로 두고, 정렬 결과로 계산한다 | die 배치는 설계로 정해지니 고정일 것 같다. 정렬과 바로 맞물려 가장 단순하다. **단 같은 제품 원판 사진이 한 장뿐이라 고정인지 확인 못 했다** |
| 다 | 사진마다 가장자리를 찾아 원을 맞춘다(블록 또는 명령) | 이번에 숫자를 뽑은 방법. 원판 밖 물체에 끌리는 것을 걸러야 한다(§11.3) |

**Q2. 가장자리 여유(edge exclusion)는 어떻게 정하나요?**
사양으로 정해지는 값인가요? 이번엔 결함 없는 사진에서 **0개가 될 때까지** 올려 봤는데, 그렇게 고르면 가장자리의 진짜 결함까지 가릴 수 있다.
실금만 가리는 데는 피치의 1% 미만이면 됐고, 그보다 크게 필요했던 것은 **노치** 때문이었다.

**Q3. 노치·플랫은 어떻게 다룰까요?**
여유로 덮을지, 노치 자리·모양을 따로 받아 가릴지. 교수님 문서는 *"장비 통합 시"* — 지금 단계에서 할 일인지 여쭙는다.

**Q4. 대략 원점(die 번호)은 어디서 오나요?**
표식이 die 마다 반복되면 정렬은 피치의 절반 안에서만 고친다(§11.4 한계). 실제 장비에서 die 번호를 정하는 첫 자리는
스테이지 좌표인지, 웨이퍼에 하나뿐인 표식인지.
