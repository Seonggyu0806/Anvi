## 1. 왜 웨이퍼 층이 따로 필요한가

**die 한 장만으로는 검사가 성립하지 않는다.**
골든을 만들려면 이웃이 필요한데, **"누가 이웃인가"는 웨이퍼 격자만 아는 정보**다.

> **비유** — 주방(die 검사) 하나로는 식당이 안 굴러간다.
> **홀 매니저**가 "3번 테이블, 7번 테이블…" 하고 주문을 넣어줘야 한다.
> 웨이퍼 층이 그 매니저다.

### 그리고 3주차에 "못 잡는 것"이 정리됐다

die-to-die만으로는 **원리적으로** 못 잡는 것들이 있다. 검사기를 더 잘 만들어도 안 된다.

| 못 잡는 것 | 왜 | 웨이퍼 층이 어떻게 |
|---|---|---|
| **반복 결함** (마스크 결함) | 모든 die에 똑같이 있으면 **골든에도 들어간다** | 여러 die의 같은 자리를 모아 본다 |
| **웨이퍼 전체 무늬** | die 하나만 보면 "좀 어둡네" 정도라 임계를 못 넘는다 | 웨이퍼 전체 지도로 본다 |
| **가장자리 die** | 이웃이 모자라다 | **E0 존**으로 따로 취급 |
| **군집** | die마다 1개씩이면 다 통과하는데 **지도로 보면 한쪽에 몰려 있다** | 절대 좌표로 모아 본다 |
| **공정 드리프트** | 모든 die가 같이 변하면 서로 닮았으니 차이가 0 | 웨이퍼끼리 비교 |

> **비유** — 학생 한 명씩 채점하면 "이 학생은 통과" 가 나온다.
> 그런데 **반 전체가 같은 문제를 틀렸다면** 학생 문제가 아니라 가르친 쪽 문제다.
> 채점만으로는 안 보이고 **성적표를 모아 봐야** 보인다.

## 2. 웨이퍼 층이 하는 일

| 하는 일 | |
|---|---|
| **격자** | 원점 · 피치 · 행열 → die 하나하나의 위치 |
| **이웃 고르기** | 이 die의 골든은 누구로 만들까 |
| **잘라내기** | 큰 사진에서 die 하나만 뜯어내기 |
| **좌표 변환** | die 안의 좌표 → 웨이퍼 전체 좌표 |
| **가장자리** | 변두리 die는 이웃이 모자람 → 다른 방식으로 (E0 존) |
| **웨이퍼 맵** | 어느 die가 불량인지 한눈에 |

## 3. 설계에서 정한 것 — die 반복은 **엔진 밖**에 둔다

이게 이 층의 제일 중요한 결정이다.

```
엔진 안에 넣을 수 있는 것    ①→②→③→…   순서가 미리 정해진 것
엔진 안에 못 넣는 것          die N개 반복   N이 실행할 때 정해진다
```

JSON 레시피는 **노드를 몇 개 어떤 순서로** 놓을지를 적는 파일이다.
그런데 die 개수는 **웨이퍼를 열어 봐야 안다.** 미리 못 적는다.

> **비유** — 레시피에 "양파를 볶는다 → 고기를 넣는다" 는 적을 수 있다.
> 그런데 **"손님 수만큼 반복한다"** 는 레시피에 못 적는다. 손님 수는 그날 정해진다.
> 그건 **홀 매니저가** 한다.

그래서 이렇게 나눈다.

```
Wafer 층 (바깥)     die 목록을 만들고, 하나씩 돌린다
    │
    └─ 각 die 마다 ─→  Core 엔진 (안쪽)   레시피대로 ①→②→…→⑦
```

**Lesson16도 교수님 구현도 같은 결론이었다.** 우연이 아니라 문제의 성질이다.

## 4. ✅ 한 것 — 격자

### 만든 파일

```
DiePipeline.Wafer/
 ├ Domain/Wafer.cs          WaferZone · DieOrigin · SimilarityTransform
 │                          WaferAlignment · DieGrid · WaferDefect
 │                          WaferDefectList · DieResult
 ├ Config/WaferSpec.cs      웨이퍼 형상
 └ Execution/DieGridBuilder.cs   형상 + 정렬 → die 원점 격자
```

### 형상은 이렇게 적는다

```
Cols · Rows           몇 열 몇 행인가
PitchX · PitchY       칸 사이 간격
DieWidth · DieHeight  die 자체 크기 (피치보다 작다 = 사이에 스크라이브 레인)
OriginX · OriginY     첫 die가 시작하는 자리
EdgeRings             가장자리 몇 겹을 E0 존으로 볼까
```

**die 크기와 피치를 따로 두는 이유** — 칩과 칩 사이에는 잘라내기 위한 여백(스크라이브 레인)이 있다.
피치는 그 여백을 포함한 간격이고, die 크기는 실제 칩이다.

```
│←── 피치 ──→│
┌────────┐ ┆ ┌────────┐
│  die   │ ┆ │  die   │
└────────┘ ┆ └────────┘
           여백
```

그래서 **die 크기가 피치보다 크면 거부한다** — ROI가 서로 겹친다는 뜻이기 때문이다.

### E1 / E0 존 — 무엇을 가르는 것인가

| | |
|---|---|
| **E1** | 온전한 die. **이웃이 다 있다** → die-to-die 로 검사한다 |
| **E0** | 변두리 die. **이웃이 모자라다** → 골든을 못 만든다 |

#### ⚠ E0 는 "이미지 테두리" 가 아니다

여기가 제일 헷갈리는 자리다. **E0 는 웨이퍼 원판의 가장자리**를 말한다.

웨이퍼는 **둥근 원판**이고 die 는 네모로 찍힌다. 그러니 **가장자리에서는 die 가 원판 밖으로 삐져나간다.**
그런 die 는 절반이 잘려 있거나 아예 비어 있다. **그게 E0 다.**

> **비유** — 피자 한 판을 네모로 잘랐다고 하자.
> **가장자리 조각은 둥근 테두리가 걸쳐서 모양이 이상하다** — 이게 진짜 E0 다.
>
> 그런데 피자 **가운데를 네모로 사진 찍어 놓고** "사진 테두리에 있는 조각은 이상할 것이다" 라고 하면 **틀린다.**
> 사진 안은 **전부 멀쩡한 조각**이다.

**교수님도 여기서 한 번 틀렸다가 고쳤다.** 초기 버전이 이미지 테두리의 die 를 E0 로 오인했고,
지금 문서에는 이렇게 적혀 있다 — *"이미지 테두리 ≠ 웨이퍼 가장자리."*

```
이미지가 웨이퍼 전체를 담았나?
   ├ 예   →  격자 테두리가 곧 원판 가장자리다. E0 가 있다
   └ 아니오(안쪽만 부분 촬영)  →  전부 온전한 die. E0 는 없다
```

#### 그래서 지금 우리 데이터는 전부 E1 이다

우리가 쓰는 원본은 **웨이퍼 안쪽을 부분 촬영**한 것이다. 원판 가장자리가 안 들어 있다.
**격자 테두리에 있는 die 도 실제로는 멀쩡한 die** 이고, 그 이웃도 이미지 안에 다 있다.

**→ `EdgeRings` 를 0 으로 둔다. 안 적으면 기본값이 0 이라 그냥 두면 된다.**

교수님도 지금 같은 상태다(`edgeExclusionPx 0`).

#### `EdgeRings` 는 어떻게 세나

```
rings 0        rings 1        rings 2
11111          00000          00000
11111          01110          00000
11111          01110          00100
11111          01110          00000
11111          00000          00000
        1 = E1 (온전)   0 = E0 (변두리)
```

**왜 겹 수로 세나** — 교수님 구현은 "가장자리에서 몇 픽셀"(`edgeExclusionPx`) 로 적는데,
코드를 보면 `그 값 > 0` 인지만 보고 **테두리 한 겹**을 E0 로 만든다.
즉 픽셀 값이 아니라 **켜고 끄는 스위치**로 쓰이고 있고, 겹 수는 늘 1 이다.
**겹 수로 적으면 "몇 겹을 뺄까" 를 그대로 표현**할 수 있다.

| | 교수님 | 우리 |
|---|---|---|
| 전부 E1 | `edgeExclusionPx = 0` | `EdgeRings = 0` |
| 테두리 한 겹 | `edgeExclusionPx > 0` | `EdgeRings = 1` |
| 두 겹 이상 | 표현 못 함 | `EdgeRings = 2, 3…` |

`EdgeRings = 1` 은 교수님 식과 **글자 그대로 같은 계산**이 된다.

#### ⚠ 그래도 이건 근사다

겹 수로 세는 것은 **격자 모양이 원판을 대신할 수 있을 때만** 맞는다.
진짜로 하려면 **웨이퍼 중심과 반지름**을 알고 "이 die 가 원 밖으로 나가나" 를 재야 한다.

지금 안 만드는 이유는 **검증할 데이터가 없어서**다 — 우리 원본에는 원판 가장자리가 안 들어 있다.
교수님 문서도 *"웨이퍼 원·노치/플랫 기반 자동 판정은 후속"* 이라고 적어 두고 미뤄 놨다.

#### E0 die 는 어떻게 검사하나 — 골든 없이

이웃이 없으니 **비교할 대상이 없다.** 그래서 **절대 임계**로 잡는다.

```
E1   이웃과 비교해서 "얘가 더 어둡네"          →  die-to-die
E0   "이 정도로 새까만 건 정상일 리 없다"      →  단일 임계
```

교수님 E0 레시피가 그것이다.

```
Binarize(Range 0 ~ 0.15) → Label(minArea 200)
```

배경이 **0.33 아래로 안 내려가니** 0.15 로 자르면 배경과 절대 안 겹친다.
**한계도 분명하다** — 밝은 결함은 패턴과 구분이 안 돼서 못 잡는다. 그건 E1 소관이다.

### 웨이퍼가 삐뚤게 놓였을 때

웨이퍼는 장비에 **정확히 반듯하게** 놓이지 않는다. 조금 돌아가고 조금 밀린다.

그래서 격자를 **두 단계**로 만든다.

```
①  이상적인 자리    (원점 + 열×피치, 원점 + 행×피치)
        ↓
②  실제로 놓인 대로 변환   회전 + 확대/축소 + 이동
```

1도만 기울어도 300px 떨어진 끝에서는 **5px** 이 밀린다.
3주차에서 본 것처럼 **2~3px만 어긋나도 모든 경계에 띠가 남으니**, 이건 반드시 보정해야 한다.

### 거부하는 것

값이 이상하면 **격자를 만들지 않고 멈춘다.**

| 거부 | 왜 |
|---|---|
| 열·행이 0 이하 | 격자가 아니다 |
| 피치가 0 이하 | 모든 die가 같은 자리에 겹친다 |
| `EdgeRings` 음수 | 뜻이 없다 |
| die 크기 > 피치 | ROI가 서로 겹친다 |
| 확대율 0 | **모든 좌표가 원점으로 무너진다** |

마지막 것이 특히 중요하다. 확대율 0이면 오류가 안 나고 **모든 die가 (0,0)에 놓인다.**
3주차에 배운 "조용히 틀리는 실패" 바로 그 모양이라, 미리 막았다.

### 이름은 교수님 것을 따랐다

`WaferZone` · `DieOrigin` · `DieGrid` · `WaferAlignment` · `WaferDefect` · `DieResult` —
전부 교수님 레포와 같은 이름이다.

> **동기와 교차 참조할 수 있어야 하기 때문이다.**
> 3주차에 "서로 코드를 못 읽었다" 를 겪었으니, 이번엔 이름부터 맞춰 둔다.

한 가지만 더했다 — `WaferZone.Unknown = 0`.
**존을 안 정했는데 기본값이 "안쪽" 이 되어 버리는 것**을 막는다.

### 5-2 이웃 고르기 — 3주차 측정이 그대로 들어간다

3주차에서 **이웃 고르는 법이 합치는 법과 짝**이라는 것을 쟀다.

```
골든 1.5장 → 3장, 두 배로 늘렸다   →  오검 24 → 22   (2개 줄었다)
합치는 법만 Mean → Median 으로     →  오검 24 →  0
```

**듣는 손잡이는 "몇 장 쓰느냐"가 아니라 "어떻게 합치느냐"다.**
끝 열에서는 장수를 늘리는 쪽이 오히려 손해였다 (오검 8 → 14).

그리고 짝은 둘이 아니라 **셋**이다 — 이웃 · 합치기 · **차영상의 부호**.
교수님 짝은 `1칸` + `Mean` + `DarkOnly` 이고, 그대로 쓰면 오검 0이다.
미러를 막는 법이 둘이라 두 짝이 서로 다른 쪽을 골랐을 뿐이다.

```
중앙값으로 합친다   ← 우리 짝.     골든을 만들 때 앞에서 막는다
부호를 본다         ← 교수님 짝.   뺀 다음 뒤에서 막는다
```

**그래서 이웃 고르기를 따로 뽑아낸다.** 셋을 **같이** 정할 수 있어야 한다.

### 6-2 정렬 — 제일 어려운 자리

3주차에 "정합이 조용히 틀린다" 를 겪었으니, **여기도 가드가 필요할 것**으로 본다.

### ★ 러너는 이미지를 안 만진다

러너가 하는 일은 **자리 계산**뿐이다. 잘라낼 네모(`Roi`)를 만들어
**바깥에서 받은 검사 함수**에 넘기고, 돌아온 결함 목록을 모은다.

```csharp
WaferRunner.Run(grid, inspectE1, inspectE0, options)
                     └─ Func<Roi, IReadOnlyList<Roi>, DefectList>
```

> **비유** — 홀 매니저는 요리를 안 한다. "3번 테이블, 파스타" 만 주방에 넘긴다.
> 주방이 바뀌어도 홀 매니저는 그대로다.

덕분에 이 층은 **OpenCV 를 모른다.** 웨이퍼 층은 `Core` 만 참조한다.
그리고 **사진 한 장 없이** 웨이퍼 전체 흐름을 테스트할 수 있다 —
검사 함수 자리에 "무엇을 받았는지 적어 두는 가짜" 를 끼우면 된다.

> ⚠ **교수님은 여기서 다르다.** `VisionStack.Wafer` 는 `VisionStack.OpenCv` 를 참조한다 —
> *"UI 무의존이지 백엔드 무의존이 아니다."* die 레시피를 실제로 돌리려면 이미지 소스가 필요해서다.
> 우리는 **함수를 받는 쪽**을 골랐다. 층 규칙이 안 깨지고 테스트가 사진 없이 돌아가기 때문이다.
> 5-6 에서 명령행이 그 함수를 만들어 넣는다 — 실제로 돌릴 때는 결국 같은 일을 한다.

### ★ 골든 ROI 는 밀어 넣고, 검사 ROI 는 잘라 낸다

둘의 처리가 **반대**다. 이유가 있다.

| | 이미지 밖으로 나가면 | 왜 |
|---|---|---|
| **검사 ROI** | **잘라 낸다**(교집합) | 그 자리에 픽셀이 없다. 없는 걸 본 척하면 안 된다 |
| **골든 ROI** | **안으로 민다**(자리 이동) | 크기가 달라지면 `Combine` 이 통째로 거부한다 |

```
골든을 "자르면"   골든 200×200, 검사 180×200  →  Combine 거부  →  die 가 조용히 건너뛰어진다
골든을 "밀면"     둘 다 180×200               →  정상 검사
```

**조용히 건너뛰어지는 게 최악이다.** 결과는 "결함 0개" 로 보이는데 사실은 **안 본 것**이다.
교수님도 실데이터에서 이걸 겪고 고쳤다(`BoundaryClampTests`).

### 좌표는 세 단계다

```
① ROI 상대     die 레시피가 낸 그대로. 이 die 의 왼쪽 위가 (0,0)
② die 상대     ① + die ROI 원점
③ 웨이퍼 절대  ②를 정렬(원점·회전·확대)로 변환     ← AbsoluteTransform 한 곳에서만
```

> **비유** — 아파트 32동에서 "302호에서 사고" 라는 신고가 32건 들어왔다.
> 각 동은 자기 302호만 안다. **단지 지도에 점을 찍으려면 동 위치를 더해야 한다.**

**원본은 안 건드린다.** `WaferDefect.Defect` 에 ① 을 그대로 두고 `AbsX`/`AbsY` 를 **덧붙인다.**
`double?` 인 게 설계다 — 0 으로 두면 **"원점에 있는 결함"과 "아직 변환 안 됨"이 구분이 안 된다.**

`abs = dieOrigin + s·R(θ)·centroid` — `DieGridBuilder` 가 die 원점을 만들 때 쓴
`SimilarityTransform` 을 **그대로 재사용**한다. 원점과 오프셋에 같은 변환이 걸려야 짝이 맞는다.

### ★★ `warp read` 와 "회전 되돌리기" 는 짝이다 — 6-2 에서 **같이** 해야 한다

왜 결함 오프셋에까지 회전을 거는지가 처음엔 이상해 보인다. **die 를 펴서 읽기 때문이다.**

```
기가픽셀은 통째로 못 돌린다
    ↓  die 마다 네모를 넉넉히 읽고
warpAffine 으로 편다        ← die 를 반듯하게 세운다
    ↓
검사한다                    결함 중심이 die 자기 축(도면 축) 값으로 나온다
    ↓
R(θ) 로 되돌린다            ← 그래야 웨이퍼 어디였는지 나온다
```

> **비유** — 비뚤게 걸린 액자를 사진 찍고, 사진을 **반듯하게 펴서** 봤다.
> "그림 왼쪽 위에서 3cm" 는 알 수 있지만 **벽의 어디인지는 모른다.**
> 원래 기울기만큼 되돌려야 벽 좌표가 나온다.

**그런데 우리는 아직 `warp read` 가 없다.** ROI 를 축정렬로 그대로 잘라 온다.
그 상태에서 회전을 걸면 **사진에 이미 찍힌 기울기에 한 번 더 돌리는** 꼴이 되어 두 배로 돈다.

```
짝 A   warp read 로 편다   +  R(θ) 로 되돌린다      ← 교수님 계획. 6-2 의 목표
짝 B   축정렬로 자른다      +  아무것도 안 건다      ← 이것도 그 자체로는 맞다
```

**섞으면 조용히 틀린다.** 두 배로 돌거나, 안 돌거나. 증상은 "웨이퍼 맵의 점이 살짝 밀려 있다" 뿐이다.
3주차의 *"파라미터는 짝이다"* 와 같은 모양이고, 이번엔 **떼면 조용히 틀리는** 쪽이다.

그래서 `AbsoluteTransform` 에 **임시 가드**를 뒀다.

```csharp
public const double MaxRotationDegWithoutWarp = 0.05;   // 교수님 문서의 임계값
```

기울기가 이보다 크면 **거부한다.** `0.05°` 면 1024px die 기준 오차가 0.6px 안쪽이라 무해하다.

> 🔨 **6-2 에서 `warp read` 를 붙이는 날 이 가드를 같이 지운다.**
> 안 지우면 정상적인 회전 웨이퍼가 거부된다. 지금은 정렬 전이라 θ=0 이어서 안 걸린다.

### 기록만 해 둔 것 — 잘린 die 의 기준점

교수님 문서는 *"② die 상대 = ① + **die ROI 원점**"* 이라 쓰는데, 코드는 `dieOrigin`(격자가 계산한
설계 원점)을 쓴다. **평소엔 같은 값**이라 안 드러난다.

갈리는 건 ROI 가 **왼쪽·위로** 잘릴 때다. 설계 원점이 -5 인데 실제로 잘라 본 자리는 0 이면,
결함 중심은 **잘린 쪽 기준**으로 재졌는데 기준점은 안 잘린 값이라 5px 어긋난다.

> **비유** — 사진 왼쪽 5mm 가 잘려 인화됐다. 잘린 사진에서 "왼쪽에서 30mm" 를 쟀는데
> **안 잘린 자를 갖다 대면** 틀린다.

지금 우리 격자는 이미지 안에 들어가서 안 걸린다. **교수님 쪽에 맞춰 두고 기록만 해 둔다** —
실제로 걸리면 그때 여쭤볼 거리다.

### 명령행 `wafer` — 조각이 처음으로 한 줄로 이어졌다

```
형상 ─ DieGridBuilder ─▶ 격자 ─▶ WaferRunner ─ die 마다 ─▶ 자리 계산
                                      │                      │
                                      │                 ★ 여기서 처음으로
                                      │                   진짜 이미지를 읽는다
                                      ▼                      ▼
                                DefectCollector ─▶ AbsoluteTransform ─▶ 웨이퍼 좌표
```

러너를 "이미지를 안 만지게" 만들어 둔 덕에, 명령행은 **검사 함수만 끼워 넣으면** 끝났다.
테스트에서 가짜가 들어가던 바로 그 자리다.

| | |
|---|---|
| **레시피는 한 번만 컴파일** | 노드는 파라미터만 들고 결과는 칠판에 놓는다 — 상태가 없으니 N die 에 그대로 재사용된다 |
| **한 die = 한 번 정리** | 읽은 이미지는 읽은 쪽이 놓는다. `SetInput` 은 소유권을 안 가져가서 **같은 원본을 다음 die 에서 또 쓸 수 있다** |

끝값을 나눠 둔 것이 중요하다 — `0` 결함 없음 · `3` 결함 있음 · **`4` 검사가 터진 die 있음**.
마지막이 제일 위험한 상태다. 결함 0개로 보이지만 **안 본 것**이다.

### ★★ 짝 가드 — 3주차에 잰 것이 코드가 됐다

돌려 보다 사고가 났다. 합성 웨이퍼에 흠집 **3개**를 심었는데 **9개**가 나왔다.

```
r0    .  1  1  1        진짜는 c2 하나뿐인데 좌우에도 찍혔다
r2    2  2  2  .        ← 미러다
```

이유는 이렇다.

```
레시피(die.diff.median)   Combine(Median)   — 3장을 전제로 한다
명령행 기본값             same-row1         — 1~2장을 준다
                                            ▲ 짝이 어긋난다
2장이면 중앙값 = 평균  →  이웃의 결함이 골든에 섞여  →  내 die 에 되비친다
```

**짝을 정하는 자리가 떨어져 있었다** — 합치는 법은 레시피에, 이웃 고르는 법은 명령행에.
사람이 매번 맞춰 넣어야 하면 언젠가 틀린다. 그리고 **틀려도 안 터진다.**

그래서 `GoldenContract` 를 놓았다 — **레시피에서 필요한 장수를 읽어낸다.**

| `Combine` | 최소 골든 | 왜 |
|---|---|---|
| `Median` | **3장** | 2장이면 중앙값 = 평균이라 이웃 결함이 골든에 섞인다 |
| `Percentile`(Min/Max) | **2장** | 한 장으로는 최소·최대를 고를 수 없다 |
| `Mean` + `DarkOnly`/`BrightOnly` | 1장 | **부호가 막으므로** 장수를 안 따진다 |
| `Mean` + `Absolute` | 1장 + **경고** | 막는 게 없다 (아래) |

> ★ **사람이 적는 값이면 틀리게 적을 수 있다.** 레시피에서 유도하면 틀릴 수가 없고,
> 교수님 레시피 형식도 안 건드린다(그쪽엔 장수 필드가 없다).

**`Mean` + `Absolute` 만 경고로 둔다.** 3주차 측정에서 3장 Mean 은 미러 0이 나왔지만,
그건 **막아서가 아니라 평균에 묽어져서**다. 심는 세기를 올렸더니 드러났던 바로 그 함정이라,
**희석을 차단이라고 부르면** 언젠가 세기 센 결함에서 터진다.

이제 짝이 깨지면 조용히 틀린 답 대신 **시끄러운 실패**가 난다.

```
골든    최소 3장 — Median 은 3장부터 중앙값이 됩니다 — ...

  r0    ×  ×  ×  ×
⚠ 검사가 터진 die 12개
  die(c0,r0)  골든이 1장뿐입니다 — 이 레시피는 3장이 필요합니다
```

### 시험용 웨이퍼를 그리는 `demo` 명령

실데이터는 레포에 안 넣는다. 그런데 그러면 **돌려볼 게 없다.**
그래서 그림을 **코드로 그린다** — 데이터를 한 톨도 안 쓴다.

```
회색 종이 → die 무늬 한 장을 그린다 → 도장처럼 찍는다 → 몇 군데 까맣게 칠한다
```

세 가지가 핵심이다.

| | |
|---|---|
| **모든 die 가 똑같다** | die-to-die 는 "이웃이 나와 같다" 를 전제한다. 도장이 어긋나면 온 데가 결함이 된다 |
| **무늬를 오른쪽에 몰아 둔다** | 무늬 위에 심으면 **골든에도 같은 무늬가 있어서** 차이가 안 난다 |
| **심은 자리를 같이 찍는다** | 정답을 알아야 검사 결과가 맞는지 판단할 수 있다 |

> **비유** — 시력검사표를 만들면서 **정답표도 같이** 인쇄하는 것이다.

씨(seed)를 받고 **기본값을 고정**해 둔다. 씨가 같으면 그림도 같다 —
"어제와 다른데?" 가 프로그램 탓인지 그림 탓인지 구분할 수 있어야 한다.

### 샘플링 — 검사를 덜 하는 게 아니라 결과를 추린다

먼저 뜻부터 갈렸다. 우리 계획서에는 *"전수 검사 대신 일부만 볼 때 어느 **die** 를 볼까"* 라고 적혀
있었는데, 교수님 `WaferSampler` 는 **결함을 추린다.**

| | 무엇을 줄이나 | 왜 |
|---|---|---|
| 우리 계획서 | **die 를 줄인다** — 일부만 검사 | 검사 시간 |
| **교수님 구현** | **결함을 줄인다** — 다 검사하고 결과만 | 하류 부하 |

**교수님 쪽으로 맞췄다.** 이름(`WaferSampler`·`SamplingMode`)을 맞춰야 서로 읽을 수 있고,
5주차 화면이 당장 이걸 쓴다 — 결함 목록에 수천 개를 못 띄운다.
그리고 **die 샘플링은 나중에 쉽다.** 러너가 `DieGrid` 를 받으니 격자만 걸러서 넘기면 된다.

```
BigSize   면적 큰 순서로 N개      "제일 심한 것부터 보자"
Range     면적이 이 사이인 것만   "티끌도 얼룩도 빼자"
Random    무작위 N개              "골고루 표본을 보자"
```

> **비유** — 답안지 1,000장을 다 못 본다. **큰 순서**로 · **점수대**로 · **무작위**로 —
> 목적에 따라 고르는 법이 다르다.

#### ★★ 전부 "같은 입력이면 같은 출력" 이어야 한다

여기가 이 단계의 진짜 어려움이다. 교수님이 못 박아 두신 규칙이다 —
*"Sampling seed 누락 = 골든마스터 파탄."*

```
무작위인데 씨가 없으면
  → 같은 웨이퍼를 두 번 돌려도 다른 목록이 나온다
  → "어제와 다른데?" 가 프로그램 탓인지 주사위 탓인지 알 수 없다
  → 회귀 시험이 통째로 무너진다
```

**`BigSize` 도 마찬가지다.** 면적이 같은 결함이 둘이면 누가 먼저인지 정해야 한다.
안 정하면 "상위 5개" 가 실행마다 바뀐다. 그래서 **면적 → 행 → 열 → 번호**로 끝까지 줄을 세운다.

무작위는 **섞은 뒤 앞에서 자른다.** 하나씩 뽑으면 이미 뽑은 것이 또 나와 다시 뽑아야 하고,
몇 번 다시 뽑을지가 운에 달린다. 섞으면 **몇 개를 뽑든 계산량이 같다.**
그리고 고른 뒤 **원래 순서로 되돌린다** — 뽑힌 순서대로 내보내면 눈으로 비교할 수가 없다.

#### 덜어낸 개수는 반드시 말한다

```
샘플링  5개 중 2개만 남겼습니다 (3개는 화면에서 뺀 것이지 없는 게 아닙니다)
        ↑ 위 웨이퍼 맵은 샘플링 전 기준입니다
```

조용히 줄이면 *"결함이 이것뿐"* 으로 읽힌다. 이 프로젝트에서 제일 위험한 모양이다.

#### ★ 끝값은 샘플링 **전** 기준이다

처음엔 샘플링 후 개수로 판정했는데, `range` 로 전부 걸러내니 **끝값이 0(결함 없음)** 으로
나왔다. 실제로는 5개가 있는데도.

> **끝값은 사람이 아니라 스크립트가 읽는다.** `--sample-count 10` 으로 화면만 줄였는데
> 결함 5,000개짜리 웨이퍼가 "통과" 로 찍히면 안 된다.
> **화면은 줄여도 판정은 못 줄인다.**

#### 설정은 숫자 다섯 개 대신 묶어서 받는다

교수님은 `WaferSampler(mode, count, seed, minArea, maxArea)` 로 받는다.
우리는 기록해 둔 이유가 있어 다르게 했다 — `Roi` 를 묶은 그 이유다.

```
Sample(list, 2, 100, 1, 0, 500)      ← 순서를 바꿔 넣어도 컴파일이 된다
Sample(list, new SamplingOptions { Mode = ..., Count = ... })   ← 이름이 붙어 섞일 수 없다
```

#### 인자 오류 메시지도 같이 고쳤다

`--pitch 100--sample` 처럼 **띄어쓰기 하나가 빠진** 명령을 넣었더니 이렇게 나왔다.

```
전   The input string '100--sample' was not in a correct format.
후   --pitch 의 값이 숫자가 아닙니다: '100--sample' — 값과 다음 옵션 사이에 띄어쓰기가 빠진 것 같습니다
```

2주차의 *"이름표 'blured' 가 없습니다. 지금 있는 것: [roi, blurred, mask]"* 와 같은 결이다.
**틀렸다고만 말하지 말고 무엇이 어떻게 틀렸는지 말하게** 한다.

### 정렬 — 웨이퍼가 어떻게 놓였는지 역산한다

지금까지는 웨이퍼가 **반듯하게 놓였다고 가정**했다. 실제로는 매번 조금씩 다르게 놓인다.

```
1도만 기울어도 300px 떨어진 끝에서 5px 이 밀린다
2~3px 만 어긋나도 모든 경계에 띠가 남는다
```

> **비유** — 모눈종이에 대고 칸을 세는데 **종이가 살짝 돌아가 있다.**
> 왼쪽 위 몇 칸은 맞는데 오른쪽 아래로 갈수록 어긋난다.

#### 세 걸음으로 나눴다

```
표식 찾기      TemplateMatchers   조각을 사진 위에서 밀어 보며 제일 닮은 자리
자세 풀기      AlignmentSolver    찾은 점들로 각도·원점 역산 + 가드
명령행 연결    wafer --mark       못 믿으면 검사를 시작조차 안 한다
```

#### 표식은 **둘 이상 · 멀리 · 비대칭**

| | 왜 |
|---|---|
| **둘 이상** | 하나로는 얼마나 밀렸는지만 알고 **얼마나 돌았는지를 모른다** |
| **멀리** | 가까우면 재는 오차 1px 이 각도 오차로 크게 뻥튀기된다 |
| **비대칭·비반복** | die 무늬처럼 반복되면 엉뚱한 자리를 자신 있게 짚는다 |

> **비유** — 못 자국 **하나**로는 액자가 비뚤었는지 알 수 없다. 두 개, 그것도 **멀리** 있어야 한다.

#### ★ 실데이터에서 확인한 것 — 점수가 높다고 맞는 게 아니다

교수님이 실원본에서 잘라 둔 표식 조각 넷으로 재 봤다.

| 조각 크기 | 결과 | 점수 |
|---|---|---|
| 수백 px | 기대 자리와 차이 **(0,0)** | **1.0000** |
| 수백 px | 차이 **(0,0)** | **1.0000** |
| 백 px 대 | 차이 **(0,0)** | 0.9511 |
| **수십 px** | **차이 (81,0) — 틀린 자리** | **0.9822** ⚠ |

**작은 조각에서 제일 높은 점수가 틀린 자리였다.** 2주차의 그 실패가 실데이터에서 재현됐다 —
*"재는 도구가 엉뚱한 답을 자신 있게 낸다."*

> **비유** — 사진에서 **눈썹만 잘라** 들고 "이 사람 찾아줘" 하면 닮은 눈썹이 수십 개 나온다.
> **얼굴 전체**를 줘야 한 명으로 좁혀진다.

**문턱을 올려도 못 막는다** — 틀린 답이 0.98점이다. 막는 방법은 셋이다.

```
조각을 크게        저작 단계의 문제.  수백 px 이면 1.0000 이 나왔다
찾는 창을 좁게     기대 위치 둘레만 본다
표식 둘의 기하     ← 이게 AlignmentSolver 가 하는 일
```

#### ★★ 표식 2개로 무엇을 검사할 수 있나 — 자유도를 세어 보면 나온다

```
배율까지 푼다   자유도 4(이동2+회전1+배율1) · 식 4개  →  언제나 완벽히 맞는다.  못 걸러낸다
배율을 1로 묶는다 자유도 3               · 식 4개  →  식이 하나 남는다.      그게 고발장이다
```

> **비유** — 점 두 개를 지나는 직선은 **반드시** 있다. "선이 점들과 잘 맞나" 를 물어야 소용없다.

그래서 **기본은 배율을 안 푼다.** 카메라 배율이 고정이면 웨이퍼가 커질 리 없고,
표현할 수 없는 것을 표현하지 않으면 **측정 노이즈에 그만큼 덜 흔들린다.**
남는 식 하나가 이걸 잡아낸다 — **웨이퍼는 돌아가고 밀릴 뿐 찌그러지지 않는다.**
두 표식 사이 거리가 변했다면 표식을 엉뚱한 자리에서 찾았거나 짝을 잘못 지은 것이다.

가드 넷을 순서대로 본다.

| 가드 | 무엇을 잡나 |
|---|---|
| 평균 점수 | 표식을 아예 못 찾았다 |
| 각도 | 웨이퍼가 그만큼 돌아갈 리 없다 → 짝짓기 의심 |
| **거리(배율)** | **표식 2개일 때 듣는 가드.** 찌그러질 수 없다 |
| 어긋남(잔차) | 표식 3개 이상일 때 나머지가 고발한다 |

#### ★ 서브픽셀 — 반 칸이 각도 오차가 된다

`matchTemplate` 은 **한 칸 단위**로만 답한다. 자리를 쓰는 데는 충분한데,
**두 점으로 각도를 풀면 그 반 칸이 그대로 각도 오차**가 된다.

점수판에서 최고점과 **양옆 칸** 세 개를 지나는 포물선을 그려 꼭대기를 소수점으로 잡는다.

```
δ = ½ · (왼쪽 − 오른쪽) / (왼쪽 − 2·가운데 + 오른쪽)
```

> **비유** — 언덕에 1m 간격 말뚝을 박고 높이를 쟀다. 제일 높은 말뚝이 꼭대기는 아니다.
> **양옆 말뚝을 비교하면** 진짜 꼭대기가 어느 쪽으로 얼마나 치우쳤는지 나온다.

실측 — 같은 그림·같은 표식으로 코드만 바꿔 쟀다(정답 0.700°).

| | 표식 1 오차 | 표식 2 오차 | 각도 |
|---|---|---|---|
| 정수 칸만 | 0.17 px | 0.70 px | 0.785° — 0.085° 틀림 |
| **서브픽셀** | **0.06 px** | **0.28 px** | **0.722° — 0.022° 틀림** |

**각도 오차가 4배 줄었다.** 1만 px 급 웨이퍼로 환산하면 끝에서 15px 밀림 → 4px 밀림이다.

못 믿을 때는 **그냥 정수 칸을 쓴다** — 가장자리라 양옆이 없거나, 점수판이 평평하거나,
반 칸을 넘는 답이 나오면 보정하지 않는다. 2주차 정합 가드와 같은 태도다.

#### 못 믿으면 검사를 시작조차 안 한다

```
정렬    각도 -5.5140° · ...
        ✗ 각도 -5.514° 가 한계 2.000° 를 넘습니다 — 웨이퍼가 이만큼 돌아갈 리 없으니 짝짓기를 의심하세요
정렬을 믿을 수 없어 검사를 하지 않았습니다                                    끝값 5
```

정렬이 틀리면 **웨이퍼 전체가 밀린 자리를 검사**하고, 결과는 "오검 천 개" 로만 보인다.
원인을 못 찾는다 — **2주차 정합 사고의 웨이퍼판**이다.

`--mark` 과 `--origin` 은 **같이 못 쓴다.** 정렬이 die(0,0) 자리를 알아내는데
`--origin` 까지 주면 같은 이동이 두 번 들어간다.

#### 기대 위치의 규약 — die(0,0) 이 (0,0) 이다

표식의 기대 위치는 **사진 좌표가 아니다.** 사진 좌표는 웨이퍼가 어떻게 놓이느냐에 따라
매번 달라지니 설계값이 될 수 없다. **die(0,0) 을 (0,0) 으로 본 좌표**로 적는다.

이 규약 덕에 풀어낸 원점이 곧 **"die(0,0) 이 실제로 놓인 자리"** 가 된다 —
"이동량" 과 "die(0,0) 위치" 가 한 규약으로 일치한다.

#### 끝까지 관통

```
demo 가 그린 정답   각도 0.030°  ·  die(0,0) 자리 (71.0, 68.0)
정렬이 되찾은 값    각도 0.0199° ·  die(0,0) 자리 (71.0, 68.0)   ✅
그 격자로 검사      심은 결함 3개를 그대로 3개 검출
```
