## 1. 블록 편집기 공통화

**왜.** 웨이퍼 레시피도 die 레시피처럼 블록으로 짠다. die 탭의 편집기(팔레트 · 캔버스 · 속성 · 검증 · 열기/저장)를 웨이퍼 탭에 **복사하면**
한쪽만 고쳐지는 날이 온다. 교수님도 웨이퍼 에디터에서 die 에디터와 같은 캔버스 · 팔레트 · 속성폼 · 검증을 다시 쓴다.

**어떻게.** 판단과 화면을 **둘 다** 꺼냈다.

| 부품 | 맡는 것 |
|---|---|
| `GraphEditorViewModel` | 판단 전부 — 팔레트 · 블록 추가/잇기/복제/삭제 · 속성 · 검증 · 열기/저장 |
| `GraphEditorView` | 화면 — 판단에 붙기만 한다. 탭마다 다른 칸 하나(`SideContent`)만 비워 둔다(die 탭은 미리보기) |
| `GraphEditorSettings` | **탭마다 다른 것** — 노드 명부 · 팔레트 필터 · 컨텍스트 입력 · 시작 그래프 · 파일 종류 |

- 편집기는 무엇을 돌리는지 모른다. 그래프가 바뀌면 `GraphChanged` 를 알리고, die 탭이 그걸 받아 미리보기를 다시 돌린다
- 확대 · 이동은 화면만 아는 값이라, 편집기는 `FitRequested`(전체 보기 해 달라)만 알리고 화면이 한다

**확인.** 꺼내기 전과 뒤에 die 탭의 상태(블록 · 선 · 속성 칸 · 검증 문장 · 미리보기 결과)를 **전부 글자로 적어 비교**했다 — 같았다.
화면을 화면 밖에 띄워 그려진 컨트롤 수도 같았다.

## 2. 노드 캔버스 — Nodify

**왜.** 첫 편집기는 블록을 상자로 늘어놓고 "연결 추가" 콤보로 선을 이었다. 교수님 화면은 Nodify 캔버스에서 포트를 끌어 잇는다.

**어떻게.** 교수님과 같은 **Nodify 7.3.0**.

| Nodify 부품 | 우리 쪽 |
|---|---|
| `NodifyEditor` | 캔버스. 블록 목록(`Nodes`) · 선 목록(`Connections`) · 끌고 있는 선(`PendingConnection`)에 붙는다 |
| `Node` + `NodeInput` / `NodeOutput` | 블록 하나 + 왼쪽 입력 점 · 오른쪽 출력 점(`ConnectorViewModel`). 점의 화면 위치(`Anchor`)는 Nodify 가 써 준다 |
| `Connection` | 두 점 사이 곡선 |
| `PendingConnection` | 점에서 끌기 시작 → 다른 점에 놓기(`StartCommand` · `FinishCommand`) |

| 규칙 | 내용 |
|---|---|
| 잇기 | 어느 쪽에서 끌었든 **출력 → 입력** 으로 바로잡는다. 출력끼리 · 입력끼리 · 같은 블록 안 · 컨텍스트 블록으로 들어가는 선은 무시한다. "입력 점에는 선 하나" 는 `GraphOps` 가 지킨다(새 선이 옛 선을 갈아 끼운다) |
| 편집 이력 | `GraphHistory` — 구조가 바뀌기 **직전**의 그래프를 통째로 복사해 쌓는다(블록 · 선 추가 · 삭제 · 복제). 새 그래프를 열면 비운다. **속성 값 고치기는 기록하지 않는다** |
| 자동 배치 | `LayoutEngine.Layered` — 블록의 열 = 그 블록까지 **가장 긴 앞 경로**의 길이. 같은 열은 레시피 순서대로 위에서 아래. 왼쪽 열(x < 240)은 컨텍스트 블록 자리. 고리가 있어도 멈춘다. 열 간격 300 · 줄 간격 160 |
| 팔레트 | 명부에서 펼쳐 분류로 묶고(`ICollectionView`) 검색칸으로 거른다 |
| 색 | 블록 머리 = 분류 색(`CategoryToBrushConverter`) — 팔레트 묶음 머리와 같은 색. 검증 오류가 가리키는 블록은 빨간 테두리(검증 문장 앞머리 `node 'id'` 에서 찾는다) |
| 단축키 | Ctrl+Z / Ctrl+Y / Ctrl+D / Delete — **탭 안에서만** 듣는다. 창 전체에 걸면 다른 탭에서 눌러도 이 그래프가 바뀐다 |

- 지운 것: "연결 추가" 콤보, 격자로 늘어놓던 `GraphOps.AutoLayout`(→ `LayoutEngine`)
- 열 간격은 처음 260 이었다. 웨이퍼의 `InspectDies`(출력 셋 + 체크박스)가 옆 열에 닿아 B-1 에서 300 으로 늘렸다

**시험.** `GraphHistoryTests`(5) · `LayoutEngineTests`(5) — 화면 없이 그래프와 좌표만 본다.

## 3. 연결 해제 — 함정 둘

**정한 것.** 선을 **더블클릭** 또는 **Alt+클릭** 하면 끊는다. Nodify 기본은 Alt+클릭뿐이고, 더블클릭은 '선 나누기' 에 걸려 있다 — 우리는 선 나누기를 안 써서 풀었다.

처음엔 둘 다 안 됐다.

**함정 ① — 명령에 무엇이 넘어오나.** 선 자신의 `DisconnectCommand` 는 **누른 위치(Point)** 를 넘긴다(Nodify 설명서: *"Parameter is the location"*).
우리 명령은 선(`ConnectionViewModel`)을 받아야 해서 위치가 오면 조용히 무시했다.
→ 편집기의 `RemoveConnectionCommand` 에 걸었다. 이쪽은 **선의 DataContext** 를 넘긴다.
교수님 앱도 선 자신의 명령에 걸려 있어 같은 증상이 있을 수 있다.

**함정 ② — 언제 판정하나.** Nodify 의 끊기 손짓은 마우스를 **뗄 때** 판정한다(`ConnectionState.Disconnect.OnMouseUp`). 선 나누기는 **누를 때** 판정한다.
실제 더블클릭은 뗄 때 '두 번째 클릭' 으로 잡히지 않아, 손짓에 더블클릭을 걸어도 끝내 맞지 않았다. Alt+클릭은 뗄 때도 Alt 가 눌려 있어 맞았다.
→ 더블클릭은 Nodify 손짓에 맡기지 않고, 선을 **누를 때** 클릭 횟수를 직접 본다(`OnLineMouseDown`). 끊는 것은 Nodify 가 부르는 것과 같은 `Remove()` 라 되돌리기도 그대로다.

**배운 것.** 처음 화면 검사는 누를 때 · 뗄 때 둘 다 클릭 횟수 2 로 흉내 내서 통과했다 — 실제와 다른 조건이었다.
이제 검사는 실제 순서(누름 1 → 뗌 → 누름 2 → 뗌)로, 뗄 때 클릭 횟수 2 · 1 둘 다 본다.

## 4. 웨이퍼 레시피 편집기

**어떻게.** 탭 셋 — die 에디터 · **웨이퍼 에디터** · 웨이퍼(옵션으로 검사). 웨이퍼 에디터는 1절의 공용 편집기에 설정만 다르게 준다(`WaferEditorViewModel`).

| 설정 | 값 |
|---|---|
| 명부 | `WaferBackend` — Cv 블록 + 웨이퍼 블록 |
| 팔레트 | 웨이퍼 종류(표식 목록 · 자세 · 격자 · 웨이퍼 결함)를 주고받는 블록만 — die 탭과 반대 |
| 컨텍스트 입력 | `alignSrc`(웨이퍼 사진) · `alignTemplate`(표식 조각) |
| 시작 | 견본 `samples/wafer/demo.wafer.json` **파일로** 연다 — 안의 경로를 풀 폴더가 생긴다. 실행 폴더에서 위로 올라가며 `DiePipeline.slnx` 를 찾는다(시험과 같은 방법). 못 찾으면 빈 그래프 |

### 4.1 실행

```
합성 견본 그리기 / 사진 열기  →  ▶ 실행  →  요약 · 정렬 · 경고  +  웨이퍼 맵  +  결함 목록
```

- 레시피는 내보내기와 같은 길로 만든다(`ExportRecipe` — 검증 강제). 검증에 막히면 돌리지 않는다
- 실행기는 명령행 `--recipe` 와 **같은** `WaferRecipeRunner` 다. 화면 그래프는 아직 파일로 안 썼을 수 있어서 입구를 하나 더 냈다 —
  `RunIn(레시피, 폴더, …)`. `RunFile` 도 이제 이걸 거친다. 경로 규칙은 `PathIn(폴더, 경로)` 한 곳
- 백그라운드로 돌고 취소할 수 있다. 취소하면 결과를 버린다(반쯤 본 웨이퍼를 결과처럼 보이지 않게)
- 실패는 예외 이름이 아니라 문장으로 검증칸에 띄운다 — 예: "레시피 파일이 없습니다: …"
- 레시피를 고치면 "결과가 바뀌기 전 레시피의 것" 이라고 알린다. 웨이퍼 검사는 오래 걸릴 수 있어 저절로 다시 돌리지 않는다(die 탭 미리보기는 저절로 돈다)

**시험.** `편집기를_거친_견본은_파일과_같은_답` — 견본을 편집기 그래프로 바꿨다가 다시 레시피로 내보내 메모리에서 돌린 결과가, 파일로 돌린 결과와 정렬 · 결함 목록까지 같다.

### 4.2 웨이퍼 맵

교수님 웨이퍼 맵과 같은 모양 — die 하나가 칸 하나, 셀에 결함 수.

| 상태 | 색 | 언제 |
|---|---|---|
| E1 | 초록 | 유효 die, 결함 없음 |
| E0 | 청회 | 가장자리 die, 결함 없음 |
| 결함 | 빨강 | 결함이 있는 die(존과 상관없이) |
| 검사 실패 | 주황 · `!` | die 검사가 터졌다 — 결함 0개로 보이지만 안 본 것 |
| 원판 밖 | 옅은 회색 | die 가 아니다 |

- 칸 계산은 화면과 상관없어 웨이퍼 층에 뒀다(`WaferMap.Of`) — 시험이 칸 상태와 수를 지킨다(`WaferMapTests` 4)
- 칸의 결함 수는 **추리기 전**(`Found`) — 판정과 같은 것을 센다. 결함 목록은 추린 뒤(`Defects`). 그래서 Sampling 으로 1개만 남겨도 맵의 결함 칸은 그대로다
- **멈췄으면 맵을 안 그린다** — 빈 맵은 "깨끗한 웨이퍼" 로 읽힌다

### 4.3 저장 위치와 경로

레시피 안의 경로(die 레시피 · 표식 조각)는 **레시피 파일이 있는 폴더 기준**이다(6주차 §6.5). 그래서 편집기는 지금 그래프를 연 · 저장한 파일(`FilePath`)과 그 폴더(`Folder`)를 들고 있다.

**다른 폴더에 저장하면** 파일만 옮기고 경로를 그대로 두면 엉뚱한 곳을 가리킨다 — 화면에선 돌았는데 명령행으로는 안 도는 레시피가 된다.
→ `WaferRecipePaths.Rebase` 가 옛 폴더 기준 경로를 새 폴더 기준으로 고쳐 적는다.

| 규칙 | 내용 |
|---|---|
| 고치는 값 | `InspectDies` 의 `e1Recipe` · `e0Recipe` · `features[].template` 셋뿐 |
| 그대로 두는 것 | 절대 경로 · 빈 값 · 다른 블록 · 경로가 아닌 값 |
| 모양 | 슬래시(`/`)로 적는다 — 견본과 같고 윈도에서도 풀린다. 드라이브가 다르면 절대 경로 |
| 화면 쪽 | 저장한 뒤 화면 그래프도 고친 경로로 다시 연다(블록 위치는 그대로). 되돌리기 기록은 옛 폴더 기준이라 비운다 |

- 열기 · 저장은 대화상자와 실제 처리를 나눴다(`Open(path)` · `Save(path, recipe)`) — 화면 없이 검사할 수 있게
- 편집기는 경로를 모른다. 경로를 품은 레시피(웨이퍼)만 설정으로 `RebasePaths` 를 준다

**시험.** `WaferRecipePathsTests`(4) — 옮겨 적은 경로를 새 폴더에서 풀면 옛 경로를 옛 폴더에서 푼 것과 같은 파일이다. `다른_폴더에_옮겨_저장한_견본도_그대로_돈다` — 옮겨 저장한 견본을 명령행 입구로 돌려도 심은 결함을 다 찾는다.

### 4.4 화면 배치

- 실행 패널은 넓어야 해서(맵 + 결함 목록) 편집기 오른쪽 칸이 아니라 **편집기 아래**에 둔다(높이를 끌어 바꾼다)
- 오른쪽 아래 칸(`SideContent`)은 높이를 끼우는 쪽이 정한다 — die 탭 미리보기는 250, 웨이퍼 에디터는 안 끼운다
- 창 크기 1360 × 860

## 5. 복합 파라미터 편집

**왜.** 속성 칸은 블록 설명(서술자)에 적힌 **낱개 값**(숫자 · 글자 · 체크 · 고르기)만 그린다. 아래 넷은 목록 · 묶음이라 서술자로 못 적어서 화면에 아예 안 나왔다 — 레시피 파일을 손으로 고쳐야 했다.

| 블록 | 값 | 모양(`ListLayout`) | 칸 |
|---|---|---|---|
| `SolveAlignment` | `expected` 표식 설계 위치 | `[[x,y], …]` — Tuples | x · y |
| `InspectDies` | `features` 표식 템플릿 | `[{ "template" }]` — Objects, 순서 바꾸기 | 경로 |
| `InspectDies` | `circle` 원판 | `{ centerX, centerY, radius }` 또는 없음 — Single | 숫자 셋 + '씀' |
| `InspectDies` | `zones` 수동 존 지정 | `[{ col, row, zone }]` — Objects | 정수 둘 + E1 · E0 · off |

### 5.1 정한 것

| | 정한 것 | 다른 길 | 까닭 |
|---|---|---|---|
| 방식 | **전용 편집 칸**(교수님 방식) — 단 부품 하나(`ListParamViewModel`)를 넷이 같이 쓰고, 어느 값에 어떤 칸인지는 표 하나(`ListParams`) | 서술자에 목록 · 묶음 모양을 적고 편집기가 알아서 그린다 | 목록 값이 넷뿐이라 서술자 · 검증기 · 속성폼 모델까지 키울 값어치가 없다. 새 값은 표에 한 줄 |
| 값 검사 | 블록 팩토리(`ICustomParamsValidator`)가 그대로 한다 — 고치는 즉시 검증칸 | 편집 칸이 따로 검사 | 규칙이 두 곳이면 어긋난다 |
| 되돌리기 | 기록하지 않는다(낱개 값과 같다) | 행 추가 · 삭제만 기록 | 낱개 값과 규칙이 달라지면 헷갈린다 |
| 입구 블록 | 누르면 안내 한 줄. `alignTemplate` 은 `InspectDies` 의 표식 템플릿 칸을 **같은 칸**으로 보여 준다 | 아무것도 안 보인다 | 어느 쪽에서 고쳐도 한 값이 바뀐다 |

### 5.2 글자 ↔ 값

`ListParams` 가 행(칸 글자들)과 JSON 값을 오간다. 화면과 상관없어 편집기 층에 두고 시험한다(`ListParamsTests`).

- **읽기** — 모양이 어긋난 행도 읽을 수 있는 칸만 채워 보여 준다. 버리면 사람이 고칠 기회도 없다. 고르는 칸은 고를 수 있는 글자로 맞춘다(`e1` → `E1`)
- **쓰기** — 숫자 칸을 하나라도 못 읽으면 **안 쓴다**. 치는 중인 빈 칸 · 잘못 친 글자를 0 으로 쓰지 않는다(낱개 값 칸과 같은 규칙)
- **묶음 하나**(원판)는 행이 없으면 레시피에서 **뺀다**
- 아는 칸만 쓴다 — 우리 레시피 형식에는 다른 칸이 없다
- ★ 시험 `쓴_값은_블록_검사를_통과한다` — 편집 칸이 쓰는 모양과 블록 팩토리가 받는 모양이 같은지 본다. 한쪽만 바뀌면 고칠 때마다 빨간 줄이 뜬다

### 5.3 경로 칸

- 서술자에 `IsPath` 를 더했다 → 속성 칸 종류 `FieldControl.Path`(입력칸 + 찾아보기). `e1Recipe` · `e0Recipe` 에 붙였다. 검증은 글자 그대로
- 찾아보기로 고른 파일은 **레시피 폴더 기준 상대 경로**로 적는다(`EditorPaths.Relative`). 저장 안 한 레시피 · 다른 드라이브는 절대 경로
- 속성 칸은 편집기에 두 가지만 묻는다 — 기준 폴더 · 파일 고르기(`FieldServices`). 파일 고르기는 대화상자라, 화면 없이 검사할 때 바꿔 끼운다(`PickFile`)

### 5.4 탭을 처음 열 때 화면 맞추기

**증상.** 웨이퍼 에디터 탭을 처음 열면 캔버스가 가장 작게(0.1배) 줄어 있거나 맞춰지지 않았다. '전체 보기' 를 누르면 제대로 됐다(B-1 부터).

**원인 둘.**
- 탭이 아직 안 보여 캔버스 크기가 0 일 때 맞추기가 먼저 돌았다 — 화면 크기 0 ÷ 그래프 크기 = 0 → 최소 배율
- 탭이 보이는 순간 Nodify 가 잠깐 확대를 막아 둔다(`DisableZooming = true`). 그때의 맞추기는 Nodify 가 무시한다(`ZoomAtPosition` 이 확대 금지면 아무것도 안 한다)

**고침.** '맞춰야 함' 만 적어 두고, **보이고 · 크기가 있고 · 확대 금지가 풀렸을 때** 한 번 맞춘다. 크기 변화 · 보임 변화 · 확대 금지 변화를 받을 때마다 다시 본다.
이제 탭을 열면 0.4초 안에 '전체 보기' 와 같은 배율로 맞춰진다.

## 6. 작업공간 · 오버레이 — C-1 · C-2

**왜.** 교수님 앱은 탭 대신 맨 위 바에서 작업공간을 고른다. 그리고 결과를 표 · 썸네일로만 보면 결함이 그림의 어디인지 바로 안 보인다.

**어떻게.** 바의 묶음과 칸은 교수님 앱과 같다.

| 작업공간 | 하는 일 |
|---|---|
| 다이 · 블록 에디터 | die 레시피 편집 + 미리보기 |
| 다이 · 오버레이 | 미리보기 결과를 크게 — 배경(검사 조각 · 단계 그림) + 결함 네모 + 결함 목록 |
| 웨이퍼 · 블록 에디터 | 웨이퍼 레시피 편집 + 실행 |
| 웨이퍼 · 오버레이 | 마지막 실행을 개요 그림 위에 — die 테두리 + 결함 네모 + 결함 목록 |
| 웨이퍼 · 옵션 검사 | 이전 '웨이퍼' 탭(레시피 파일 없이 입력칸으로) — 남길지는 따로 정한다 |
| 원본 · 이미지 뷰어 | 원본 확대 · 영역 지정 · 결함 자리 · 거리(7 ~ 10절) |

- 칸은 전부 떠 있고 **보이기만** 바꾼다 — 오갈 때 캔버스 확대 · 입력 값이 그대로 남는다
- 좌표는 전부 원본 픽셀이다. 그림을 원본 크기 판에 늘여 깔고 네모를 좌표 그대로 얹는다 — 배율은 화면(Viewbox)이 맞춘다
- 웨이퍼 die 테두리 색 = 웨이퍼 맵 칸 상태(샘플링 **전** 결함으로 셈). 결함 네모는 절대 좌표가 가운데, 개요 그림 기준 최소 8 px
- 목록에서 고르면 네모가 강조되고, 네모를 누르면 목록 줄이 골라진다. 미리보기 썸네일 더블클릭 → 그 단계 그림을 배경으로 오버레이

**함정 — 값을 고칠 때마다 오버레이 배경이 첫 그림으로 돌아갔다.** 미리보기를 다시 돌리면 배경 목록을 비웠다 채우는데,
비우는 순간 콤보가 고른 값을 null 로 되돌려 보낸다. 고른 배경의 **이름**을 따로 들고 있다가 다시 찾는다.

## 7. 원본 이미지 뷰어 — C-3

**왜.** 실데이터 원본은 통째로 화면에 못 올린다. 결함 · 영역을 원본 해상도로 보려면 보이는 곳만 읽어야 한다.

**어떻게.** 교수님 `LevelPolicy` · `ViewportPlanner` 의 값 그대로.

| | |
|---|---|
| 원본 그대로 올림 | 3,200만 px 이하 |
| 축소본 | 넘으면 긴 변 4,096 이하로 솎는다 — 축소 배율 = 긴 변 ÷ 4,096 올림 |
| 선명 조각 | 축소본 1 px 이 화면 1 px 보다 커지면 **보이는 영역만** 원본에서 읽어 덮는다 · 한 번에 600만 px 까지 · 확대 · 이동을 멈추고 0.15초 뒤 |

- 판(Board)은 원본 픽셀 크기이고 확대는 판 전체에 배율을 건다 — 판 위 좌표가 곧 원본 픽셀이라 영역 · 결함 · 거리 모두 좌표를 다시 계산하지 않는다
- 휠 = 커서 기준 확대 · 축소, 오른쪽 끌기 = 이동(블록 캔버스와 같은 조작)
- 계산(화면 ↔ 원본 · 맞춤 배율 · 보이는 영역 · 선명 조각)은 새 프로젝트 `Viewer`(교수님 `Viewer.Core` 자리) — 화면 없이 시험
- 합성 큰 그림으로 확인 — 축소 배율 3, 확대하면 선명 조각 = 보이는 영역

**함정 — 맞춤 상태에서 그림이 왼쪽에 붙어 보였다.** 그림을 가운데에 두자 이번에는 커서 기준 확대가 여백만큼 어긋났다.
스크롤 위치 ÷ 배율로 원본 좌표를 셈하면 가운데 여백을 모른다 → 화면 왼쪽 위가 판의 어디인지 **판에 직접 묻는다**(`TranslatePoint`).

## 8. 영역 지정 · 에디터 연계 — C-4

**왜.** die 미리보기는 합성 견본으로만 돌았다 — 실데이터 die 로 레시피 값을 맞춰 볼 길이 없었다. 웨이퍼 레시피의 표식 설계 자리는 숫자로만 적었다.

**어떻게.** 뷰어 위에 세 종류의 영역을 그린다(교수님과 같은 색).

| 영역 | 개수 | 색 | 쓰임 |
|---|---|---|---|
| 검사 ROI | 1 | 파랑 | 다이 미리보기의 `roi` |
| 정상 die | N | 초록 | 다이 미리보기의 `chipRegions`(골든을 만들 이웃) |
| 정렬 특징 | N | 보라 | 웨이퍼 레시피의 표식 설계 자리 · 표식 조각 |

- 첫 영역은 끈 크기, 그다음은 **같은 크기로 찍는다**(정상 die = ROI 크기) — die-to-die 는 같은 크기끼리 뺀다.
  가장자리에서는 잘라 내지 않고 그림 안으로 밀어 넣는다(교수님 규칙)
- 숫자 칸으로 다듬는다. 적용할 때 그림 밖 · 크기 다름을 막는다
- **다이 에디터에 적용** — 미리보기 입력이 합성 견본에서 원본의 ROI · 정상 die 로 바뀐다. '합성으로 되돌리기' 가 있다.
  원판 마스크를 받는 레시피는 막는다(원판 위치를 모른다). 뷰어가 다른 원본을 열면 합성으로 되돌린다
- **웨이퍼 에디터에 적용** — 설계 자리 = 특징 왼쪽 위 − die(0,0) 원점 → `SolveAlignment` 의 `expected` · `firstDieX/Y`(교수님 규약)
- **원본에서 보기**(웨이퍼 오버레이 결함 줄 더블클릭) — 같은 사진이면 다시 열지 않는다(파일은 경로, 합성은 복사본).
  결함 전부 빨강 · 고른 것 노랑(최소 12 px) · 그 자리를 가운데에. 막 연 원본이면 100%, 보던 원본이면 100% 이상의 배율을 그대로 둔다
- 계산(끌기 · 도장 · 적용 전 점검 · 설계 자리 · 결함 표시 · 가운데 두기)은 `Viewer` 의 `RegionTool`

**실데이터 die 로 적용해 보니 결함이 너무 많이 잡혔다.** 원인은 레시피 — 다이 에디터의 기본 그래프는 합성 견본용 값(면적 하한 4 px 등)이다.
실데이터용 `die.diff.json` 으로 열자 정상으로 돌아왔다. 3주차에 반대 방향으로 데인 것과 같은 교훈이다 — **용도가 다른 값을 섞지 않는다.**
손으로 찍은 정상 die 의 몇 px 어긋남도 빼기 그림에 윤곽선을 남길 수 있어 자동 맞춤(스냅)을 제안했지만, 레시피만으로 풀려서 미뤘다(`deferred.md` §12 ②).

## 9. 파일로 남기기 — 레포 안은 거부 · C-5

**왜.** 그린 영역은 앱을 끄면 사라진다. 교수님 앱은 영역을 회귀 케이스 · 명령행 입력으로 쓰는 파일로 남긴다.

**어떻게.**

| 남기는 것 | 형식 |
|---|---|
| 영역 | `*.case.json` — 교수님 `InspectionCase` 그대로(`image` 는 케이스 파일 기준 상대 경로 · `roi` · `chipRegions`) |
| 골든 패치 | 정상 die 마다 8비트 png(`이름_0.png` …) — 내보내기만. 쓰는 길은 교수님도 다음 단계 |
| 표식 조각 | 첫 정렬 특징 png → `InspectDies.features`(하나로 바꾼다 — 실행기는 1장만 쓴다) + 설계 자리 · 원점 |

- 불러올 때 사진이 다르면 그 사진을 연다. 영역이 그림 밖이거나 크기가 다르면 **잘라 맞추지 않고 거부**한다 — 케이스와 사진 짝이 틀린 것이다
- 명령행 `run -r <레시피> --case <케이스>` — 사진 · ROI · 정상 die 를 케이스에서 읽는다. `-i` · `--pitch` 등과 같이 못 쓴다.
  합성 그림으로 화면 길과 같은 결과(결함 1개 · 면적 1296 px)를 확인했다
- 케이스 파일이 없거나 깨지면 사람 말로 — `케이스 파일이 없습니다: <경로>` · 어느 칸이 틀렸는지

**레포 안 저장 거부.** 원본에서 나온 것(영역 좌표 · 조각 · 골든 · 보고서)은 회사 자료다. 저장할 곳에서 위로 올라가며 `.git`(폴더, 또는 작업 트리의 파일)을 찾아,
있으면 **화면은 저장을 거부**하고 명령행은 경고한다. 판단은 `RepositoryGuard` 한 곳이다.

## 10. 계측 · 결함 보고서 — C-6

**왜.** 결함 크기 · die 간격을 실제 길이로 말하려면 px → µm 환산이 필요하다(교수님 #4.10 · #6.1b).

**어떻게.**
- **µm/px** — raw 옆 설명 파일의 `micronsPerPixel` 로 채우고, 사람이 고칠 수 있다. 1 은 미보정이라 µm 를 적지 않는다(0 이하 · 숫자 아님도 1).
  장비 정보라 어디에도 저장하지 않는다
- **'거리' 도구** — 첫 클릭 A · 둘째 클릭 B 로 확정 · 다음 클릭은 새 A(교수님과 같다). 픽셀 칸 번호로 잰다 — `거리 123.7 px · 61.8 µm (Δx 120 · Δy -30)`
- **결함 보고서**(다이 오버레이) — CSV · JSON, 교수님 `DefectReport` 칸 그대로(유형 이름 포함).
  원본 입력일 때만 뷰어의 µm/px · 원본 ROI 를 적고, 합성 견본은 미보정 · ROI 없음 — 합성 그림에 실제 µm 를 붙이면 지어낸 숫자가 된다
- 환산 · 보고서는 Core(`Calibration` · `DefectReport`) — 화면 없이 시험

## 11. 실시간 웨이퍼 실행 · die 미리보기 — D

**왜.** 동기 앱은 웨이퍼를 돌리는 동안 맵 칸이 die 마다 채워지고, 맵에서 die 를 골라 그 자리로 die 레시피를 다듬는다.
우리 웨이퍼 에디터는 끝날 때까지 빈 화면이었고, 결과 die 를 다이 에디터로 가져갈 길이 없었다.

**어떻게.**
- **진행 알림**(`WaferProgress`) — 격자가 놓이면 `WaferGridReady`, die 하나가 끝날 때마다 `WaferDieDone(die, n, N)`.
  `WaferRunner` → `WaferInspection` → `WaferRecipeRunner` 로 `IProgress<WaferProgress>` 를 그대로 넘긴다. 결과는 알림을 받든 안 받든 같다(시험)
- **화면** — `Progress<T>` 가 화면 스레드로 넘겨 준다. 실행 번호가 다른 늦은 알림은 버린다. 맵은 '대기' 칸으로 깔고 die 가 끝날 때마다 그 칸만 바꾼다.
  끝나면 결과로 다시 그린다 — 같은 칸이 나온다(시험: 실행 중 칸 = `WaferMap.Of`)
- **die → 다이 미리보기** — 맵 칸이나 결함 줄을 고르면 그 die 의 레시피 파일(E1 · E0)을 다이 에디터에 열고,
  **러너가 실제로 쓴 ROI · 골든 자리(`DieInspection.GoldenRois`) · 원판(`WaferInspectionResult.Circle`)** 으로 미리보기를 돌린다.
  손으로 그린 영역이 아니라서 같은 레시피면 웨이퍼 결과와 같은 결함이 나온다. E0 die 는 원판 마스크까지 같게 만든다(`PreviewInput.Circle`)
- **정합 견본 레시피** `die.diff.align` — `die.diff` + 정합(평행이동 · 소수점 픽셀) + 빼기 뒤 Median 3(동기 E1 과 같은 처방).
  뷰어에서 손으로 찍은 정상 die 는 몇 px 어긋나 무늬 윤곽이 결함으로 남는다. 합성 시험: 8,6 px 어긋남에서 `die.diff` 는 윤곽까지, `die.diff.align` 은 결함 하나만

## 12. 웨이퍼 맵 표시 · 없는 블록 레시피

**맵.** 실데이터 원판은 칸이 많아 고정 크기 칸이 잘렸고, '대기' 와 '원판 밖' 색이 거의 같았다.

| 상태 | 색 |
|---|---|
| E1 · E1 결함 | 연두 · 분홍(교수님 짝) |
| E0 · E0 결함 | 청회 · 주황(교수님 짝) — 변두리 결함은 가장자리 · 노치일 수 있어 따로 본다 |
| 대기 | 흰 바탕 + 회색 테두리 |
| 수동 제외 | 회색 빗금 + `×` — 사람이 뺀 die 가 '원판 밖' 으로 숨지 않게(`DieOrigin.Manual` → `WaferMapState.Excluded`) |
| 검사 실패 | 보라 + `!` |

- 칸 틈 4 px · 고른 칸 테두리는 칸 안쪽 · 맵 위 범례 한 줄
- 맵은 자리에 맞게 줄인다(`Viewbox`, 키우지는 않는다). 웨이퍼 작업공간은 위 그래프 : 아래 실행 칸 = 반반 — 창을 키우면 맵도 커진다

**없는 블록.** 동기 레시피(`WaferDefectCluster` 블록)를 열자 앱이 꺼졌다 — 블록을 그리다 "모르는 블록" 예외가 잡히지 않았다.
이제 그리기 **전에** 레시피의 블록 이름을 명부와 맞춰 보고, 없으면 열지 않고 까닭과 있는 블록 목록을 띄운다. 보던 그래프는 그대로다.

> 동기 레시피를 우리 형식으로 옮길 때 다른 점: 결함 묶기 블록 · `dieMap`(die 있는 칸 지도) · Align 입력 이름(`test` ↔ `src`) ·
> 결함 분류 규칙(밝음/어두움 ↔ 모양). 골든은 우리가 E1 die 만 쓰고 같은 행 방식은 좌우 1칸이라, 동기의 '좌우 2칸' 대신 가까운 E1 3장(`nearest`)으로 맞췄다.

## 13. 뷰어 화질 · 영역 찍기

**깨짐.** 큰 원본은 두 번 건너뛰며 줄였다 — 축소본을 만들 때(칸마다 한 픽셀) · 화면에 맞출 때(`NearestNeighbor`). 칸보다 가는 회로선이 끊겨 점선처럼 보였다.
- 화면 — 줄여 볼 때(배율 < 1) `HighQuality`, 키워 볼 때 `NearestNeighbor`(픽셀 칸 그대로)
- 축소본 — 솎아낸 것을 먼저 띄우고, 칸 안을 전부 평균 낸 축소본(`SmoothOverview`)을 뒤에서 만들어 바꿔 끼운다.
  띠(칸 높이만큼의 행)를 나눠 동시에 읽는다(메모리 매핑 읽기는 동시에 해도 된다) — 한 줄로는 20초 가까이, 나누면 1초 남짓.
  다른 사진을 열거나 닫으면 멈추고 끝나기를 기다린 뒤 원본을 놓는다(읽는 도중에 놓지 않게)

**영역이 더 잡힘.** 버그가 아니라 '같은 크기로 찍기' 규칙 — 크기가 정해진 뒤에는 끈 크기를 버리고 고정 크기로 찍는다(die-to-die 는 크기가 같아야 뺄 수 있다).
그런데 고무줄은 끈 크기를 그려, 놓는 순간 다른 상자가 생겼다. 이제 끄는 동안 **실제로 찍힐 상자**가 마우스를 따라오고(놓은 자리가 왼쪽 위), 상태 줄에 고정 크기와 기준을 적는다.

**raw 설명 파일.** 설명 파일(`*.raw.json`)만 다른 폴더로 옮기면 "형식을 모름" 이 나왔다. 이제 어디에 둬야 하는지 말한다.

## 14. 실데이터 점검 — 노치 · 존 · 정렬 마크 · 결함 심기

**노치.** 원판 아래 가운데 수동 제외 die 를 검사에 넣어 보니, 노치(방향 기준으로 가장자리를 판 V자 홈)와 원판 밖 배경이 결함으로 잡혔다.
원 판정은 원판을 완전한 원으로 보기 때문이다. die 미리보기로 노치를 확인하고 **수동 제외를 유지**했다. 홈만 가리는 마스크는 미뤘다(16절).

**E0 판정 — 원 기준 vs 이웃 기준.** 동기 질문: 안쪽 die 가 왜 E0 인가.
- 우리 · 교수님(`CircleZoneRule`) — die 네모가 원(가장자리 여유만큼 줄인 것)에 **조금이라도 걸치면 E0**. 귀퉁이 하나가 원 밖이어도 그 자리에는 무늬가 없어
  die-to-die 로 빼면 잘린 귀퉁이 전체가 결함이 된다 — 그래서 원판 마스크로 가리고 혼자 본다
- 동기(`dieMap`) — 상하좌우 이웃 중 하나라도 없으면 E0. 원판 대각선 쪽 die 는 이웃이 다 있어도 귀퉁이가 잘린다 — 두 규칙이 갈리는 칸이다

**정렬 마크 — 셋 비교.** 흐름은 같다: 마크 조각으로 찾기 → 설계 자리와 짝짓기(기대 자리 + 대략 원점에서 가장 가까운 것, 피치 절반 안) → 자세 계산 → 점수 · 회전 판정.

| | 동기 | 교수님 | 우리 |
|---|---|---|---|
| 마크 조각 | 자기 사진에서 등록 | 실데이터 사진에서 자른 것 | 원판은 교수님 조각을 빌려 씀 · 부분 촬영은 정렬 없음 → 교수님 방식 추가 |
| 마크 수 | 4(격자 네 끝) | 2(대각) | 2 |
| 찾는 범위 | 사진 전체 | 사진 전체 | 사진 전체 또는 설계 자리 ± 창 |
| 거부 | 점수 · 회전 | 점수 · 회전 | 점수 · 회전 · 배율 · 어긋남(마크 3개부터) |

- 마크 2개면 밀림 · 회전은 풀린다. 4개는 남는 짝으로 '제대로 찾았나' 를 재는 덤이다
- **부분 촬영 레시피에 교수님 방식 정렬을 넣었다**(레포 밖) — 정렬 없는 레시피와 die 자리 차이 1 px 이하 · 결함 같음.
  설계 자리 ± 창으로 찾게 해 시간을 줄였다. 실데이터 회귀 시험에 경우로 넣었다 — 정렬 코드가 바뀌어 깨지면 바로 걸린다
- **교수님 골든마스터와 맞춰 봄** — 같은 사진의 교수님 기준 결과(`inspect.roimono.baseline.json`, 교수님이 주입한 결함과 같다)와 결함을 하나씩 견줬다.
  전부 같은 die · 같은 자리(1 px 안) · 같은 면적, 오검 없음. 사진을 보지 않고 정답으로 확인한 실데이터 검출이다(원판 사진은 정답이 없어 이렇게 못 본다)

**결함 심기 — 폐기.** 원본의 사본에 어둡게 · 밝게 점을 찍어 검출을 재 봤다(원본은 읽기만 · 사본 · 정답 목록은 레포 밖 · 레포 코드 없이 일회성 도구).
- 지금 원판 레시피는 대부분 놓쳤다. 어두운 점은 회로 무늬 때문에 **조각으로 쪼개져** 조각이 면적 하한 아래로 버려지고,
  하한을 낮추면 정상 자리 오검이 크게 는다(골든 1~2장). 밝은 점은 `DarkOnly` 라 구조상 못 잡는다
- 하지 않기로 하고 폐기했다(검출 개선 실험도 함께). 남긴 것은 조각 밝기 계산 속도 고침뿐이다(16절)
- 범위를 키우지 말 것 — 처음에 레포 기능(심기 · 채점 명령)으로 만들었다가 시험 사진 한 장이 목적이라 버렸다

## 15. 화면 검사 방법

WPF 화면은 단위 시험에 안 들어간다. 대신 **레포 밖 검사 프로그램**으로 확인했다(레포에는 안 넣었다).

| 무엇 | 어떻게 |
|---|---|
| 뷰모델 조작 | 화면 없이 뷰모델 명령을 직접 부른다 — 끌어 잇기 · 끊기 · 되돌리기 · 실행 · 행 추가 · 찾아보기(파일 고르기를 바꿔 끼움) |
| 그려진 것 세기 | 창을 화면 밖(-20000, -20000)에 띄우고 시각 트리에서 블록 · 선 · 칸 · 버튼 수를 센다 |
| 바인딩 오류 | `PresentationTraceSources` 로 바인딩 경고를 모은다 — 매번 0개 |
| 그림 | `RenderTargetBitmap` 으로 창을 그림으로 떠서 눈으로 본다(합성 견본만) |
| 마우스 | 실제 순서로 흉내 낸다(3절 배운 것) |
| 더블클릭 | 위로 퍼지는 `MouseDown` 에 ClickCount 2 를 실어 올린다 — `MouseLeftButtonDown` 은 요소마다 따로 나는 이벤트라 위로 안 간다. 표(DataGrid) 같은 컨트롤은 스스로 `MouseDoubleClick` 을 낸다 |
| 파일 고르기 | 저장 · 열기 창을 바꿔 끼워 경로를 넣는다. 레포 안 거부는 임시 폴더의 가짜 저장소(`.git`)로 본다 |

- 고친 것은 **고치기 전 상태에서 증상이 재현되는지** 먼저 보고, 고친 뒤 없어지는지 본다 — 선 끊기 · 화면 맞추기 모두 그렇게 확인했다
- 창을 띄우는 검사는 단계마다 마지막에 한 번만 돌린다 — 계산은 단위 시험으로 먼저 본다
- 마지막은 사람이 실제 화면에서 확인한다
