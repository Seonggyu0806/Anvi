# 2주차 — 파이프라인 한 벌을 만들었다

`2026-09-04 ~ 09-11` · 레포 `DiePipeline` (v1, 지금은 `master` 에 남아 있다)

---

## 한 줄

**동기와 각자 파이프라인을 만들어 보기로 했고, 엔진·레시피·알고리즘 7종·꼬리 3종까지
처음부터 끝까지 돌아가는 한 벌을 만들었다.**

---

## 1. 먼저 정리한 것

웨이퍼에는 **같은 칩(die)이 도장 찍듯 수십~수백 개** 찍혀 있다. 그중 몇 개에 흠이 있다.

당연한 접근은 "결함이 어떻게 생겼는지 배우자" 인데, 이 분야에서는 안 된다.

| 문제 | |
|---|---|
| 데이터가 없다 | 반도체 라인은 **정상이 수십만 장, 불량이 수십 장** |
| 새 결함은 배울 수 없다 | 처음 보는 종류의 결함은 **정의상 학습 데이터에 없다** |

그래서 질문을 뒤집는다.

> ### 결함이 뭔지 배우지 않는다. **정상이 뭔지 만들어 두고 뺀다.**

**비유** — 같은 도장을 종이 10장에 찍었는데 한 장에만 얼룩이 있다.
10장을 겹쳐 보면 **도장 무늬는 모든 장에 있으니 진하게 남고, 얼룩은 한 장뿐이라 흐려진다.**
이렇게 만든 "얼룩 없는 표준 도장"을 의심스러운 한 장에서 빼면 — **얼룩만 남는다.**

이것이 **die-to-die 검사**다. 겹쳐서 만든 표준을 **골든(golden)** 이라 부른다.

## 2. 구조 — 3층

```
┌──────────────────────────────────────────────┐
│  App       명령행 — 레시피를 읽어 돌린다        │
├──────────────────────────────────────────────┤
│  OpenCv    요리사들 — 실제 알고리즘 7종         │  OpenCV 씀
├──────────────────────────────────────────────┤
│  Core      주방 시스템 — 칠판·엔진·레시피       │  OpenCV 모름
└──────────────────────────────────────────────┘
```

**아래가 위를 모르는 것이 핵심이다.** `Core`는 블러가 뭔지 모르고, `OpenCv`는 다음 노드가 누군지 모른다.

> ⚠ **웨이퍼 층은 아직 없다.** die 한 장을 검사하는 데까지가 이번 주의 범위다.
> "누가 이웃인가" 는 명령행 인자로 직접 넘겼다 

덕분에 **새 알고리즘을 추가할 때 고치는 파일이 "등록 1줄"뿐**이다 — 엔진도 Core도 안 바뀐다.

### 칠판(blackboard)이라는 규칙

노드끼리 **직접 말을 걸지 않는다.** 할 말이 있으면 칠판에 이름표를 붙여 올려둔다.

요리사 1번이 "썬 양파"를 만들어 `양파`라는 이름표로 올리면, 3번이 그걸 가져다 쓴다.
**3번은 그게 누가 만든 건지 모른다.**

| | |
|---|---|
| 얻는 것 | **순서를 JSON이 정할 수 있다.** 임계값을 바꾸려고 다시 빌드할 필요가 없다 |
| 대가 | 이름표는 그냥 글씨라 **오타를 컴파일러가 못 잡는다** |
| 되사오는 법 | **레시피 검증기** — 실행 전에 이름표 배선을 전부 확인한다 |

## 3. 검사 한 번이 어떻게 도나 — 7단계

```
이웃 die들 ──┐
             ▼
        ① Combine      겹쳐서 골든을 만든다
             │
        ② Normalize    골든과 검사 이미지를 같은 조건으로
             │
        ③ Align        몇 px 어긋난 걸 밀어서 맞춘다
             │
        ④ Difference   ★ 뺀다 — 검출의 심장부
             │
        ⑤ Filter       티끌 노이즈를 지운다
             │
        ⑥ Binarize     "결함이다 / 아니다" 를 정한다
             │
        ⑦ Label        흰 덩어리를 세어 목록으로
             ▼
        결함 목록
```

각 단계가 **왜** 있는지가 진짜 내용이다.

### ① Combine — 왜 평균이 아니라 중앙값인가

이웃 die 3장을 겹친다. 그런데 **이웃 중 한 장에도 결함이 있으면?**

- **평균**이면 그 결함이 3분의 1만큼 골든에 섞인다 — 골든이 오염된다
- **중앙값**이면 "가운데 값"을 고르니 혼자 튀는 값은 **아예 안 들어간다**

> **비유** — 세 사람에게 키를 물어 "보통 키"를 정하는데 한 명이 3미터라고 하면
> 평균은 망가지지만 **가운데 사람을 고르면** 멀쩡하다.

### ② Normalize — 양쪽에 똑같이 해야 한다

골든을 살짝 흐리게(블러) 만든다. **검사 이미지에도 똑같이 해야 한다.**
한쪽만 흐리게 하면 멀쩡한 die인데도 **모든 경계선마다 차이가 남아** 전부 결함으로 잡힌다.

> **비유** — 두 그림을 비교하는데 한 장만 안경을 벗고 보면,
> 그림이 달라서가 아니라 **초점이 달라서** 다르게 보인다.

### ③ Align — 몇 픽셀이 큰일이다

die를 잘라낼 때 **2~3픽셀만 어긋나도** 배선 경계마다 얇은 띠가 남고, 그게 전부 결함으로 잡힌다.
그래서 얼마나 밀렸는지 재서 되밀어 놓는다.

> **이 프로젝트에서 제일 위험한 곳이다.** 이번 주에 여기서 사고가 났다 (§5).

### ④ Difference — 심장부

빼기다. 골든보다 **어두운 만큼 / 밝은 만큼**을 남긴다.

함정이 하나 있다. 골든을 **이웃으로** 만들었으니
**이웃의 결함이 내 차영상에 부호만 반대로 나타난다** — **미러 문제**라고 부른다.

막는 방법은 둘이고 서로 독립이다.

```
골든을 중앙값으로 만든다   →  오염된 한 장이 가운데 값으로 안 뽑힌다
부호 있는 차이를 쓴다      →  어두운 쪽만 보면 밝게 되비친 것은 안 센다
```

### ⑤⑥⑦ Filter → Binarize → Label

- **Filter** — 튀는 점 노이즈를 지우고, **가는 것**을 지운다(모폴로지 열림).
  크기가 아니라 **두께**로 거르는 것이 핵심이다
- **Binarize** — 임계값을 넘으면 흰색, 아니면 검정. **여기서 결함 여부가 확정된다**
- **Label** — 흰 덩어리를 세어 "번호·위치·크기"로 만든다

> **꼭 기억할 것** — 결함의 **면적은 임계값의 함수**다. 임계값을 올리면 같은 결함의 면적이 줄어든다.
> "면적 2000짜리 결함" 이라는 기록은 **임계값을 같이 적지 않으면 의미가 없다.**

### 꼬리 3종 — 찾은 다음

| | |
|---|---|
| `DefectFilter` | 모양으로 거른다 (종횡비 · 원형도 · 채움비) |
| `DefectClassify` | 종류를 붙인다 (Scratch · Blob · Particle) |
| `DefectLimit` | 개수를 제한한다 |

**여기서부터는 이미지를 안 본다.** Label이 뽑아 놓은 **숫자 목록만** 만진다.

> 찾기 7종은 사진을 보는 일, 꼬리 3종은 **찾아 놓은 목록을 정리하는 일**이다.
> 목록 정리는 사진이 진짜든 합성이든 똑같이 동작한다.

> 꼬리 3종은 처음부터 있던 게 아니라 **주 끝에 동기 구현을 보고 가져온 것**이다 (§8).
> 이미지를 안 보는 단계라 옮기기가 쉬웠다.

## 5. ★ 막힌 것 — 정합이 **조용히** 오검 11개를 만들고 있었다

실데이터 셀 하나에서 결함이 11개 나왔다. 그 셀은 **깨끗한 셀**이었다.

원인은 ③ Align이었다.

```
무늬가 규칙적이면 "가장 닮은 자리"가 여러 개다
        ↓
재는 도구(위상 상관)가 엉뚱한 답을 낸다
        ↓
그런데 "못 믿겠다"는 표시 없이 그냥 값을 낸다
        ↓
그 값대로 밀어 버리니 모든 배선 경계에 세로 띠가 남는다
```

**제일 무서운 실패 방식이다.** 프로그램이 죽지 않는다. 오류도 안 난다. **답만 틀린다.**

> **비유** — 벽지가 똑같은 무늬로 반복되는 방에서 "아까 본 자리가 여기 맞나?" 를 물으면
> 자신 있게 틀린 자리를 가리킨다. 무늬가 다 똑같아서 **본인도 모른다.**

### 어떻게 정합이 범인인 줄 알았나

`Align` 만 끄고 다시 돌렸다.

| | r=8 | r=5 | r=3 | r=2 |
|---|---|---|---|---|
| `Align: Translation` | **11** | 1 | 1 | 1 |
| `Align: None` | **1** | 1 | 1 | 1 |

정합을 끄니 **심은 것 하나만** 나온다. 그래서 어긋난 양을 직접 재 봤다.

```
cell_0_0   shift=(-0.02,-0.52)   response= 0.783
cell_1_0   shift=( 0.18, 4.26)   response= 0.101
cell_3_0   shift=(10.90, 0.82)   response=-0.050
cell_4_0   shift=(-0.24,-23.07)  response= 0.105
```

셀들은 사실상 정렬돼 있는데(그래서 정합 없이 오검 0) **측정값이 4px·11px·23px로 제각각**이다.
공통점은 `response`(상관의 뾰족함)가 **0.1이거나 음수**라는 것이었다.

> 반복 무늬는 그 자체가 주기적이라 **위상 상관의 답이 하나로 정해지지 않는다.**
> 닮은 자리가 여럿이면 어느 봉우리가 뽑힐지는 운이다.

**합성 데이터에서도 같은 함정을 겪었다.** 합성 die가 가로줄만 있을 때 정합이 **24px**(줄 간격의 4배) 밀렸다.
비주기 랜드마크(패드 모양)를 넣어 해결했는데, 실데이터에서 같은 원인을 다시 만난 것이다.

> 실제 die에 **정렬 마크가 따로 있는 이유**가 이것이다 —
> 반복 무늬만으로는 "여기가 어디인지" 정할 수 없다.

### 고친 법 — 못 믿을 때 멈추는 가드

| 손잡이 | 기본값 | 하는 일 |
|---|---|---|
| `minResponse` | 0.3 | 상관 신뢰도가 낮으면 **중단**. 주기 무늬에서 이게 걸린다 |
| `maxShiftPx` | 20 | 터무니없이 크게 어긋났다고 나오면 **중단** |

이제 같은 상황에서 오검 11개 대신 이렇게 멈춘다.

```
[실행 실패] node 'align'(Align) — 상관 신뢰도 0.003이 기준 0.3에 못 미칩니다
```

**코드 30줄로 오검 11개가 사라졌다.**

> 이 가드가 **진짜 되는지**(맞는 어긋남은 되찾고 틀린 것만 막는지)는
> 다음 주에 답을 아는 어긋남을 만들어 확인한다.

## 6. ★ 막힌 것 — 처리 시간이 두 배였다

WPF를 얹으면 아래층을 고치기 어려워진다. 그 전에 한 번 훑었다.
**추측으로 고치지 않았다 — 재고, 고치고, 다시 쟀다.**

```
전                                      후
  Combine      24.95 ms  27.9%           Difference   15.55 ms  33.0%
  Difference   23.45 ms  26.2%           Combine       8.51 ms  18.1%
  Filter       12.67 ms  14.2%           Binarize      6.42 ms  13.6%
  Binarize      8.03 ms   9.0%           Filter        5.53 ms  11.7%
  Label         6.16 ms   6.9%           Label         3.87 ms   8.2%
  Align         5.72 ms   6.4%           Normalize     3.33 ms   7.1%
  Normalize×2   8.40 ms   9.4%           Align         2.06 ms   4.4%
  ───────────────────────                Normalize     1.82 ms   3.9%
  합계            90 ms                  ───────────────────────
                                         합계            44 ms
```

| | 전 | 후 |
|---|---|---|
| 1024×1024 처리 시간 | 90 ms | **44 ms** (−51%) |
| 예외 경로 메모리 누수 | 9곳 | **0** |
| 100회 반복 시 메모리 증가 | — | **없음** (테스트로 고정) |

**그리고 결과가 바뀌지 않았다.** 최적화 전후 검출값이 완전히 같다.

> 성능을 고칠 때 **결과가 안 변했다는 것을 같이 확인하지 않으면**
> 고친 게 아니라 망가뜨린 것일 수 있다.

## 7. 검출 한계를 쟀다

실데이터에는 "여기 결함이 있다" 는 정답표가 없다. 그래서 **답을 아는 결함을 심었다.**

```
반지름 2px = 지름 4px   →  검출
반지름 1px = 지름 2px   →  놓침
```

**지름 4px까지 1개씩 정확히** 잡는다. 최적화 전후로도 검출값이 **비트 단위로 같았다.**

```
clean 0 · r=8 area=217 · r=5 97 · r=3 39 · r=2 12 · r=1 0
```

더 작은 것을 잡으려면 `minArea` 와 임계값을 같이 내려야 하는데, **그러면 오검이 는다.**
맞바꿈이라 공짜로 좋아지는 방향이 없다.

## 8. 주 끝에 — 동기와 서로 돌려봤다

같은 과제를 **처음부터 따로** 구현한 둘을 다 읽고 돌려 봤다.

| | 이쪽 | 동기 |
|---|---|---|
| 1250×1250 한 번 | **76.6 ms** | 1,611 ms |
| 테스트 | 176개 | **212개** |
| 알고리즘 | 7 + 꼬리 3 | **15** |
| src / tests 줄 | 5,758 / 2,152 | 4,744 / **3,065** |
| 외부 라이브러리 | OpenCvSharp | **없음** (FFT·BMP·PNG 직접 구현) |
| 실데이터 | 타일 1장 | **대용량 원본 관통** |
| 웨이퍼 층 | 없음 | **있음** |

**한쪽이 더 낫다기보다, 이쪽은 깊게(성능·메모리) 동기는 넓게(기능·실데이터) 갔다.**

동기 쪽에서 **셋을 가져왔다.**

| 가져온 것 | 바꾼 것 |
|---|---|
| **노드 끄기** | 아이디어만. 원본은 아무 노드나 끄는데, `Label`을 끄면 결함 목록이 **아예 안 생기고 예외 없이 0개**가 된다 → 끌 수 있는 노드를 **선언**하게 하고 검증기가 막는다 |
| **결함 후처리 3종** | 로직·기본값 그대로. 자리만 `Core`로 — 입력도 출력도 숫자 목록뿐이라 이미지가 필요 없다 |
| **ECC 정합** | 위상 상관과 **실패하는 방식이 다르다.** 항등 변환에서 가까운 최적점으로 내려가므로 주기 무늬에 덜 걸린다 |

그리고 **동기 쪽에 알릴 것**이 하나 나왔다 — 정합 단계가 응답값을 **기록만 하고 검사하지 않는다.**
§5에서 이쪽이 오검 11개를 냈던 바로 그 상황이다.

## 10. 이 주에 얻은 것

1. **돌아가는 한 벌**을 처음부터 끝까지 만들어 봤다
2. **조용히 틀리는 실패**가 제일 무섭다는 것을 겪었다 → 못 믿을 때 **멈추는 가드**
3. 성능은 **재고 고치고 다시 재야** 한다 — 그리고 결과가 안 변했는지 같이 확인해야 한다
4. **정답을 아는 시험**을 만들어야 성능을 말할 수 있다 (결함 심기 · 일부러 밀기)

---

## 11. 다음 주로 넘긴 것

만들어 놓고 서로 돌려보고 나니 **이대로 가면 안 되겠다**는 것이 분명해졌다.
이유가 둘이었고, 그게 3주차의 시작이다.
