## 1. raw 직접 읽기

**왜.** 실데이터는 raw(픽셀 바이트만 나열한 파일)로 온다. 지금까지는 BMP 로 바꿔 썼다.
raw 에는 머리(헤더)가 없어 파일만으로는 폭 · 높이를 알 수 없다 — 옆의 **설명 파일(사이드카)** 이 알려 준다.

**어떻게.**

| 규칙 | 내용 |
|---|---|
| 설명 파일 키 | `width` · `height` · `bytesPerPixel` · `rowOrder` · `micronsPerPixel` — 교수님 `RawImageMeta` 와 같은 이름 |
| 찾는 순서 | `a.raw` 면 `a.raw.json` → `a.json`. 이미지를 열 때 설명 파일부터 본다(교수님 `ImageSource.Open` 과 같은 순서) |
| 크기 검사 | 파일 크기가 **폭 × 높이 × 픽셀당 바이트와 정확히 같아야** 한다. raw 에는 헤더도 줄 끝 채움도 없어서, 다르면 설명 파일이 틀린 것이다 |
| 행 순서 | 위에서 아래(`TopDown`)만 받는다. 다른 값은 거부 — 조용히 뒤집힌 그림을 검사하면 좌표가 전부 틀린다 |
| 실패하면 | 열었던 파일을 놓는다. 안 놓으면 파일이 계속 잠겨 있다 |

자리 계산은 이미 있던 부분 읽기(`ImageGeometry`)를 그대로 쓴다. 설명 파일은 그 계산에 넣을 숫자만 준다.

**확인.** 같은 원판을 BMP 와 raw 로 각각 돌려 **결과가 같았다**.

## 2. die 수동 지정

**왜.** 원판(원)으로 존을 판정하면 **노치**(원판의 방향 홈)에 걸린 die 를 온전한 die 로 본다.
5주차에는 가장자리 여유를 키워 노치를 가렸는데, 그러면 원 둘레 전체에서 그만큼을 안 보게 된다.

**어떻게.** 사람이 die 하나의 존을 정한다 — 교수님 문서(Phase8 §10)의 **"수동 오버라이드 목록"**.

```
--zone 열,행=E1|E0|off      여러 번 쓴다
```

| 규칙 | 내용 |
|---|---|
| 순서 | 자동 판정이 먼저, 사람이 적은 die 만 덮어쓴다 |
| `off` | 원판 밖과 같게 처리한다 — 검사도 안 하고 **이웃(골든)에서도 빠진다** |
| 실행 전 거부 | 격자 밖 칸 · 알 수 없는 존 · 같은 die 두 번 — 조용히 무시하면 "지정했는데 왜 그대로지" 가 되고, 두 번 적으면 어느 쪽이 이겼는지 모른다 |
| 결과 표시 | 결과 머리에 지정 목록을 찍는다. 특히 `off` 는 die 전체가 빠지므로 결과보다 먼저 보여야 한다 |

**확인.** 실데이터에서 노치 die 2칸을 `off` 로 빼자 가장자리 결함이 0개가 됐다(가장자리 여유는 5주차보다 작게).

## 3. 결함 원본 보기

**왜.** 화면의 웨이퍼 맵은 축소본이다. 원판 원본이면 결함이 1~2 px 점이 되어 모양을 볼 수 없다.

**어떻게.** 결함 목록에서 하나를 고르면 원본 해상도로 그 주변을 잘라 보여 준다(`DefectWindow`).

| 규칙 | 내용 |
|---|---|
| 좌표 기준 | 결함 좌표는 **die 를 잘라 읽은 영역 기준**이다. 사진 위 자리 = 그 영역의 왼쪽 위 + 결함 네모 |
| 창 크기 | 결함 긴 변의 **4배**, **128~1024 px** 로 제한 — 작은 결함도 주변 무늬와 같이 보이고, 큰 결함이 화면을 넘지 않게 |
| 사진 가장자리 | 창이 사진 밖으로 나가면 안쪽으로 민다. 사진이 창보다 작으면 사진 전체 |

순수 계산이라 이미지 없이 시험된다.

## 4. 화면 입력

**왜.** 정렬 표식 · 수동 지정 · 원판 마스크가 명령행에서만 됐다.

| 어디 | 넣은 것 |
|---|---|
| 웨이퍼 탭 | 정렬 표식(조각 · 설계 위치 · 찾는 범위) · 수동 지정 입력칸 |
| die 탭 미리보기 | 원판 마스크(`waferMask`)를 받는 레시피도 돌린다 — 미리보기 그림에 원을 그려 원판 밖을 어둡게 칠하고 마스크를 같이 넘긴다 |

**글자 규칙은 한 곳.** 점(`x,y`)과 수동 지정(`열,행=off`)을 읽는 규칙을 `WaferInputText` 하나에 두고 명령행과 화면이 같이 쓴다.
따로 만들면 명령행에서 되는 글자가 화면에서 안 되는 날이 온다.

**실데이터로 확인하다 겪은 것.** 화면에서 실데이터를 돌리자 결함이 **72개** 나왔다.
명령행으로 같은 설정을 화면 없이 재현하니 0개였고, 원인은 **E0 레시피를 다른 것으로 고른 것**이었다. 고른 뒤 명령행과 같은 결과가 나왔다.
→ 화면은 입력칸이 많아 한 칸만 달라도 결과가 달라진다. 이것이 6절(설정을 파일 하나로)의 계기가 됐다.

## 5. 미뤄 둔 실험 — `todo.md` §3

### 5.1 밝은 결함으로 두 레시피 비교 ✅

**왜.** 대안 레시피(`die.diff.median` — 중앙값 + 양쪽 부호)의 장점으로 "밝은 결함도 본다"를 적어 두었는데,
실데이터에 밝은 결함이 없어 **확인한 적이 없었다**(3주차 레시피 확정 기록의 단서).

**어떻게.** 부분 촬영 실데이터의 결함 없는 die 여섯 칸에 **밝은 점(+80/255)**을 심었다.
- 사진은 **읽을 때만** 바꾸고 파일은 그대로 둔다(실험 프로그램은 레포 밖)
- 지름 12 · 26 · 26 · 32 · 40 · 52 px, die 마다 하나
- 심는 자리는 die 마다 13×13 범위폭이 가장 작고 평균이 0.6 미만인 곳(밝게 올릴 여유가 있는 평평한 자리)
- 두 레시피로 웨이퍼 전체를 검사 — 기본은 같은 행 좌우 이웃, 대안은 가까운 순 3장

| | 기본 `die.diff` (Mean + DarkOnly) | 대안 `die.diff.median` (Median + Absolute) |
|---|---|---|
| 원래 있던 어두운 결함 | 전부 찾음 · **오검 0** | 전부 찾음 + **오검 2** |
| 심은 밝은 점 — 지름 12 px | 놓침 | 놓침 |
| 심은 밝은 점 — 지름 26 px 이상(5개) | **전부 놓침**(설계대로) | **전부 찾음** |
| 밝은 점 때문에 **다른 die** 에 생긴 오검 | **2** | 0 |

**배운 것 ① — 지름 약 25 px 보다 작은 결함은 부호와 상관없이 못 잡는다.**
두 레시피 모두 `minArea 500` 이다. 지름 12 px 원은 약 113 px 라 덩어리째 버려진다. 부호가 아니라 **크기의 한계**다.

**배운 것 ② — DarkOnly 도 미러가 난다. 밝은 결함이 있으면.**
밝은 점을 심은 die 의 **옆 die** 에서 어두운 결함이 새로 나왔다.

```
옆 die 의 골든에 밝은 점이 섞인다  →  옆 die 는 골든보다 '어둡게' 보인다  →  DarkOnly 가 결함으로 잡는다
```

Mean 은 이웃이 2장이면 밝은 점을 반으로 묽혀 임계(0.2)를 못 넘는다(0.31 → 0.16).
그래서 **이웃이 1장뿐인 끝 열 die 에서만** 났다. 5주차의 *"막는 것은 장수가 아니라 부호다"* 는
**결함이 어둡다는 전제**에서만 참이다. 밝은 이물질이 있는 공정이면 기본 레시피는 그 이웃에 어두운 미러를 낸다.

**배운 것 ③ — 대안 레시피의 오검 2개는 실데이터의 '2장 겹침 미러'다.**
오검이 난 die 의 골든 3장 중 **2장에 결함이 거의 같은 자리**(수십 px 안)에 있었다. 중앙값이 그 결함을 골든으로 넣고,
Absolute 가 '검사 die 가 더 밝음' 을 결함으로 잡았다. 오검의 면적이 두 결함이 겹친 넓이와 같은 크기다.
5주차 상세 §11.1 ★3(합성에서 "3개 심었는데 4개")과 **같은 현상이 실데이터에서도** 났다.

| 정리 | 기본 | 대안 |
|---|---|---|
| 어두운 결함만 나오는 공정 | **맞다** — 오검 0 | 2장 겹침 미러가 날 수 있다 |
| 밝은 결함도 나오는 공정 | 밝은 결함을 못 보고, 끝 열에 어두운 미러를 낸다 | 밝은 결함을 본다(지름 약 25 px 이상) |

→ 레시피를 고르는 기준은 여전히 **"이 공정의 결함이 어느 쪽인가"** 다. 바뀐 것은, 기본 레시피를 쓸 때
**밝은 이물질이 끝 열 이웃에 어두운 미러를 만든다**는 위험을 알고 쓴다는 것.

### 5.2 die 전체로 결함 수 ✅

5.1 의 기준 실행(점을 심기 전)이 답이다. 기본 레시피로 **die 전체**를 보니 결함 **16개 · 오검 0**.
3주차의 12개는 die 가운데 일부만 본 **부분 집계**였다. 교수님 실데이터 골든마스터(결함 16)와 같다.

### 5.3 표식 정렬이 같은 입력에 같은 값을 내는가 ✅

**왜.** 이 프로젝트의 규칙이 *"같은 입력이면 같은 결과"* 다. 깨지면 어제와 오늘의 차이가
코드 때문인지 운 때문인지 알 수 없고 회귀 시험이 무너진다.
v1 에서 **위상상관(`PhaseCorrelate`)이 같은 입력에 매번 다른 값**을 내는 것을 봤다(소수 셋째 자리에서 흔들림).
OpenCV 의 DFT 가 여러 스레드로 나눠 더해서, 실수 덧셈 순서가 실행마다 달라지기 때문이다.
v2 에서는 다시 재지 않았는데, **5주차 상세 §11.4 로 표식 정렬이 실데이터 경로의 첫 단계가 됐다** —
표식 찾기(`MatchTemplate`)도 큰 조각에서는 DFT 를 쓴다.

**어떻게.** 원판 실데이터로 표식 정렬만 **30번** 돌려(격자 1×1 로 die 검사는 한 칸) 값을 **소수 17자리까지** 비교했다.

| 잰 것 | 서로 다른 값 | 폭 |
|---|---|---|
| 표식 2개의 자리(x · y) | 각 1개 | **0** |
| 표식 점수 | 1개 | **0** |
| 정렬 원점 x · y | 각 1개 | **0** |
| 각도 · 배율 · 어긋남 | 각 1개 | **0** |

**결정적이었다.** 30번이 마지막 자리까지 같다.

**왜 위상상관과 다른가 — 줄이는 자리가 있나 없나.**

```
MatchTemplate   픽셀마다 점수를 따로 낸다  →  한 픽셀 값은 다른 픽셀과 안 섞인다  →  스레드 순서가 안 보인다
PhaseCorrelate  여러 픽셀을 더해 숫자 하나로 줄인다  →  더하는 순서가 끝자리에 남는다
```

우리 소수점 자리 보정도 점수판의 **이웃 몇 칸만** 보는 국소 계산이라, 점수판이 같으면 결과도 같다.

**단서.**

- 이 컴퓨터 · 이 OpenCV 판 · 이 창 크기에서 30번이다. 창이 아주 커지면 OpenCV 가 다른 길로 갈 수 있다
- **사진 전체를 뒤지는 길(찾는 범위 0)은 안 쟀다** — 원판 원본은 통째로 못 읽는다
- `Align`(위상상관) 자체는 안 쟀다. 3주차에 레시피에서 뺐고(효과 0) 지금 어느 레시피도 안 쓴다

**쓸모.** 실데이터 시험(`todo.md` §3-1)의 **허용오차를 감이 아니라 이 측정으로 정한다** — 정렬은 자리까지 같으니 좁게 잡아도 된다.
다만 **완전일치는 쓰지 않는다**(Lesson09 — 허용오차 비교). 기계·판올림이 바뀌면 끝자리는 달라질 수 있다.

**덤.** 정렬 한 번이 **0.5초**다(창 2개만 읽는다). 사진 전체를 읽던 때는 원판 원본에서 아예 돌지 못했다.

## 6. 웨이퍼 레시피 — 설정을 파일 하나로

**계기.** 4절 — 웨이퍼 탭에 격자 · 원판 · 표식 · 수동 지정을 매번 입력하는 것이 번거롭고, 한 칸만 틀려도 결과가 달라진다.
`deferred.md` §10 ② 의 넣을 조건이 됐다.

**교수님 방식.** 작업 파일(`*.job.json`)을 먼저 만들었다가, 지금은 **통합 블록 레시피**(`*.wafer.json`)를 권장한다. 그쪽으로 갔다.

```
[TemplateMatchAll] → [SolveAlignment] → [InspectDies] → [TransformAbs] → [Sampling]
 ① 표식 찾기          ② 자세 계산        ③ die 전부 검사     ④ 웨이퍼 좌표 · 결과 추리기
 창마다 반복           1번               die 마다 반복        1번
```

### 6.1 단계

| | 내용 | 테스트 |
|---|---|---|
| 1 | Core — 블록 사이로 넘길 종류 4개(표식 목록 · 놓인 자세 · 격자 · 웨이퍼 결함 목록) · 예약 입력 `alignSrc` · `alignTemplate` | 545 |
| 2 | 블록 5종 · 웨이퍼 레시피용 명부 · die 탭 팔레트는 웨이퍼 종류를 주고받는 블록을 숨긴다(이름이 아니라 포트 종류로) | 569 |
| 3 | 실행기 `WaferRecipeRunner` | 581 |
| 4 | 명령행 `--recipe` · 견본 `samples/wafer/demo.wafer.json` | 584 |
| 5 | 화면 블록 편집기 — 보류, 미팅에서 묻는다 | |

### 6.2 토막 내서 돈다

엔진은 블록을 한 번씩만 돈다(4주차). 그런데 ①은 창마다, ③은 die 마다 돌아야 한다.

- `InspectDies` 는 **경계 블록**이다 — 설정만 담고, 엔진이 돌리면 오류로 멈춘다(빈 결과가 "결함 0개" 로 읽히면 안 된다)
- 실행기가 레시피를 `InspectDies` 에서 자른다 — 앞 = 그 블록으로 흘러드는 블록, 뒤 = 그 블록에서 흘러나가는 블록
- 앞은 '표식 목록' 칸에서 한 번 더 자른다. ①찾기 토막은 창마다 돌리고 찾은 자리를 사진 좌표로 모은다. ②풀기 토막은 모은 목록으로 한 번
- 뒤 토막이 없으면 좌표 변환만 한다(교수님 하위호환과 같다)
- 결과는 '웨이퍼 결함 목록을 내고 아무 블록도 안 읽는 칸' 하나에서 꺼낸다 — 둘이면 거부

교수님은 정렬 토막을 **사진 전체에서 한 번** 돌린다(창은 "후속"으로 남겨 둠). 원판 원본은 통째로 읽으면 수 GB 라 우리는 창이 필요했다(5주차 §11.4).

### 6.3 우리가 정한 것

| | 우리 | 교수님 | 까닭 |
|---|---|---|---|
| 입구 | 명령행 옵션 · 화면 입력 · 레시피 파일 — **속은 `WaferInspection` 하나** | 레시피 · 작업 파일 | 화면은 die 레시피를 파일이 아니라 메모리로 들고 있어 레시피로 바꾸려면 가짜 경로가 필요했다. 정렬 가드 · 격자 · die 반복이 한 곳이면 된다 — 두 입구가 같은 답인지 시험이 본다 |
| 값을 적는 자리 | 표식 설계 자리 · 대략 원점 · 판정 기준은 `SolveAlignment` 에만. 격자 · 원판 · 수동 지정 · 조각 경로는 `InspectDies` 에만 | 표식 자리를 두 블록에, 판정 기준은 `InspectDies` 에 | 같은 값을 두 곳에 적으면 언젠가 어긋난다 |
| `edgeExclusionPx` | 원판 가장자리에서 안쪽으로 뺄 폭(px). 겹 수는 `edgeRings` 로 따로 | 문서는 같은 뜻, 코드는 테두리 한 겹 스위치 | 문서의 뜻을 따랐다 |
| `nmsRadiusPx` 기본 | 0 = 조각 짧은 변의 절반 | 8 | 교수님 문서가 "템플릿 크기의 절반 이상" 을 권한다. 큰 조각에서 8 이면 한 표식이 여러 개로 잡힌다 |
| 조각 | 1개만. 2개면 거부 | `features[0]` 만 씀 | 조용히 첫 번째만 쓰면 둘 다 쓰인다고 믿게 된다 |
| 놓인 자세 칸의 값 | `AlignmentResult` — 자세 + 판정(받아들였나 · 까닭) | `WaferAlignment` | 실행기가 "못 믿으면 시작 안 함" 을 지키고 까닭을 띄운다 |

### 6.4 실행 전에 막는 것

die 를 하나도 돌기 전에, 파일도 하나도 읽기 전에 거부한다(끝값 2).

- 배선 오류 — 검증기(`RecipeValidator`)가 먼저 본다. 예: '표식 목록' 을 '놓인 자세' 칸에 바로 꽂음(자세 계산을 건너뜀)
- `InspectDies` 0개 · 2개 · 어디에도 안 이어진 블록 · 끝 블록 2개 · 조각 2개
- 정렬을 이었는데 조각이 없음 · 정렬하면서 원점을 두 곳에 적음 · `expected` 가 2개 미만

### 6.5 명령행과 견본

```
diepipe wafer -i <사진> --recipe <웨이퍼레시피>
```

- 안에 적힌 die 레시피 · 조각 경로는 **레시피 파일이 있는 폴더 기준**(교수님 CLI 와 같다). 절대 경로도 된다
- `-i` 말고 다른 옵션과 같이 못 쓴다 — 파일 값과 옵션 값 중 어느 것이 쓰였는지 결과에서 안 보인다
- 결과 머리 맨 위에 레시피 파일과 돈 블록(`match(TemplateMatchAll) → … → sample(Sampling)`)을 찍는다
- 견본은 `diepipe demo` 기본 그림에 맞췄다. 옵션으로 돌린 결과와 결함 좌표 · 면적까지 같다
- 견본 조각 그림(`features/demo_mark.bmp`)은 코드가 그린 조각과 **픽셀까지 같은지** 시험이 본다. `.gitignore` 의 `*.bmp` 에서 **이 파일 하나만** 예외로 풀었다 — 다른 `.bmp` 는 그대로 막힌다
- 실데이터 웨이퍼 레시피는 **레포 밖**(사진 옆)에 둔다 — 격자 · 피치 · 원판 위치가 들어간다

## 7. 실데이터 회귀 시험 — `todo.md` §3-1

**왜.** 실데이터 결과는 사람이 명령행으로 돌려 눈으로 확인해 왔다. 다음 작업(화면 블록 편집기)은 편집기 · 레시피 변환을 크게 건드리는데,
그 사이 실데이터 결과가 바뀌어도 알아챌 장치가 없었다.

**어떻게.** 교수님 `WaferRealDataTests`(Phase8 8.7)와 같은 방식 — 확인된 결과를 **기준 파일**로 굳히고, 시험을 돌릴 때마다 다시 검사해 비교한다(`RealDataTests`).

| 어디 | 무엇 |
|---|---|
| 레포 안 | 시험 코드만 — 실데이터에 관한 이름 · 경로 · 숫자가 하나도 없다 |
| 레포 밖 | 케이스 목록 파일 · 케이스마다 사진 · 웨이퍼 레시피 · 기준 파일. 경로는 목록 파일 기준 |
| 연결 | 환경 변수 `DIEPIPE_REALDATA` 가 케이스 목록 파일을 가리킨다. **없으면 조용히 통과**(원본이 있는 컴퓨터에서만 돈다) |

```
케이스 목록 파일 = { "cases": [ { "name", "image", "recipe", "baseline" }, … ] }
```

- 레포 밖 설정은 **웨이퍼 레시피 그대로**다(6절). 실데이터용 설정 형식을 따로 만들지 않았다 — 같은 형식을 두 번 만들면 언젠가 어긋난다
- 검사는 명령행 `--recipe` 와 같은 입구(`WaferRecipeRunner.RunFile`)로 돈다

**기준 파일에 적는 것.** 멈춤 여부 · 정렬 받아들임 · 원점 · 각도 · 배율 · die 수(E1 · E0 · 원판 밖 · 검사 실패) · 결함 목록(die 칸 · 존 · 자리 · 면적).
결함 목록은 **추리기 전**(`Found`)이다 — 판정과 같은 것을 본다.

**비교 — 허용오차**(Lesson09, 완전일치 금지).

| 값 | 허용 | 까닭 |
|---|---|---|
| 원점 x · y | ±0.01 px | 5.3 — 같은 입력 30번이 끝자리까지 같았다. 좁게 잡는다 |
| 각도 | ±0.0001° | 〃 |
| 배율 | ±0.00001 | 〃 |
| 결함 자리 | ±0.5 px | 반올림 한 칸 |
| 결함 면적 | ±1% (최소 1 px) | |
| 멈춤 · 정렬 받아들임 · die 수 · 결함 수 · 결함의 die 칸과 존 | **같아야 한다** | 개수와 판정은 흔들릴 이유가 없다 |

- 케이스 하나가 틀려도 멈추지 않고 전부 돌린 뒤 다른 곳을 **한꺼번에** 알린다 — 여러 케이스를 같이 봐야 원인이 좁혀진다
- 기준 갱신은 결과가 **일부러** 바뀌는 수정을 했을 때만 `UPDATE_BASELINE=1` 로 돌려 다시 쓰고, 쓴 뒤 사람이 검토한다
- 기준 파일이 없으면 실패한다(갱신하라는 문장과 함께) — 조용히 통과하면 비교 없이 넘어간다

```
set DIEPIPE_REALDATA=<레포 밖 케이스 목록 파일>
dotnet test --filter RealData
set DIEPIPE_REALDATA=
```

- 같은 창에서 변수를 지우지 않으면 이후 모든 `dotnet test` 가 실데이터까지 돌아 느려진다(약 45초) — 끝나면 비운다

**확인.** 원판 · 부분 촬영 두 케이스로 기준을 만들고, 그 값이 그동안 손으로 확인한 결과와 같은지 사람이 대조했다. 이후 시험은 두 케이스 모두 기준과 같다.
