# 부분 재실행 — 슬라이더를 위한 구조

WPF에서 임계값 슬라이더를 드래그하면 초당 수십 번 검사가 돈다.
1024×1024 한 번이 **86ms**면 초당 11번이 한계고, 화면은 끊겨 보인다.

그런데 임계값을 바꿨을 때 실제로 달라지는 것은 `Binarize`와 `Label`뿐이다.
골든을 만들고, 정규화하고, 정합하고, 차영상을 뜨는 앞의 6개는 **조금도 달라지지 않는다.**

```
Combine → Normalize → Normalize → Align → Difference → Filter │ Binarize → Label
└──────────── 임계값과 무관. 지난 결과를 그대로 쓴다 ────────────┘ └─ 이것만 다시 ─┘
```

---

## 1. 잰 결과

```bash
diepipe bench --size 1024 --ticks 20 --timings
```

| 크기 | 전체 실행 | 부분 재실행 | |
|---|---|---|---|
| 1024×1024 | 86.1 ms | **4.1 ms** | 21배 |
| 2500×2500 | 536.5 ms | **22.0 ms** | 24배 |

중앙값이다(평균이 아니라 — GC 한 번이 평균을 통째로 밀어 올린다).
`docs/pre-wpf-check.md`가 적어 둔 목표는 "44ms → 10ms"였는데, 실제로는 그보다 많이 줄었다.

> **답이 같은지부터 본다.** `bench`는 마지막에 부분 재실행과 전체 실행의 결함을
> 면적·중심까지 대조해 출력한다. 빨라지려고 답이 달라지면 아무 의미가 없다.

---

## 2. 어디부터 다시 돌까 — 노드 지문

레시피의 노드 하나를 **id · type · 배선 · 파라미터**로 지문화한다(`RecipeFingerprint`).
지난 실행의 지문 목록과 나란히 놓고 **처음으로 달라지는 자리**가 곧 답이다.

```
지난번  [a1, b2, c3, d4, e5, f6, g7, h8]
이번    [a1, b2, c3, d4, e5, f6, X9, h8]
                                 ↑ 여기부터 다시 — 6개 재사용
```

### 뒤쪽이 같아도 전부 다시 돈다

`g7`만 바뀌었는데 `h8`도 다시 돈다. `h8`의 입력이 `g7`의 출력일 수 있기 때문이다.
의존 그래프를 따져 더 아낄 수는 있지만, **그건 틀렸을 때 조용히 틀린다** —
결함 개수가 미묘하게 다른 결과가 나오고, 원인을 찾을 방법이 없다.
여기서 몇 ms 더 아끼는 것보다 부분 재실행이 **항상** 전체 실행과 같은 답을 내는 쪽이 훨씬 중요하다.

### 처음부터 도는 경우 셋

| | 왜 |
|---|---|
| 첫 실행 | 재사용할 것이 없다 |
| 이미지가 바뀜 | 앞 노드의 결과가 통째로 의미를 잃는다 |
| 머리말이 바뀜 | `workingFormat`이 `Gray8`이 되면 파라미터는 그대로인데 **숫자의 뜻**이 달라진다 |

이미지는 **참조로** 비교한다. 내용 해시로 비교하면 픽셀을 다 훑어야 해서
아끼려던 시간만큼 도로 쓰게 된다. "같은 객체를 다시 줬다"가 재사용의 조건이다.

### 레시피를 정리한 것만으로는 다시 돌지 않는다

파라미터를 원문 그대로 비교하면 줄바꿈·들여쓰기만 바꿔도 다시 돈다.
`JsonSerializer`로 다시 써서 비교하므로 서식은 영향이 없다.
(키 순서가 바뀌면 여전히 다시 돈다 — 보수적인 쪽으로 틀리는 것이라 그대로 뒀다.)

## 3. 진짜 어려운 부분은 메모리였다

지금까지 구조는 **실행 1회 = 풀 스코프 1개**였다. 끝나면 `ReleaseScope()`가 전부 반납하고,
반납된 버퍼는 다음 실행의 `Rent`가 가져가 **내용을 덮어쓴다.**
즉 "지난 실행의 중간 결과"라는 것이 애초에 존재할 수 없었다.

### 남길 것을 지정한다 (반납할 것이 아니라)

```csharp
void ReleaseScopeExcept(IReadOnlySet<IImage> keep);
```

반납 목록을 받는 방식으로 하면 **미아 버퍼**가 샌다.
노드 중에는 내부 임시 버퍼를 돌려주지 않고 스코프 종료에 기대는 것이 있는데,
그런 버퍼는 반납 목록에 안 들어가므로 매 틱 쌓인다. 30초 드래그면 수백 장이다.

남길 것만 지정하면 **나머지는 무엇이든 회수된다.** 남길 것은 칠판이 아직 들고 있는 이미지다.

```
매 실행 끝 → Sweep() → 칠판이 안 들고 있는 버퍼 전부 반납
```

테스트가 40틱을 돌려 살아 있는 버퍼 수가 **늘지 않는 것**을 고정한다
(`Dragging_a_slider_does_not_grow_memory`). 부분 재실행은 "일부러 반납하지 않는" 구조라,
누수와 의도된 보관이 겉보기에 같다 — 구분하는 방법은 그 수가 안정적인지 보는 것뿐이다.

### 엔진의 `finally`는 남겨 뒀다

```csharp
finally { if (releaseScope) context.Pool.ReleaseScope(); }
```

`releaseScope: false`는 세션만 쓴다. 이게 `finally`인 이유가 "오류 한 번에 버퍼가 통째로 새지 않게"라
기본값은 그대로 두고, 반납 책임을 가져가는 쪽만 끄게 했다.

## 4. 칠판을 그대로 재사용하면 안 된다

여기서 버그를 하나 만들었다가 테스트로 잡았다.

지난 실행의 `PipelineContext`를 그대로 다시 쓰면 **지난 실행의 취소 토큰**을 물고 돈다.
한 번 취소된 세션은 영영 취소된 채로 돌고, 새로 건넨 취소는 먹지 않는다. 진단도 마찬가지다.

```csharp
PipelineContext carried = _context.Carry(diagnostics, cancellation);
```

값만 이어받고 진단·취소는 이번 것으로 갈아 끼운다.
`A_cancelled_run_makes_the_next_one_start_over`가 이걸 고정한다.

## 5. WPF가 쓸 자리

```csharp
using InspectionSession session = new();

// 슬라이더 콜백마다
InspectionResult result = session.Run(recipe, roi, golden, diagnostics, cancellation: token);
```

| 물음 | 답 |
|---|---|
| 스레드 안전한가 | **아니다.** 풀과 칠판을 실행 사이에 들고 있는 것이 존재 이유다. 미리보기 패널 하나당 세션 하나, 한 스레드에서만 |
| UI 스레드에서 돌려도 되나 | **안 된다.** 첫 실행이 2500×2500이면 536ms다. 백그라운드로 돌리고 결과만 디스패치 |
| 취소는 얼마나 빨리 듣나 | 노드 경계에서만 본다. 2500×2500이면 Align 한 노드가 250ms라 **최대 그만큼** 늦는다 |
| 안 돌린 노드의 중간 이미지는 | `TryGetIntermediate("diff", out var image)` — 칠판에 그대로 살아 있다 |
| 실패하면 | 세션이 스스로 캐시를 버린다. 다음 실행은 처음부터 |
| 실행 전에 거절된 레시피는 | 캐시를 **안** 버린다. 아무것도 실행되지 않았으니 지난 결과는 여전히 옳다 |

### 중간 이미지는 진단 캡처가 아니라 칠판에서 꺼낸다

부분 재실행에서는 안 돈 노드의 캡처가 **이번 실행에 안 생긴다.**
`RecordingDiagnostics.Captures`만 보고 화면을 그리면 슬라이더를 움직일 때마다
차영상 패널이 비어 버린다. 그런데 그 이미지는 칠판에 그대로 있다.

```csharp
if (session.TryGetIntermediate("diff", out IImage diff)) { /* 화면에 */ }
```

**⚠ 다음 `Run`까지만 유효하다.** 풀 소유 버퍼라 재실행 때 회수되어 덮어써진다.
오래 들고 있어야 하면 `Clone()`.

## 6. `bench`로 무엇을 보나

```bash
diepipe bench --size 1024 --ticks 20 --timings
```

`--timings`를 주면 **전체 실행 한 번의 노드별 시간**이 같이 나온다.
부분 재실행은 슬라이더를 해결했지만 **새 die가 올 때마다 도는 전체 실행은 그대로**라,
다음에 무엇을 고칠지는 이 표에서 정한다.

| 노드 | 1024×1024 | 2500×2500 |
|---|---|---|
| Align | 29.1 ms (41%) | 250.0 ms (47%) |
| Difference | 19.8 ms (28%) | 119.8 ms (23%) |
| Combine | 6.5 ms (9%) | 58.3 ms (11%) |
| Filter | 7.0 ms (10%) | 42.9 ms (8%) |
| 나머지 넷 | 8.8 ms (12%) | 56.5 ms (11%) |

합성 die 기준이다. 실데이터는 레포에 없고(회사 이미지 파생물) 크기를 마음대로 고를 수 없어서인데,
여기서 궁금한 것은 결함을 잘 찾는지가 아니라 **같은 일을 얼마나 덜 하는지**라 합성으로 충분하다.
