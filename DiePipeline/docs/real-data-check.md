# 실데이터 검증 기록

`2026-09-12` · [← README](../README.md)

> 합성 die가 아니라 **실제 장비에서 취득한 이미지**로 파이프라인을 돌려 본 기록.
> 오검이 나는지, 잡아야 할 것을 잡는지, 얼마나 작은 것까지 잡는지.

---

## 0. 결론

| 물음 | 답 |
|---|---|
| 깨끗한 실데이터에서 오검이 나는가 | **0개** |
| 심은 결함을 잡는가 | **반지름 2px까지 1개씩 정확히** |
| 검출 한계 | 반지름 1px(지름 2px)에서 놓침 |
| 물리 단위 환산 | 지름 4px ≈ **2µm**까지 검출 |

그리고 **파이프라인의 버그를 하나 찾았다** — 정합이 조용히 오검 11개를 만들고 있었다(5절).

## 1. 안전 규칙 — 먼저 정한 것

쓴 이미지는 `visionstack_proto/samples/images/wafer_tile_*.png`인데, 그 README에 이렇게 적혀 있다.

> 원본: 장비에서 취득한 대용량 BMP. **원본 자체는 커밋하지 않는다**(여기엔 잘라낸 타일만 둔다).
> (구체적인 파일 이름·해상도는 회사 자료라 옮겨 적지 않는다.)

즉 이 타일들은 **회사 자료에서 잘라낸 파생물**이다. 그래서:

```
❌ DiePipeline 레포에 복사하지 않는다
❌ 잘라낸 셀·주입 이미지도 레포에 넣지 않는다
✅ 원래 자리에서 경로로만 읽는다
✅ 중간 산출물은 레포 밖 임시 폴더에
✅ 레포에 남기는 것은 방법과 숫자뿐
```

`.gitignore`가 2차 방어선이지만, **애초에 레포 밖에 두는 것이 1차 방어선**이다.

## 2. 대상

| | |
|---|---|
| 파일 | `wafer_tile_1.png` (1024×1024, 8-bit gray) |
| 내용 | 라인&스페이스·체커보드 캘리브레이션 패턴, **셀 피치 100px** |
| 배율 | 0.5 µm/px *(같은 원본의 raw 사이드카 `micronsPerPixel` 기준 — 타일에도 같은 배율이라고 가정)* |

### 먼저 재기 — `diepipe stats`

```
평균       0.5947   ( 151.7 / 255)
표준편차   0.2924   (  74.6 / 255)

백분위수
     1.0%    0.3490   (  89.0 / 255)
    50.0%    0.3922   ( 100.0 / 255)     ← 배경
    75.0%    1.0000   ( 255.0 / 255)     ← 밝은 구조물(25% 이상이 포화)

국소 노이즈(중앙값 필터 대비)  0.0094
결함 대비(중앙값 ↔ 극값)       0.6078
→ 임계값 후보 구간  0.0378 ~ 0.3039
```

**국소 노이즈를 전체 표준편차로 재면 안 된다.** 거기엔 회로 무늬의 명암이 들어 있어
실제 노이즈(0.0094)보다 30배 크게 나오고, 임계값을 과도하게 높이게 된다.
그래서 `stats`는 **원본과 중앙값 필터의 차이**로 노이즈를 잰다.

레시피의 임계 `0.12`는 이 구간(`0.038 ~ 0.304`) 안에 들어간다. 그대로 써도 된다는 뜻.

## 3. 절차

실데이터에는 "여기에 결함이 있다"는 정답표가 없다. 그래서 **답을 아는 결함을 심는다** —
교수님 레포의 실데이터 골든마스터도 같은 방법이다(*주입 결함 16개와 1:1 대조*).

```
① 셀 5장을 잘라낸다 (피치 100)
② 가운데 셀을 검사, 나머지 4장을 골든으로
③ 깨끗한 상태에서 오검이 0인지 확인
④ 반지름을 줄여가며 결함을 심고, 어디까지 잡는지 본다
```

### 재현 명령

```bash
# 레포 밖 임시 폴더
SET CELLS=%TEMP%\diepipe_cells

diepipe stats --image <타일 경로>

diepipe crop --image <타일 경로> --rect 200,200,100,100 --grid 5x1 --pitch 100,100 --out %CELLS%

diepipe measure --image %CELLS%\cell_2_0.png --golden %CELLS%\cell_0_0.png ...

diepipe inject --image %CELLS%\cell_2_0.png --spot 50,50,3 --out %CELLS%\hurt.png

diepipe run --recipe samples\recipes\die.diff.json --image %CELLS%\hurt.png ^
            --golden %CELLS%\cell_0_0.png --golden %CELLS%\cell_1_0.png ^
            --golden %CELLS%\cell_3_0.png --golden %CELLS%\cell_4_0.png
```

> ⚠ 위 명령은 **경로를 전부 인자로 받는다.** 실데이터 경로가 코드나 레시피에 들어가지 않게.

## 4. 결과

정합을 끄고(`Align: None` — 이유는 5절) 반지름을 줄여가며 측정.

| 주입 반지름 | 검출 수 | 검출 면적 | 원 넓이(이론) | 지름(µm) |
|---|---|---|---|---|
| — (깨끗) | **0** | — | — | — |
| 8 | 1 | 217 | 201 | 8.0 |
| 5 | 1 | 97 | 79 | 5.0 |
| 3 | 1 | 39 | 28 | 3.0 |
| 2 | 1 | 12 | 13 | 2.0 |
| 1 | **0** | — | 3 | 1.0 |

**읽어야 할 것 셋**

1. **깨끗한 셀에서 0개** — 실제 회로 무늬를 결함으로 오인하지 않는다. 이게 가장 중요하다
2. **반지름 2까지 정확히 1개씩** — 위치·개수 모두 맞다
3. **검출 면적 > 이론 넓이** (217 vs 201) — 블러가 경계를 퍼뜨린 만큼 커진다.
   반대로 r=2에서는 12 < 13으로 작아진다 — 임계값이 가장자리를 깎기 때문.
   **면적은 결함의 성질이 아니라 임계값의 함수**라는 것이 실데이터에서도 그대로 보인다

### 검출 한계

```
반지름 2px = 지름 4px = 2.0µm   → 검출
반지름 1px = 지름 2px = 1.0µm   → 놓침
```

타일에 라벨된 결함 크기가 `12 / 6 / 3.6 / 3 / 1.8 µm`이므로, 지금 설정으로는
**1.8µm를 제외한 전부를 잡을 수 있다.** 더 작은 것을 잡으려면 `minArea`(현재 5)를 내리고
임계값도 함께 내려야 하는데, 그러면 오검이 늘어난다 — 맞바꿈이다.

## 5. 찾은 문제 — 정합이 오검 11개를 만들고 있었다

### 증상

반지름 8짜리 결함 하나를 심었더니 **결함 11개**가 나왔다. 그것도 모양이 이상했다.

```
#1   (32,7)  9×70    area=397
#2   (44,6) 31×94    area=1385
#3   (21,8)  7×69    area=379
```

전부 **세로로 길쭉한 띠**다. 점 결함 하나를 심었는데 세로 띠가 나올 이유가 없다.

### 원인

`Align`을 끄고 다시 돌려 봤다.

| | r=8 | r=5 | r=3 | r=2 |
|---|---|---|---|---|
| `Align: Translation` | **11** | 1 | 1 | 1 |
| `Align: None` | **1** | 1 | 1 | 1 |

정합이 범인이었다. 그래서 어긋남을 **재 봤다**(`diepipe measure`).

```
cell_0_0   shift=(-0.02,-0.52)   response= 0.783
cell_1_0   shift=( 0.18, 4.26)   response= 0.101
cell_3_0   shift=(10.90, 0.82)   response=-0.050
cell_4_0   shift=(-0.24,-23.07)  response= 0.105
```

셀들은 사실상 정렬돼 있는데(그래서 정합 없이 오검 0) **측정값이 4px·11px·23px로 제각각**이다.
공통점은 `response`(상관의 뾰족함)가 0.1이거나 음수라는 것.

> **라인&스페이스 무늬는 그 자체가 주기적이라, 위상 상관의 답이 하나로 정해지지 않는다.**
> 닮은 자리가 여럿이면 어느 봉우리가 뽑힐지는 운이다.
> 반지름 8짜리 결함은 그 운을 뒤집기에 충분했다.

### 같은 함정을 합성에서도 겪었다

이 프로젝트를 만들면서 합성 die가 **가로줄만** 있을 때 정합이 **24px**(= 줄 간격 6 × 4) 밀렸다.
비주기 랜드마크(패드 모양)를 넣어 해결했는데, 실데이터에서 같은 원인을 다시 만난 것이다.

> 실제 die에 정렬 마크가 따로 있는 이유가 이것이다 —
> **반복 무늬만으로는 "여기가 어디인지" 정할 수 없다.**

### 고친 것

정합 측정을 **믿을 수 있을 때만** 쓰도록 가드 두 개를 넣었다.

| 파라미터 | 기본값 | 하는 일 |
|---|---|---|
| `minResponse` | 0.3 | 상관 신뢰도가 낮으면 **중단**. 주기 무늬에서 이게 걸린다 |
| `maxShiftPx` | 20 | 터무니없이 크게 어긋났다고 나오면 **중단** |

이제 같은 상황에서 오검 11개 대신 이렇게 멈춘다.

```
[실행 실패] node 'align'(Align) — 상관 신뢰도 0.003이 기준 0.3에 못 미칩니다
            (shift=(9.32,12.09) response=0.003).
            무늬가 주기적이면 닮은 자리가 여럿이라 측정값이 의미를 잃습니다.
            'diepipe measure'로 확인하고, 이미 맞아 있으면 method를 None으로 두세요.
```

**틀린 답을 조용히 내놓는 것보다 멈추는 편이 낫다.**

## 6. 이번에 추가한 도구

실데이터를 다루려면 **재고 준비하는 도구**가 먼저 있어야 했다.
알고리즘이 아니라 측정·준비용이고, 나중에 WPF가 마우스로 하게 될 일이다.

| 명령 | 하는 일 | 이 문서의 어디에 쓰였나 |
|---|---|---|
| `diepipe stats` | 밝기 분포를 재고 **임계값 후보 구간**을 계산 | 2절 |
| `diepipe crop` | 셀 어레이를 잘라 저장 | 3절 ① |
| `diepipe measure` | 어긋남을 **재기만** 한다(보정 안 함) | 5절 — 원인 규명 |
| `diepipe inject` | 답을 아는 결함을 심는다 | 3절 ④ |

`measure`가 특히 값졌다. **"붙이기 전에 먼저 재라"** 를 실제로 할 수 있게 해 준 도구이고,
그게 없었으면 "정합이 문제다"까지는 알아도 **왜**인지는 몰랐을 것이다.

## 7. 이 데이터에 맞는 레시피

```json
{
  "id": "align",
  "type": "Align",
  "params": { "method": "None" }
}
```

정합을 **끈다**. 셀들이 이미 픽셀 단위로 맞아 있고(측정으로 확인),
무늬가 주기적이라 위상 상관을 믿을 수 없기 때문이다.

나머지는 `samples/recipes/die.diff.json` 그대로 — 임계 `0.12`, `minArea 5`가
2절에서 잰 값과 맞는다.

> 실데이터용 레시피 파일은 **레포에 넣지 않는다**(기하·좌표가 들어가므로).
> 로컬 작업 폴더에 두고 `--recipe`로 준다.

## 8. 남은 것

- **더 넓은 영역 검증** — 지금은 타일 1장의 셀 5개. 타일 4장 전체로 넓히면
  "어느 영역에서 오검이 나는가"를 볼 수 있다
- **밝은 결함** — 이번엔 어두운 점만 심었다. `--spot-value 1`로 밝은 쪽도 봐야 한다
- **µm 환산의 근거** — 0.5µm/px는 같은 원본의 raw 사이드카에서 가져온 값이다.
  타일에도 같은 배율인지는 확인하지 않았다
- **회귀로 고정** — 실데이터 결과는 테스트에 넣을 수 없다(레포 밖 파일).
  원본이 있을 때만 도는 선택적 테스트로 만들지는 더 생각해 볼 것
