# 웨이퍼 파이프라인 전체 지도

### 웨이퍼 검사 파이프라인 (통합 웨이퍼 레시피)

```


contextInputs: alignSrc, alignTemplate
   │
[TemplateMatchAll]─ alignSrc + alignTemplate ► matches      (정렬마크 다중 매칭 + NMS)
[SolveAlignment]── matches ─────────────────► alignment     (유사변환 → 원점·회전)
   │
[InspectDies] ◄─── alignment (Optional)                     ★ 경계 블록 — die 루프
   │                ► defects · grid · alignment
   │
[TransformAbs]──── defects+grid+alignment ──► absDefects    (die 상대 → 웨이퍼 절대)
[WaferDefectCluster]  (선택, TransformAbs 이전)
[Sampling]──────── absDefects ──────────────► finalDefects  (BigSize/Range/Random)
```

- `alignment`를 연결 안 하면 **정렬 생략**(항등 정렬 — 원점 (0,0)·회전 0).
- 하류(TransformAbs 이후)를 배선 안 하면 **내장 TransformAbs**가 대신 돈다.
- `InspectDies`는 레시피에 **정확히 1개**만 있어야 한다.

---

## 다이 파이프라인과의 관계

웨이퍼 파이프라인은 **바깥 껍데기**고, 다이 파이프라인이 **안쪽 알맹이**다.

```
[웨이퍼 파이프라인]  ← 이 문서
   │
   ├── 웨이퍼 어디에 die가 있는지 찾고(정렬)
   ├── die를 하나씩 꺼내서
   │      │
   │      └──► [다이 파이프라인] ← 「다이 파이프라인.md」
   │             Combine → Normalize → Align → Difference
   │             → Filter → Binarize → Label → defectList
   │
   └── die 32개 결과를 모아서 웨이퍼 좌표로 바꾸고 정리
```

즉 die 한 장을 검사하는 방법은 다이 파이프라인이 담당하고,
웨이퍼 파이프라인은 **"어느 die를, 어떤 레시피로, 몇 번 돌릴 것인가"** 를 담당한다.

```
웨이퍼 1장
 ├── die (0,0) → 다이 파이프라인 실행 → 결함 0개
 ├── die (1,0) → 다이 파이프라인 실행 → 결함 2개
 ├── die (2,0) → 다이 파이프라인 실행 → 결함 0개
 ...
 └── die (3,7) → 다이 파이프라인 실행 → 결함 1개
                                       ─────────
                                       합계 16개
```

## 왜 정렬(Align)부터 시작하나

카메라는 매번 **똑같은 위치에서 똑같이** 찍히지 않는다.

```
설계상 기대한 프레이밍          실제로 찍힌 프레이밍
┌───────────────┐             ┌───────────────┐
│ ■ ■ ■ ■       │             │  ■ ■ ■ ■      │
│ ■ ■ ■ ■       │             │  ■ ■ ■ ■      │   ← 살짝 밀리고
│ ■ ■ ■ ■       │             │  ■ ■ ■ ■      │      살짝 돌아감
└───────────────┘             └───────────────┘
```

이 상태에서 "die는 (0,0)부터 2500px 간격"이라고 그냥 잘라 버리면,
die ROI가 전부 어긋나서 **모든 die가 결함투성이**로 보인다.

그래서 먼저 **웨이퍼에 새겨진 정렬마크를 찾아서**, 이번 촬영이 얼마나 밀리고 얼마나 돌아갔는지를 재고
(= 정렬), 그 값으로 die 격자를 통째로 보정한 뒤에 검사에 들어간다.

```
정렬마크 찾기 → "아, 이번엔 x로 0.2px 밀리고 0.001° 돌아갔구나"
              → die 격자를 그만큼 밀고 돌려서 생성
              → 이제 die를 잘라도 정확히 die가 나온다
```

### 용어 정리

**alignSrc** — 정렬마크를 찾을 **검색 대상 이미지**. 웨이퍼 원본 전체다.

**alignTemplate** — 찾을 **정렬마크 패치(작은 조각 이미지)**.
예: 스크라이브 라인 교차점의 십자(+) 마크를 274×274로 잘라 놓은 png.

```
alignSrc (10000×20000)                 alignTemplate (274×274)

┌──────────────────────────┐
│  +        +        +     │                 ┌────┐
│    ■ ■ ■ ■ ■ ■ ■ ■       │                 │ +  │   ← 이 조각을
│  +        +        +     │                 └────┘      원본에서 찾는다
│    ■ ■ ■ ■ ■ ■ ■ ■       │
└──────────────────────────┘
```

**정렬마크(Align Mark)** — 웨이퍼에 일부러 새겨 놓은 기준 무늬.
보통 die와 die 사이의 빈 통로(**스크라이브 라인**) 교차점에 십자로 들어간다.

**pitch** — die와 die 사이의 간격(px). `pitchX = 2500`이면 옆 die는 2500px 오른쪽에 있다.

```
 ◄── pitchX 2500 ──►
┌────────┐ ┌────────┐ ┌────────┐
│ die    │ │ die    │ │ die    │
│ (0,0)  │ │ (1,0)  │ │ (2,0)  │
└────────┘ └────────┘ └────────┘
```

**cols / rows** — die 격자의 열·행 개수. `cols=4, rows=8`이면 die 32개.

**E1 / E0 존(Zone)** — die를 두 종류로 나눈 것.

| 존 | 뜻 | 검사 방식 |
|---|---|---|
| **E1** | 유효 die — **양옆에 이웃 die가 있다** | die-to-die(이웃을 Golden으로) |
| **E0** | 변두리 die — 웨이퍼 원판 가장자리라 **이웃이 없다** | 단일 임계(Golden 없이 절대 밝기로) |

```
웨이퍼(원판)

        ○ ○ ○
      ○ ● ● ● ○          ● = E1 (이웃 있음 → die-to-die 가능)
    ○ ● ● ● ● ● ○        ○ = E0 (가장자리, 이웃 없음 → 단일 임계)
      ○ ● ● ● ○
        ○ ○ ○
```

> ⚠ E0는 **웨이퍼 원판의 가장자리** 개념이지 **이미지의 테두리**가 아니다.
> 웨이퍼 안쪽을 부분 촬영한 이미지라면 테두리 die도 전부 E1이다(`edgeExclusionPx = 0`).
> 실제로 초기 버전이 이미지 테두리 20개를 E0로 오인해서 결과가 틀렸던 사고가 있었다.

## [TemplateMatchAll]
[TemplateMatchAll]─ alignSrc + alignTemplate ► matches      (정렬마크 다중 매칭 + NMS)

```
alignSrc + alignTemplate
          │
          ▼
  [TemplateMatchAll]
          │
          ▼
       matches
```

작은 패치(template)를 원본(src) 위에서 **한 칸씩 미끄러뜨리며** 얼마나 닮았는지 점수를 매긴다.

```
패치를 여기 놓으면?  → 닮음 0.12
한 칸 옆에 놓으면?   → 닮음 0.15
...
정확히 십자 위면?    → 닮음 0.99   ★ 여기다!
```

점수가 가장 높은 곳이 마크의 위치다. 이걸 **템플릿 매칭**이라고 한다.

결과는 여러 개가 나온다. 십자 마크가 웨이퍼에 21곳 있으면 21개가 잡힌다.

```
matches

Match #1  위치 (2332, 2332)   score 0.99
Match #2  위치 (4832, 2332)   score 0.99
Match #3  위치 (7332, 2332)   score 0.98
...
Match #21 위치 (7332, 17332)  score 0.99
```

| | |
|---|---|
| 입력 | `src : GrayF32`, `template : GrayF32` |
| 출력 | `matches : MatchList` |
| 파라미터 | `method`(**CCoeffNormed**, {CCoeffNormed·CCorrNormed·SqDiffNormed}) · `minScore`(0.8, −1–1) · `maxMatches`(32, ≥1) · `nmsRadiusPx`(8, ≥0) |

해석 -> CCoeffNormed 방식으로 닮음 점수를 계산하고, minScore는 0.8로 설정하여 0.8 미만인 후보는 채택하지 않고 검색을 멈춥니다. maxMatches는 32로 설정하여 최대 32개까지만 찾으며, nmsRadiusPx는 8로 설정하여 이미 채택한 위치 주변 8px 안에서는 중복으로 다시 뽑지 않습니다.

### method — 닮음을 재는 방법

| method | 규칙 | 특성 |
|---|---|---|
| `CCoeffNormed` | 평균을 뺀 뒤 정규화 상관 | **기본 권장.** 전체 밝기 차·조명 변화에 강함 |
| `CCorrNormed` | 정규화 상관(평균 안 뺌) | 밝기 오프셋에 민감 |
| `SqDiffNormed` | 차이 제곱합(낮을수록 좋음) | 내부에서 `1 − value`로 뒤집어 "높을수록 좋음"으로 통일 |

왜 `CCoeffNormed`가 기본인가?

```
템플릿을 만든 날: 배경 밝기 100
오늘 찍은 사진:  배경 밝기 120   (조명이 조금 밝아짐)
```

평균을 빼고 비교하면 "전체가 20만큼 밝아진 것"은 상쇄되고 **무늬의 모양**만 비교된다.

### minScore — 어디까지를 진짜로 볼 것인가

```
진짜 십자        → 0.99
비슷한 무늬      → 0.7 정도
아무 배경        → 0.1 정도
```

진짜(0.99)와 가짜 최고점(0.7) **사이**에 두면 된다. 실데이터 레시피는 여유 있게 `0.6`을 썼다.
이 값 미만이 나오면 **그 자리에서 검색을 중단**한다(점수가 높은 것부터 뽑기 때문).

### nmsRadiusPx — 중복 제거(비최대 억제, NMS)

닮음 점수는 마크 정중앙에서만 높은 게 아니라 **그 주변도 덩달아 높다.**

```
score 맵 (십자 근처)

 0.91  0.95  0.97  0.95  0.91
 0.95  0.98  0.99  0.98  0.95
 0.97  0.99  1.00  0.99  0.97    ← 중앙 하나만 필요한데
 0.95  0.98  0.99  0.98  0.95       주변도 다 0.9 이상
 0.91  0.95  0.97  0.95  0.91
```

그냥 상위 21개를 뽑으면 **십자 한 개에서 21개가 다 나온다.**
그래서 하나를 채택할 때마다 **그 주변 반경을 점수판에서 지워 버린다.** 이게 NMS다.

```
① 최고점 (2332,2332) 채택
② 그 주변 nmsRadiusPx 안을 −∞로 덮어씀
③ 다시 최고점 찾기 → 다음 마크가 나옴
④ minScore 미만이거나 maxMatches에 닿을 때까지 반복
```

- `nmsRadiusPx`는 **템플릿 크기의 절반 이상**, 그리고 **마크 간 실제 간격보다는 작게**.
- 실데이터: 십자끼리 2500px 떨어져 있으므로 `200`이면 충분.
- 데모: 마크 간격 100px이므로 `20`.

### maxMatches

실제 있는 마크 개수보다 **조금 넉넉히**. 실데이터는 21곳이 있으니 `25`.

> ⚠ 템플릿 매칭은 **회전 불변이 아니다.** ±1~2° 정도가 한계고, 크게 돌아간 웨이퍼는
> 매칭 자체가 실패한다. 그런 경우는 뒤에서 `maxAngleDeg` 판정으로 잡아낸다.

## [SolveAlignment]
[SolveAlignment]── matches ─────────────────► alignment     (유사변환 → 원점·회전)

```
matches
   │
   ▼
[SolveAlignment]
   │
   ▼
alignment ( + grid )
```

매칭으로 "**마크가 실제로 어디 있는지**"는 알아냈다.
이제 "**설계상 어디 있어야 했는지**"와 비교해서, 이번 촬영이 얼마나 틀어졌는지를 계산한다.

```
기대 위치(expected)      실제 위치(observed)      차이
(2332, 2332)      →     (2332.2, 2332.4)        +0.2, +0.4
(7332, 17332)     →     (7332.2, 17332.7)       +0.2, +0.7
                                                 ───────────
                                        origin (0.2, 0.4) · 회전 0.001°
```

이 "밀림 + 돌아감"을 하나로 표현한 것이 **유사변환(Similarity Transform)** 이다.

```
p' = s · R(θ) · p + t

 s = 배율(scale)      — 보통 1 고정(카메라 배율이 안 변하니까)
 θ = 회전각(rotation)
 t = 평행이동(translation)
```

### 왜 기대점이 2개 이상이어야 하나

점이 **하나면 평행이동만** 알 수 있다. 얼마나 돌아갔는지는 알 수가 없다.

```
점 1개:
   기대 ●  →  실제 ●        "오른쪽으로 3 밀렸다"까지만. 회전은 모름.

점 2개:
   기대 ●────────●
   실제  ●────────●         두 점을 잇는 선이 기울어진 만큼이 회전각
             ╲
```

그래서 **서로 다른 위치의 기대점 최소 2개**가 필수다(같은 좌표 2개는 계산 불가로 거부된다).

### 두 점은 멀수록 좋다 — 대각선으로

```
가까운 두 점                       먼 두 점

 ●─●                              ●
   ↑ 1px 오차                       ╲
   → 각도로 크게 증폭                 ╲
                                       ●  ← 1px 오차가 각도로는 미미
```

각도 오차 `Δθ ≈ (매칭 오차) / (두 점 사이 거리)`.
그래서 실데이터 레시피는 `(2332,2332)`와 `(7332,17332)` — **대각으로 가장 먼 두 점**을 쓴다.

### 기대 위치는 이미지 좌표가 아니라 "die(0,0) 기준 상대좌표"

이게 헷갈리기 쉬운 부분이다.

```
expectedAt = "die(0,0)의 원점을 (0,0)으로 봤을 때, 마크가 있어야 할 자리"
```

이미지 절대좌표가 아니다. 그래야 **프레이밍이 달라져도 그대로 동작**한다.

```
촬영 A: die(0,0)이 이미지 (0,0)에서 시작    → 마크 실측 (2332,2332) → origin (0,0)
촬영 B: die(0,0)이 이미지 (50,30)에서 시작  → 마크 실측 (2382,2362) → origin (50,30)
                                                                      ↑ 같은 기대값으로 자동 복원
```

| | |
|---|---|
| 입력 | `matches : MatchList` |
| 출력 | `alignment : Alignment`, `grid : DieGrid` |
| 파라미터 | `expected`([[x,y],…] **≥2 필수**, 중첩 배열) · `firstDieX`(0.0)/`firstDieY`(0.0) · `pitchX`/`pitchY`(1, ≥1) · `cols`/`rows`(1, ≥1) · `solveScale`(false) |

해석 -> expected에 기대 위치를 [x, y] 쌍으로 2개 이상 적어 주면 실제 매칭 위치와 짝지어 변환을 계산합니다. firstDieX와 firstDieY는 die(0,0)의 원점 좌표로 각각 0으로 설정하고, pitchX·pitchY는 die 간격, cols·rows는 격자 크기를 지정합니다. solveScale은 false로 설정하여 배율은 추정하지 않고 1로 고정합니다.

### 기대점 ↔ 관측점 짝짓기

매칭 결과는 **점수가 높은 순서**라 순서가 기대점과 아무 상관이 없다.
여분으로 더 잡히기도 하고, 몇 개는 못 잡기도 한다. 그래서:

```
기대점마다 → 아직 안 쓴 관측점 중 가장 가까운 것을 집어 온다(탐욕적 최근접)
```

- 특징을 서로 멀리 배치했기 때문에 최근접이면 사실상 유일한 대응이 된다.
- 짝이 2개 미만이면 solver가 명확히 거부한다(조용히 틀린 값을 내지 않는다).

### 계산 과정 (Umeyama류 닫힌형 최소자승)

```
① 기대점 무게중심 ē, 관측점 무게중심 ō 계산
② 중심을 뺀 좌표로 상관합 누적
      a = Σ (e·o)   ← 내적
      b = Σ (e×o)   ← 외적
③ θ = atan2(b, a)                      ← 회전각
   s = √(a²+b²) / Σ|e|²  (solveScale)  ← 배율
④ t = ō − s·R(θ)·ē                     ← 평행이동
```

반복 없이 **한 번에** 답이 나온다. 회전 템플릿을 여러 개 만들어 놓고 다 돌려 보는 방식보다
정확하고 훨씬 싸다.

### 출력 alignment

```
alignment

Origin      = (0.2, 0.4)     ← die(0,0) 원점이 실제로 놓인 자리
RotationDeg = 0.001          ← 회전각(도)
Scale       = 1.0            ← 배율
MeanScore   = 0.993          ← 짝지은 매칭들의 평균 닮음 점수(= 정렬 신뢰도)
```

> `SolveAlignment`도 `grid`를 내지만 그건 **에디터 미리보기용**이다.
> 실제 검사에 쓰는 die 격자는 `InspectDies`의 파라미터로 다시 만든다(기하의 단일 진실원).

## [InspectDies] ★ 경계 블록
[InspectDies] ◄─── alignment (Optional) ──► defects · grid · alignment

```
alignment
    │
    ▼
[InspectDies]  ← die 루프가 여기서 돈다
    │
    ├──► defects    (die 상대 좌표의 결함들)
    ├──► grid       (die 격자)
    └──► alignment  (그대로 통과)
```

이 블록이 웨이퍼 파이프라인의 **심장부**다. 하는 일은 세 가지.

```
① 정렬 결과 + 기하 파라미터로 die 격자를 만든다 (E0/E1 존 판정 포함)
② die를 하나씩 순회하면서
      E1 die → e1Recipe(다이 파이프라인)로 검사
      E0 die → e0Recipe(다이 파이프라인)로 검사
③ 결과를 모아서 내보낸다
```

### 왜 "경계 블록"이라고 부르나

다른 블록들은 전부 엔진(PipelineEngine)이 실행한다. 그런데 이 블록은 **엔진이 실행하지 않는다.**
직접 실행하면 `NotSupportedException`이 난다.

이유는 **die 개수가 실행할 때마다 달라지기 때문**이다.

```
엔진의 규칙: 파이프라인은 사이클(루프) 없는 그래프여야 한다

그런데 die 검사는:
   for (die in 32개) { ... }      ← 루프다. 게다가 개수가 레시피마다 다름
```

그래서 `WaferRunner`가 이 블록을 **경계선**으로 삼아 그래프를 세 토막으로 자른다.

```
[TemplateMatchAll] [SolveAlignment] │ [InspectDies] │ [TransformAbs] [Sampling]
◄────── 상류(엔진이 실행) ─────────►│  ◄루프: 코드►  │◄─── 하류(엔진이 실행) ───►
        이미지 컨텍스트              │  엔진 밖       │     블랙보드 컨텍스트
```

- **상류** = `InspectDies`의 입력으로 (간접적으로라도) 흘러드는 모든 조상 노드. 정렬 담당.
- **루프** = C# `foreach`. 엔진이 아니라 러너 코드.
- **하류** = 나머지 전부. 후처리 담당.

캔버스에는 블록 하나로 보이지만, 실제로는 "여기서 파이프라인 구조가 코드로 고정된다"는 표시다.

| | |
|---|---|
| 입력 | `alignment : Alignment` (**Optional** — 미연결이면 항등 정렬) |
| 출력 | `defects : WaferDefectList`(die 상대) · `grid : DieGrid` · `alignment : Alignment`(통과) |
| 파라미터 | `e1Recipe`(**필수**, 경로) · `e0Recipe`("") · `pitchX`/`pitchY`(100, ≥1) · `cols`/`rows`(1, ≥1) · `edgeExclusionPx`(0, ≥0) · `minScore`(0.0, 0–1) · `maxAngleDeg`(0.0) · `features[]`(중첩 배열) |

해석 -> e1Recipe에 유효 die용 다이 레시피 경로를 반드시 지정하고, e0Recipe에는 변두리 die용 레시피 경로를 지정하며 변두리 구분이 없으면 비워 둡니다. pitchX·pitchY는 die 간격(px), cols·rows는 격자의 열·행 개수이고, edgeExclusionPx는 0보다 크면 테두리 die를 E0로 분류합니다. minScore는 정렬 평균 점수의 하한, maxAngleDeg는 허용 회전각 상한이며 둘 다 0이면 검사하지 않습니다. features에는 정렬에 쓸 특징 패치 경로와 기대 위치 목록을 넣습니다.

### e1Recipe / e0Recipe — 경로 참조

값이 아니라 **파일 경로**를 적는다. 그리고 **실행할 때마다 다시 읽는다.**

```
inspect.roimono.wafer.json
   └── "e1Recipe": "die.diff.roimono.json"   ← 경로만 적어 둠
                          │
                          ▼ 실행할 때 읽음
              die.diff.roimono.json
                 Combine → Difference → Binarize → Label
```

이렇게 해 두면 **다이 블록 에디터에서 die 레시피를 고치는 즉시 다음 실행에 반영**된다.
다이 레시피의 단일 진실원은 어디까지나 그 파일 자신이다.

### features[] — 정렬 특징 목록

```jsonc
"features": [
  { "template": "features/cross_mark.png", "expectedAt": [2332, 2332],  "dieOffset": [0, 0] },
  { "template": "features/cross_mark.png", "expectedAt": [7332, 17332], "dieOffset": [0, 0] }
]
```

| 필드 | 뜻 |
|---|---|
| `template` | 정렬마크 패치 파일 경로 |
| `expectedAt` | die(0,0) 원점 기준 **상대** 기대 위치 |
| `dieOffset` | 특징 → die(0,0) 원점까지의 오프셋(사이드카 계약용 메타. 보통 0 근처) |

> 현재 구현은 **템플릿 이미지는 features[0] 하나만** 로드해서 쓴다.
> 기대점은 N개를 쓸 수 있고(같은 모양 마크가 여러 곳에 반복되는 경우),
> 회전을 풀려면 기대점이 **≥2** 여야 한다.

### edgeExclusionPx — 존 판정

```
edgeExclusionPx = 0   → 전부 E1
edgeExclusionPx > 0   → 격자의 첫/끝 행·열(테두리)을 E0로
```

```
cols=4, rows=8, edgeExclusionPx > 0

○ ○ ○ ○        ○ = E0 (테두리)
○ ● ● ○        ● = E1 (안쪽)
○ ● ● ○
○ ● ● ○
○ ● ● ○
○ ● ● ○
○ ● ● ○
○ ○ ○ ○
```

> MVP 규칙이라 "테두리 한 줄"로만 나눈다. 웨이퍼 원판의 원형·노치 기반 자동 판정은 후속 과제다.
> **자동 판정을 그냥 믿지 말고 결과를 눈으로 확인할 것.**

### minScore / maxAngleDeg — 정렬 판정(fail-loud)

정렬이 실패했는데 그대로 검사에 들어가면, **엉뚱한 자리를 die라고 잘라서** 전부 불량으로 나온다.
그래서 검사 전에 정렬 결과를 검문한다.

```
if (minScore > 0 && alignment.MeanScore < minScore)           → 예외로 중단
if (maxAngleDeg > 0 && |alignment.RotationDeg| > maxAngleDeg)  → 예외로 중단
```

```
정상:   score 0.993,  회전 0.001°     → minScore 0.8 / maxAngleDeg 3.0 통과
사고:   score 0.31,   회전 12.7°      → 즉시 중단
```

**"조용히 틀린 결과를 내느니 크게 실패하는 게 낫다"** 는 원칙이다. `0`이면 검사하지 않는다.

### die 격자 생성

```
각 die의 원점 = 정렬변환을 이상 격자점에 적용

    이상 격자점 = (col × pitchX, row × pitchY)
    실제 원점   = s · R(θ) · 이상 격자점 + origin
```

```
die(0,0) 이상 (0,     0)     → 실제 (0.2,      0.4)
die(1,0) 이상 (2500,  0)     → 실제 (2500.2,   0.4)
die(0,1) 이상 (0,     2500)  → 실제 (0.2,   2500.4)
...
```

순회 순서는 **row-major 고정**(왼→오, 위→아래). 순서가 고정이어야 결과가 매번 같다(결정론).

### die 하나를 검사하는 과정

```
die ROI = (원점 반올림, pitchX × pitchY 크기)
          │
          ├─ E1이면 → 이웃 die들을 golden으로 넘겨서 e1Recipe 실행
          └─ E0이면 → golden 없이 e0Recipe 실행
```

여기서 die ROI가 **다이 파이프라인의 `roi`**, 이웃 die ROI들이 **`chipRegions`** 로 들어간다.

```
웨이퍼 파이프라인                       다이 파이프라인
─────────────────                      ─────────────────
die ROI            ──────────────►     roi
이웃 E1 die ROI들  ──────────────►     chipRegions
                                            │
                                       Combine → Golden
                                       Difference → ... → Label
                                            │
결함 목록          ◄──────────────     defectList
```

### die-to-die golden 선택 규칙

```
golden = 같은 행에서 좌·우로 딱 1칸 떨어진 E1 die

        ┌──────┬──────┬──────┐
        │ die  │ die  │ die  │
        │(0,3) │(1,3) │(2,3) │
        └──────┴──────┴──────┘
          golden  검사   golden
```

- 같은 행만 쓴다(공정 조건이 행 방향으로 더 비슷하다).
- 가장자리 열은 **이웃이 1개**밖에 없다 → 이때 미러 오검이 생기기 쉽다(아래 함정표 참고).
- golden ROI는 **검사 ROI와 똑같은 크기**로 만들고 이미지 안쪽으로 밀어 넣는다.
  크기가 어긋나면 `Combine`이 거부해서 **die가 통째로 조용히 건너뛰어지는** 버그가 있었다.

### ROI 클램프 — 경계 die

회전과 반올림 때문에 경계 die의 ROI가 이미지 밖으로 1px 삐져나갈 수 있다.
그래서 ROI를 **이미지 경계와 교집합**해서 실제 존재하는 픽셀만 자른다.

```
요청 ROI        ┌─────────┐
이미지 경계  ───┼──────┐  │
                │      │  │
                └──────┼──┘
                       │
실제 사용        ┌─────┐      ← 교집합
```

### die 실패 처리

```
die 한 개가 검사 실패 → ErrorRaised 이벤트 + 그 die는 빈 결과로 넘어감
                        (웨이퍼 전체가 죽지는 않는다)

E0 die인데 e0Recipe가 없음 → 설정 오류 → 즉시 중단(fail-loud)
```

## [TransformAbs]
[TransformAbs]──── defects+grid+alignment ──► absDefects    (die 상대 → 웨이퍼 절대)

```
defects + grid + alignment
          │
          ▼
    [TransformAbs]
          │
          ▼
      absDefects
```

다이 파이프라인이 낸 결함 좌표는 **그 die 안에서의 좌표**다.

```
die (2,3) 안에서 발견한 결함

    ┌──────────────┐
    │              │
    │    ✕ (120, 340)   ← die 기준 좌표
    │              │
    └──────────────┘
```

그런데 사람이 알고 싶은 건 "**웨이퍼 어디**에 있느냐"다.

```
die (2,3)의 원점이 (5000.2, 7500.4)라면

절대좌표 = (5000.2, 7500.4) + (120, 340) = (5120.2, 7840.4)
```

| | |
|---|---|
| 입력 | `defects : WaferDefectList`, `grid : DieGrid`, `alignment : Alignment` |
| 출력 | `result : WaferDefectList` (absX / absY 채움) |
| 파라미터 | 없음 |

해석 -> 파라미터가 없습니다. 결함 목록과 die 격자, 정렬 결과를 받아 각 결함의 웨이퍼 절대좌표를 채워서 내보냅니다.

### 계산식

```
abs = dieOrigin + s · R(θ) · centroid
```

단순 덧셈이 아니라 **회전·배율도 같이 적용**한다. die가 θ만큼 기울어져 놓여 있으면
die 안쪽 오프셋도 그만큼 기울어져 있기 때문이다.

```
유도:
  전체 정렬변환   abs       = s·R(θ)·(이상격자점 + 오프셋) + t
  die 원점        dieOrigin = s·R(θ)·이상격자점 + t
  빼면            abs       = dieOrigin + s·R(θ)·오프셋
```

### 좌표계는 세 단계로 분리해서 관리한다

| 단계 | 어디에 들어 있나 | 누가 만드나 |
|---|---|---|
| ① ROI 상대 | `defect.bounds`, `defect.centroid` | 다이 레시피(원본 그대로 보존) |
| ② die 상대 | die ROI 원점 기준(암묵) | — |
| ③ 웨이퍼 절대 | `absX`, `absY` | **TransformAbs만** |

> **절대좌표를 계산하는 곳은 이 블록 하나뿐이다.**
> 뷰어·에디터·클라이언트에서 각자 다시 계산하면 반드시 어긋난다. 받은 `absX`/`absY`를 그대로 쓸 것.
> 격자에 없는 die 인덱스가 들어오면 조용히 틀린 좌표를 내지 않고 예외를 던진다.

## [WaferDefectCluster]  (선택)
[WaferDefectCluster]  (선택, TransformAbs 이전)

```
defects
   │
   ▼
[WaferDefectCluster]
   │
   ▼
result
```

가까이 붙어 있는 결함들을 하나로 묶는다. 다이 파이프라인의 `DefectCluster`와 같은 개념인데
**웨이퍼 레벨(여러 die 결과를 모은 뒤)** 에서 돈다.

```
묶기 전                        묶은 후
 ✕ ✕                            ┌───┐
 ✕ ✕   ← 실은 한 덩어리          │ ✕ │  ← 결함 1개로 취합
                                └───┘
```

| | |
|---|---|
| 입력 | `defects : WaferDefectList` |
| 출력 | `result : WaferDefectList` |
| 파라미터 | `inflatePx`(5, ≥0) |

해석 -> inflatePx를 5로 설정하여 각 결함의 경계 상자를 5px씩 부풀린 뒤 서로 겹치면 같은 덩어리로 취합합니다. 즉 간격이 10px(2×5) 미만인 결함들이 하나로 묶입니다.

```
inflatePx = 5

  원래 bbox        5px 팽창        겹침 → 같은 덩어리
  ┌──┐ ┌──┐      ┌────┬────┐
  │  │ │  │  →   │    │    │  →   ┌─────────┐
  └──┘ └──┘      └────┴────┘      └─────────┘
```

### 두 가지 규칙

1. **die 경계를 넘어서는 묶지 않는다.** 좌표계가 die 상대라 다른 die끼리는 겹칠 수가 없다.
2. **반드시 `TransformAbs` 앞에 둔다.** 묶은 덩어리의 절대좌표는 다시 계산해야 하므로,
   취합 후 `absX`/`absY`는 비워 두고 `TransformAbs`가 채우게 한다(변환은 한 곳에서만).

## [Sampling]
[Sampling]──────── absDefects ──────────────► finalDefects  (BigSize/Range/Random)

```
absDefects
    │
    ▼
[Sampling]
    │
    ▼
finalDefects
```

검출된 결함이 5000개 나왔다고 해서 5000개를 전부 SEM으로 리뷰할 수는 없다.
**의미 있는 일부만 골라내는** 단계다.

```
결함 5000개
    │
    ▼  큰 것부터 50개만
결함 50개  → 리뷰 큐로
```

| | |
|---|---|
| 입력 | `defects : WaferDefectList` |
| 출력 | `result : WaferDefectList` |
| 파라미터 | `mode`(**BigSize**, {BigSize·Range·Random}) · `count`(100, ≥1) · `seed`(0) · `minArea`(0, ≥0) · `maxArea`(100000000, ≥0) |

해석 -> BigSize 방식을 사용하여 면적이 큰 결함부터 우선 남기고, count는 100으로 설정하여 100개까지만 남깁니다. seed는 0으로 설정하여 Random 방식일 때 매번 같은 결과가 나오게 하고, minArea·maxArea는 Range 방식에서 남길 면적 범위의 하한·상한을 지정합니다.

| mode | 규칙 | 언제 |
|---|---|---|
| `BigSize` | 면적 내림차순 상위 `count`개 | **기본 권장.** 큰 결함이 대체로 더 치명적 |
| `Range` | 면적이 `minArea` ~ `maxArea`인 것만 | 특정 크기대 결함만 보고 싶을 때 |
| `Random` | 시드 고정 무작위 `count`개 | 편향 없는 표본이 필요할 때(모니터링·통계) |

### BigSize — 동률 처리

면적이 같은 결함이 여러 개면 순서가 흔들릴 수 있다. 그래서 동률일 때의 순서까지 못 박아 놨다.

```
정렬 기준: 면적 내림차순
           → 같으면 DieRow 오름차순
           → 같으면 DieCol 오름차순
           → 같으면 Defect.Id 오름차순
```

### Random — seed가 왜 필수인가

```
seed 없음:  실행 1 → 결함 A, C, F
            실행 2 → 결함 B, D, E     ← 매번 다름 → 골든마스터 비교 불가

seed 0 고정: 실행 1 → 결함 A, C, F
            실행 2 → 결함 A, C, F     ← 항상 같음
```

시드 고정 Fisher-Yates 셔플로 인덱스를 고른 뒤, **원래 순서대로 되돌려서** 내보낸다.
`Range`는 순수 필터라 애초에 비결정 요소가 없다.

> 세 방식 모두 **결정론**이다. 웨이퍼 결과는 골든마스터 회귀 테스트의 비교 대상이라
> 실행할 때마다 달라지는 값이 섞이면 안 된다.

```
  SolveAlignment
        ↓
   alignment (origin·회전·score)
```

③ 정렬 신뢰도 검문
```
score < minScore  또는  |회전| > maxAngleDeg
        ↓
     즉시 중단 (fail-loud)
```

④ die 격자 만들기
```
alignment + pitch·cols·rows·edgeExclusionPx
        ↓
     DieGrid (die 32개, E1/E0 태그)
```

⑤ die 하나씩 검사 (← 다이 파이프라인)
```
for each die (row-major):
    E1 → roi + 이웃 golden → e1Recipe
    E0 → roi              → e0Recipe
        ↓
   die별 defectList
```

⑥ 취합
```
die별 결과 32개
        ↓
   WaferDefectList (die 상대 좌표, absX/absY는 아직 null)
```

⑦ (선택) 근접 결함 묶기
```
WaferDefectCluster
```

⑧ 웨이퍼 절대좌표로 변환
```
defects + grid + alignment
        ↓
   TransformAbs
        ↓
   absX / absY 채워짐
```

⑨ 샘플링
```
Sampling (BigSize 50)
        ↓
   finalDefects
```


`WaferDefect` 한 개:

```jsonc

  },
  "absX": 158, "absY": 8            // 웨이퍼 절대좌표
}
```

### provenance — "이 결과가 무엇으로 나왔나"

레시피를 조금만 고쳐도 결과가 달라진다. 그래서 **실행 시점의 내용 해시**(SHA-256 앞 16자리)를 같이 기록한다.

| 필드 | 무엇의 해시 |
|---|---|
| `defSha` | 웨이퍼 레시피 자신 |
| `e1RecipeSha` / `e0RecipeSha` | 실행할 때 다시 읽은 die 레시피 내용 |
| `templateSha` | 정렬 특징 템플릿의 픽셀 내용 |

경로가 아니라 **내용** 기준이라 파일을 옮기거나 이름을 바꿔도 안 변하고, 내용이 바뀌면 바로 드러난다.

## 실행 방법

```bash
dotnet run --project src/VisionStack.Cli -- wafer-run --recipe samples/wafer/inspect.demo.wafer.json --image samples/images/wafer_demo.bmp
```

- 진행 이벤트는 **stderr**, 결과 JSON은 **stdout**(또는 `--out`) — 파이프가 안 섞인다.
- `--image`는 png·bmp·tiff, 또는 **사이드카(`<이미지>.json`)가 있는 `.raw`**.
  raw는 mmap으로 **die ROI만 읽어서** 585MB·기가픽셀도 전체 적재 없이 처리한다.
- 구 형식 `--job <job.json>`도 하위호환으로 동작한다.

## 자주 겪는 함정

| 함정 | 증상 | 대응 |
|---|---|---|
| **존 오판** | 웨이퍼 안쪽을 부분 촬영했는데 테두리를 E0로 잡음 | `edgeExclusionPx = 0`. E0는 **원판 가장자리** 개념 |
| **미러 오검** | 가장자리 열에서 결함이 두 배로 잡힘 | 이웃 golden이 1개뿐이라 이웃의 결함이 되비침 → die 레시피를 `DarkOnly`/`BrightOnly` 한 방향으로 |
| **기대점이 가깝다** | 회전각이 들쭉날쭉 | 기대점을 **대각으로 멀리** 배치 |
| **기대점 1개** | 회전이 항상 0 | 유사변환은 **≥2점** 필요 |
| **반복 마크 + 큰 프레이밍 차이** | 격자는 맞는데 die 인덱스가 한 칸 밀림 | 프레이밍 차이가 `pitch/2`를 넘으면 이웃 마크에 스냅됨 → 웨이퍼에 유일한 마크를 쓰거나 스테이지 좌표로 초기 위치 제공 |
| **골든 크기 불일치** | die가 결과에서 통째로 빠짐 | golden ROI를 검사 ROI와 같은 크기로 클램프(러너가 처리) |
| **Random에 seed 없음** | 골든마스터 비교가 매번 깨짐 | `seed` 고정 |
| **절대좌표 재계산** | 뷰어 박스가 결함과 어긋남 | `absX`/`absY`를 그대로 쓸 것 |
