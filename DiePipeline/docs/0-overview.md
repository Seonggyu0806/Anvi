## 1. 계기 — 어쩌다 이걸 만들게 되었나

### 방학 학습에서 여기까지

C# 재학습(`Studty_Cpp_CSharp`)으로 Lesson01~16을 하면서 검사 장비 소프트웨어의 조각들을 하나씩 익혔다.
HAL·메시징·DB·네트워크·EFEM·ONNX를 거쳐 **Lesson15에서 파이프라인 엔진과 JSON 레시피**,
**Lesson16에서 웨이퍼 단위 검사**까지 왔다.

조각은 다 만들어 봤는데 **하나로 이어 붙인 적이 없었다.** Lesson은 "이 개념을 이해했다"에서 끝나고,
다음 Lesson으로 넘어가면 앞의 것은 그 폴더에 남는다.

> **그래서 이 프로젝트가 있다 — 배운 조각들을 하나의 돌아가는 앱으로 잇는 것.**

### 둘이 따로 만들었다

동기와 같은 과제를 **각자** 구현했다. 출발점이 달랐다.

| | 출발점 | 성격 |
|---|---|---|
| 이쪽 | Lesson15·16 (파이프라인·웨이퍼) | 구조부터 |
| 동기 | 브리핑 문서 (die 검출 표준 흐름) | 알고리즘부터 — FFT·모폴로지·연결요소를 **직접 구현** |

둘 다 같은 결론에 도달한 부분이 많았다(노드·레시피·레지스트리·디스크립터).
서로 다른 부분이 서로의 빈칸이었고, 그걸 합치는 것이 이 프로젝트다.

### 참조는 교수님 레포

`visionstack_proto`가 이 문제의 **완성된 참조 구현**이다.
다만 **따라잡을 목표가 아니라 막혔을 때 보는 정답지**로 둔다 — 베껴 오면 배우는 게 없다.

`icecore_proto_md`는 한 층 위다. 장비 소프트웨어 플랫폼(HAL·IPC·스케줄러·SECS/GEM·DB·GUI) 10단계 중
**Phase 7 = Vision 알고리즘**이 이 프로젝트가 채울 자리다.

```
IceCore        장비 플랫폼
  └ Phase 7    IVisionAlgorithm 구현체 하나
       └ DiePipeline   ← 여기
```

### v1을 접고 다시 시작했다 — 이 기록이 제일 중요하다

2026-09-12~14에 한 번 만들었다(v1, `develop` 브랜치에 남아 있다). 잘 돌았다.
성능도 좋았고 테스트도 176개였다. **그런데 접었다.**

이유는 하나다. **배움을 앞질러 버렸다.**

```
v1 전체 6,621줄
  ├ Lesson15에서 온 것        (배운 것)
  ├ 브리핑에서 온 것           (동기가 배운 것)
  └ 1,535줄 (23%)  ← 어디에도 없는 것. 전부 AI가 제안한 것
```

그 1,535줄이 무엇이었냐면 — 부분 재실행·결과 봉투·내용 해시·메모리 풀·성능 측정 도구.
**엔지니어링으로는 옳지만, 브리핑에도 Lesson에도 없는 것들이었다.**
설명할 수 없는 코드가 레포의 1/4을 차지하고 있었다.

게다가 배운 것을 거스른 자리도 있었다. Lesson09에서 *"허용오차 비교 — 완전일치는 쓰지 않는다"* 를
배웠는데, v1은 결과를 **글자 단위로 완전일치** 비교하고 있었다.
(그러다 정합 측정이 비트 단위로 재현되지 않는다는 걸 발견하고 뒤늦게 정정했다.)

> **v2의 규칙: 배운 것과 브리핑 범위 안에서만 만든다.**
> 좋아 보이는 기능이라도 "이걸 어디서 배웠나"에 답할 수 없으면 넣지 않는다.

v1이 헛수고는 아니었다. **재서 얻은 지식**은 가져온다(§8).

## 2. 무엇을 만드나

> **웨이퍼 사진 한 장을 받아, 그 안의 die 수십 개를 하나씩 검사해서
> "어디에 무슨 결함이 있는지" 목록을 내는 프로그램.**

---

## 3. 이 문제가 왜 어려운가

웨이퍼에는 **같은 칩(die)이 도장 찍듯 수십~수백 개** 찍혀 있다. 그중 몇 개에 흠이 있다.

당연한 접근은 *"결함이 어떻게 생겼는지 배우자"* 인데, 이 분야에서는 안 된다.

| 문제 | |
|---|---|
| 데이터가 없다 | 반도체 라인은 **정상이 수십만 장, 불량이 수십 장** |
| 새 결함은 배울 수 없다 | 처음 보는 종류의 결함은 **정의상 학습 데이터에 없다** |

그래서 질문을 뒤집는다.

> ### 결함이 뭔지 배우지 않는다. **정상이 뭔지 만들어 두고 뺀다.**

**비유** — 같은 도장을 종이 10장에 찍었는데 한 장에만 얼룩이 있다.
10장을 겹쳐 보면 **도장 무늬는 모든 장에 있으니 진하게 남고, 얼룩은 한 장뿐이라 흐려진다.**
이렇게 만든 "얼룩 없는 표준 도장"을 의심스러운 한 장에서 빼면 — **얼룩만 남는다.**

이것이 **die-to-die 검사**다. 겹쳐서 만든 표준을 **골든(golden)** 이라 부른다.

## 4. 검사 한 번이 어떻게 도나 — 7단계

```
이웃 die들 ──┐
             ▼
        ① Combine      겹쳐서 골든을 만든다
             │
        ② Normalize    골든과 검사 이미지를 같은 조건으로
             │
        ③ Align        몇 px 어긋난 걸 밀어서 맞춘다
             │
        ④ Difference   ★ 뺀다 — 검출의 심장부
             │
        ⑤ Filter       티끌 노이즈를 지운다
             │
        ⑥ Binarize     "결함이다 / 아니다" 를 정한다
             │
        ⑦ Label        흰 덩어리를 세어 목록으로
             ▼
        결함 목록
```

각 단계가 **왜** 있는지가 진짜 내용이다.

### ① Combine — 왜 평균이 아니라 중앙값인가

이웃 die 3장을 겹친다. 그런데 **이웃 중 한 장에도 결함이 있으면?**

- **평균**이면 그 결함이 `1/3`만큼 골든에 섞인다 — 골든이 오염된다
- **중앙값**이면 "가운데 값"을 고르니 혼자 튀는 값은 **아예 안 들어간다**

> 비유: 세 사람에게 키를 물어 "보통 키"를 정하는데 한 명이 3미터라고 하면
> 평균은 망가지지만 **가운데 사람을 고르면** 멀쩡하다.

### ② Normalize — 양쪽에 똑같이 해야 한다

골든을 살짝 흐리게(블러) 만든다. **검사 이미지에도 똑같이 해야 한다.**
한쪽만 흐리게 하면 멀쩡한 die인데도 **모든 경계선마다 차이가 남아** 전부 결함으로 잡힌다.

> 비유: 두 그림을 비교하는데 한 장만 안경을 벗고 보면,
> 그림이 달라서가 아니라 **초점이 달라서** 다르게 보인다.

### ③ Align — 몇 픽셀이 큰일이다

die를 잘라낼 때 **2~3픽셀만 어긋나도** 배선 경계마다 얇은 띠가 남고, 그게 전부 결함으로 잡힌다.
그래서 얼마나 밀렸는지 재서 되밀어 놓는다.

> **이 프로젝트에서 제일 위험한 곳이다.** v1의 실데이터에서 이것 때문에 **오검 11개**가 났다.
> 무늬가 규칙적이면 "가장 닮은 자리"가 여러 개라, 재는 도구가 엉뚱한 답을 **자신 있게** 내놓는다.
> → 못 믿을 때는 **멈추는 가드**를 단다(§8).

### ④ Difference — 심장부

빼기다. 골든보다 **어두운 만큼 / 밝은 만큼**을 남긴다.

함정이 하나 있다. 골든을 **이웃으로** 만들었으니 **이웃의 결함이 내 차영상에 부호만 반대로 나타난다**
(미러 문제). 막는 방법은 둘이고 서로 독립이다 — 골든을 중앙값으로 만들기 / 부호 있는 차이를 쓰기.

### ⑤⑥⑦ Filter → Binarize → Label

- **Filter** — 튀는 점 노이즈를 지우고, **가는 것**을 지운다(모폴로지 열림).
  크기가 아니라 **두께**로 거르는 것이 핵심이다
- **Binarize** — 임계값을 넘으면 흰색, 아니면 검정. **여기서 결함 여부가 확정된다**
- **Label** — 흰 덩어리를 세어 "번호·위치·크기"로 만든다

> **꼭 기억할 것:** 결함의 **면적은 임계값의 함수**다. 임계값을 올리면 같은 결함의 면적이 줄어든다.
> "면적 2000짜리 결함"이라는 기록은 **임계값을 같이 적지 않으면 의미가 없다.**

### 꼬리 — 찾은 다음

`DefectFilter`(형상으로 거르기) · `DefectClassify`(종류 붙이기) · `DefectLimit`(개수 제한).
Label이 찾은 것을 **다듬는** 단계다.

## 5. 왜 웨이퍼 층이 따로 필요한가

**die 한 장만으로는 검사가 성립하지 않는다.** 골든을 만들려면 이웃이 필요한데,
"누가 이웃인가"는 **웨이퍼 격자만 아는 정보**다.

| 웨이퍼 층이 하는 일 | |
|---|---|
| 격자 | 원점·피치·행열 → die 하나하나의 위치 |
| 이웃 고르기 | (1,3) die의 골든은 누구로 만들까 |
| 잘라내기 | 큰 사진에서 die 하나만 뜯어내기 |
| 좌표 변환 | die 안 (50,60) → 웨이퍼 전체 (3550,8560) |
| 가장자리 | 변두리 die는 이웃이 모자람 → 다른 방식으로(E0 존) |
| 웨이퍼 맵 | 어느 die가 불량인지 한눈에 |

**비유** — 주방(die 검사) 하나로는 식당이 안 굴러간다.
**홀 매니저**가 "3번 테이블, 7번 테이블…" 하고 주문을 넣어줘야 한다. 웨이퍼 층이 그 매니저다.

## 6. 실데이터

장비에서 취득한 원본 웨이퍼 이미지 한 장 — **수억 픽셀, 수백 MB**.
검사용 테스트 차트가 **die 격자로 반복 인쇄**되어 있다.

> 파일 이름·해상도·피치 같은 구체값은 **회사 자료라 이 문서에 적지 않는다.**
> 값은 명령행 인자와 레시피로 넘긴다.

**중요한 건 정답을 안다는 것이다.**

```
왼쪽 절반의 die  →  결함이 심어져 있음
오른쪽 절반의 die →  깨끗함
```

그래서 **"절반은 찾고 절반은 깨끗"** 이 나와야 맞다.
이런 것을 **정답 오라클**이라 하고, 없으면 "잘 되는지"를 판단할 방법 자체가 없다.

> ⚠ **이미지는 레포에 넣지 않는다.** 회사 자료다. 레포 밖에 두고 **경로만 명령행 인자로** 넘긴다.
> 원본을 통째로 메모리에 올릴 수도 없어서, **필요한 부분만 파일에서 뜯어 읽는 BMP 리더를 직접 만든다.**
> 실제 장비가 하는 방식이다.

## 7. 구조 — 3층

```
┌─────────────────────────────────────────────┐
│  Wafer    홀 매니저 — die 를 차례로 돌린다      │  OpenCV 모름
├─────────────────────────────────────────────┤
│  Core     주방 시스템 — 칠판·엔진·레시피       │  OpenCV 모름
├─────────────────────────────────────────────┤
│  Cv       요리사들 — 실제 알고리즘 7종         │  OpenCV 씀
└─────────────────────────────────────────────┘
```

**아래가 위를 모르는 것이 핵심이다.** `Core`는 블러가 뭔지 모르고, `Cv`는 다음 노드가 누군지 모른다.

덕분에 **새 알고리즘을 추가할 때 고치는 파일이 "등록 1줄"뿐**이다 — 엔진도 Core도 안 바뀐다.

그리고 **조립 순서는 코드가 아니라 JSON 레시피가 정한다.**
임계값을 바꾸려고 다시 빌드할 필요가 없다. 파일 한 줄 고치고 다시 돌리면 된다.

### 칠판(blackboard)이라는 규칙

노드끼리 **직접 말을 걸지 않는다.** 할 말이 있으면 칠판에 이름표를 붙여 올려둔다.

요리사 1번이 "썬 양파"를 만들어 `양파`라는 이름표로 올리면, 3번이 그걸 가져다 쓴다.
**3번은 그게 누가 만든 건지 모른다.**

불편한 대신 얻는 것: **순서를 JSON이 정할 수 있다.**
대가: 이름표는 그냥 글씨라 오타를 컴파일러가 못 잡는다 → **레시피 검증기**가 그 안전을 되사온다.

### 만든다

Lesson15(엔진·레시피·검증기) + Lesson16(웨이퍼 층) + 브리핑(알고리즘 7종 + 꼬리 3종).

> **2026-09-16 — 기준을 하나로 정했다.**
> 우리가 배운 것이 전부 교수님 자료이므로, **갈라지는 자리에서는 교수님 구현을 따른다.**
> 그 결과 두 가지가 바뀌었다.
>
> | | |
> |---|---|
> | **Filter** | 방법 하나를 고르는 게 아니라 **순서 있는 체인**. 모폴로지도 그 안의 한 스텝이다 |
> | **Binarize** | 교수님 6종 그대로(Threshold·Otsu·Range·Sigma·Adaptive·Hysteresis), **기본값도 그대로** |
>
> **기본값을 우리가 재서 정하지 않는다.** 한 번 그러다 틀렸다 —
> 합성 데이터로 재고 확정했는데 실웨이퍼에서 다른 답이 나왔다.
> 재는 것은 계속하되, 결과는 **판단 근거로 문서에 남기고** 기본값은 교수님 값을 쓴다.
> 경위와 측정값: [1-deferred.md](1-deferred.md) §5·§6.

### 안 만든다

v1에서 만들었다가 **이번엔 빼기로 한 것들** — 전부 브리핑에도 Lesson에도 없다.

| | |
|---|---|
| 부분 재실행 | 슬라이더용 중간 결과 캐시 |
| 결과 봉투 · 내용 해시 | 결정/비결정 분리, 레시피 원문 해시 |
| 메모리 풀 | 버퍼 재사용 |
| 성능 측정 도구 | `bench` |

필요해지면 그때 넣는다. **"좋아 보인다"는 이유로는 안 넣는다.**

### 예외 — v1에서 재서 얻은 것은 가져온다

| | |
|---|---|
