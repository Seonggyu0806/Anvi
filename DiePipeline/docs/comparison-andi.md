# 같은 문제를 둘이 따로 풀었다 — AnDi(DiePipeline2)와의 비교

2026-09-14. 동기가 같은 과제를 **처음부터 따로** 구현했다(`AnDi/DiePipeline2`, `VisionStack.*`).
둘을 다 읽고 돌려 본 기록이다. 나중에 "왜 이 구조로 갔느냐"는 질문이 반드시 나오고,
합칠 때 기준이 필요해서 남긴다.

> 참고: `AnDi/DiePipeline`은 이쪽 레포의 `c458474` 스냅샷이다(바이트 단위로 동일).
> 비교 대상은 `AnDi/DiePipeline2`뿐이다.

---

## 1. 서로 다른 것을 잘한다

| | 이쪽 (DiePipeline) | 동기 (DiePipeline2) |
|---|---|---|
| 1250×1250 한 번 | **76.6 ms** | 1,611 ms (실데이터 기록) |
| 테스트 | 176개 | 212개 |
| 알고리즘 | 7 + 결함 후처리 3 | **15** |
| src / tests 줄 | 5,758 / 2,152 | 4,744 / **3,065** |
| 외부 의존성 | OpenCvSharp | **없음** (FFT·BMP·PNG 직접 구현) |
| 실데이터 | 타일 1장 | **대용량 원본 웨이퍼 관통** |
| 웨이퍼 층 | 없음 | **있음** (타일·비닝·절대좌표) |

성능 차이의 조건이 완전히 같지는 않다 — 동기는 12노드 레시피·실이미지·다른 PC, 이쪽은 8노드·합성이다.
그래도 자릿수는 분명하다. OpenCV는 SIMD 네이티브고, 동기 쪽은 `Parallel.For` C# 루프다.

**한쪽이 더 낫다기보다, 이쪽은 깊게(성능·메모리·재현성) 동기는 넓게(기능·실데이터) 갔다.**

---

## 2. 뼈대를 이쪽으로 정한 이유

전부 **WPF에 직결되는 것**들이다. 알고리즘은 옮기기 쉽지만 이것들은 나중에 끼워 넣기 어렵다.

### 성능 20배

슬라이더를 1.6초짜리 파이프라인 위에 얹을 수 없다. 이쪽은 부분 재실행까지 더해 4.6ms다.

### 메모리 소유권

동기 쪽은 연산마다 새 배열을 만든다(`GrayF32(w,h,data)`는 복사까지 한다).
2500² F32 한 장이 25MB이고 노드가 12개면 **실행마다 300MB를 GC에 던진다**.
드래그하면 GC가 화면을 끊는다. 이쪽은 `IImagePool`이 버퍼를 재사용한다.

이건 나중에 못 넣는다. 넣으려면 모든 스테이지의 시그니처를 바꿔야 한다.

### 부분 재실행

메모리 소유권 위에만 설 수 있다. 동기 구조는 실행마다 `Blackboard`를 새로 만들어
"지난 실행의 중간 결과"라는 것이 존재할 수 없다.

### 칠판이 조용히 덮어쓴다

```csharp
public void Set(string key, object artifact) => _items[key] = artifact;   // 동기
```

이쪽은 `DuplicateKeyException`을 던진다. 레시피에서 출력 이름이 겹치면
"분명 A를 넣었는데 B가 나오는" 추적 불가능한 버그가 되는데, 그게 조용히 통과한다.

### 취소 토큰이 없다

1.6초 파이프라인에 취소가 없으면 WPF에서 답이 없다.

## 3. 가져온 것 셋

### ① 노드 끄기 (`"enabled": false`) — 아이디어를 가져오고 구현은 바꿨다

동기 쪽이 좋은 아이디어를 냈다. 노드를 끄면 출력 이름표가 입력을 그대로 가리킨다 —
**WPF 체크박스에 1:1로 대응한다.** 노드를 지웠다 되살리는 것보다 안전하다(배선과 값이 남는다).

다만 구현이 `Inputs.Values.First() → Outputs.Values.First()`라 **아무 노드나 끈다.** 여기선 세 군데가 깨진다.

| 끄면 | 무슨 일이 |
|---|---|
| `Binarize` | Image가 **Mask 자리**로 간다 |
| `Combine` | ImageList가 **Image 자리**로 간다 |
| `Label` | `defectList`가 **아예 안 생긴다** → 예외 없이 결함 0개 |

마지막은 이 프로젝트가 가장 경계하는 실패 방식이다(레시피 검증기가 따로 있는 이유가 그것이다).

**그래서 디스크립터가 "끌 수 있는가, 끌 때 어느 포트를 통과시킬까"를 선언하게 했다.**

- 못 끄는 노드를 끄면 **실행 전에** 검증기가 막는다
- 등록 시점에 "끄면 타입이 바뀌는" 선언인지 검사한다 — 틀리면 앱이 아예 안 뜬다
- 꺼진 노드는 `BypassNode`가 된다. 엔진도 세션도 "꺼짐"을 모른다 → 타이밍·부분 재실행이 그냥 동작
- 타이밍에 `Normalize (꺼짐)`으로 찍혀 안 돈 이유가 읽힌다

지금 끌 수 있는 것: `Normalize` · `Filter` · `Align` · `DefectFilter` · `DefectClassify`.

### ② 결함 후처리 셋 — 로직은 그대로, 자리는 Core로

`DefectFilter` · `DefectMerge` · `DefectClassify`를 옮겼다. 규칙도 기본값도 동기 쪽을 따랐다
(축이 기본 범위면 그 축은 무시 / 원형도 낮으면 Scratch, 아니면 면적으로 Blob·Particle).

**바꾼 것 둘**

- **`DiePipeline.Core`에 뒀다.** 입력도 출력도 `DefectList`뿐이라 픽셀도 풀도 백엔드도 필요 없다.
  이미지 파일 없이 밀리초 단위로 테스트된다. 백엔드가 바뀌어도 이 셋은 그대로 쓰인다.
- **원형도가 없으면 멈춘다.** 동기 쪽 `Defect.Circularity`는 항상 채워지지만 이쪽은 `double?`라
  Label의 `computeShape`를 켜야 채워진다. 없는데 조용히 통과시키면
  "게이트를 걸었는데 아무것도 안 걸러지는" 상태가 되고, 레시피를 아무리 봐도 원인을 알 수 없다.
  그래서 **무엇을 켜야 하는지 말하고 멈춘다.**

`Defect.Extent`(채움비)도 같이 들어왔다 — 종횡비로는 못 거르는 것을 거른다.
비스듬한 흠집은 경계 상자가 정사각형이라 종횡비가 1인데 안이 거의 비어 있다.

예시 레시피: `samples/recipes/die.diff.post.json`.

### ③ ECC 정합 + 측정 비용 상한

**ECC** — 위상 상관과 **실패하는 방식이 다르다.** 위상 상관은 전역에서 가장 닮은 자리를 찾아
주기 무늬면 엉뚱한 봉우리에 걸리지만, ECC는 항등 변환에서 출발해 **가까운** 최적점으로 내려간다.
die가 대체로 맞아 있으면 그 가까운 곳이 정답이다. 실데이터에서 위상 상관이 4px·11px·23px로 튀던
자리가 정확히 여기에 해당한다.

**`estimateSize`** — 잴 때만 중앙을 잘라 쓴다. 평행이동은 이미지 전체에 똑같이 적용되는 값이라
가운데만 재도 답이 같고, FFT는 픽셀 수에 `n log n`으로 붙는다.

**바꾼 것**: 회전·크기를 크롭에서 구하면 **크롭 원점 기준**이라 전체 이미지에 못 쓴다.
동기 쪽은 그 구분 없이 `EstimateSize = 1024`를 기본값으로 두고 모든 모션에 적용한다.
이쪽은 `eccMotion`이 `Translation`이 아니면 **조용히 무시하지 않고 거부한다.**

## 4. 재보니 이렇더라 — `estimateSize`의 실제 효과

2500×2500 합성 die, `die.diff.json`의 Align에 `estimateSize`만 넣어 봤다.

| estimateSize | 전체 실행 | Align | |
|---|---|---|---|
| 없음(전체) | 299 ms | 159 ms (44%) | |
| 2000 | **269 ms** | **125 ms** (41%) | −21% |
| 1500 | — | — | **가드가 거부**(response 0.074) |
| 1024 | — | — | **가드가 거부**(response 0.019) |
| 512 | — | — | **가드가 거부**(response 0.029) |

합성 die의 랜드마크(패드·바)가 이미지 전체에 흩어져 있어 가운데만 자르면 **주기 무늬만 남는다.**
잴 단서가 없어지니 신뢰도가 무너지고, 가드가 잡았다.

**이게 맞는 동작이다.** 거부가 아니라 그대로 밀었다면 response 0.019짜리 값으로 격자를 옮겨
실데이터에서 봤던 세로 띠 오검이 재현됐을 것이다.

교훈: `estimateSize`는 **무늬가 이미지 전체에 고르게 있는 실데이터**에서 값을 하고,
넣을 때는 `diepipe measure`로 response를 먼저 확인해야 한다.

## 5. 동기에게 알릴 것 — `AlignStage`에 가드가 없다

```csharp
var shift = Fft.PhaseCorrelate(t, r);
LastInfo = new AlignInfo(shift.Dx, shift.Dy, shift.Response, true, ...);   // Converged: 항상 true
return Ops.Shift(test, shift.Dx, shift.Dy, SubPixel);                      // 무조건 적용
```

`Response`를 **기록만 하고 검사하지 않는다.** 게다가 `EstimateSize = 1024`가 기본값이라
위 표의 "가드가 거부"한 상황이 그쪽에서는 **그대로 적용**된다.

이쪽에서 이것 때문에 실데이터 셀 하나에서 **오검 11개(세로 띠)** 가 나왔다.
라인&스페이스 무늬가 주기적이라 위상 상관의 답이 유일하지 않고,
측정값이 제각각에 response가 음수인데도 그대로 밀어버린다(`docs/real-data-check.md`).

이쪽 가드: `minResponse`(기본 0.3) · `maxShiftPx`(기본 20). 못 믿으면 **중단한다.**

대용량 실데이터를 이미 돌렸으니, 무늬가 규칙적인 셀에서 확인하면 재현될 것이다.

## 6. 안 가져온 것과 이유

| | 왜 |
|---|---|
| `DefectCluster` · `DefectLimit` · `MaskApply` · `CellToCell` · `Distance` | 지금 쓸 자리가 없다. 필요해지면 그때 — 넷 다 옮기기 쉬운 모양이다 |
| 웨이퍼 층 | 다음 단계다. 봉투 구조는 이미 웨이퍼를 받게 설계해 뒀다(`docs/provenance.md` §7) |
| 의존성 0 (자체 FFT·코덱) | 배포는 쉬워지지만 **성능 20배**를 내준다. 검사 장비에서는 그 거래가 안 맞는다 |
| 스테이지가 출력을 반환하는 계약 | 동기 쪽이 더 깨끗하다(노드가 칠판을 직접 못 만진다). 다만 지금 구조를 바꿀 만큼은 아니다 — **이건 이쪽이 진 부분으로 적어 둔다** |
| 마스크 전용 타입(`Gray8`) | 같은 이유. 이쪽은 `PixelFormat` enum이라 런타임에 검사한다 |

## 7. 남은 숙제 하나 — 우리 쪽 결정성은 생각보다 약하다

비교하다가 이쪽 문제를 하나 찾았다.

**`Cv2.PhaseCorrelate`는 같은 입력에 같은 값을 내지 않는다.** 같은 `Mat` 두 장으로 여덟 번 재면
`-2.998877 / -2.994076 / -2.993652 …`처럼 1e-3 수준으로 흔들린다.
OpenCV의 DFT가 멀티스레드라 부동소수 덧셈 순서가 실행마다 달라지기 때문이다.

`docs/provenance.md`에 "같은 입력이면 결정적 칸이 글자 단위로 같다"고 적었는데,
**정확히는 실측이지 보장이 아니다.** 같은 검사를 30번 돌려 결과가 1가지였던 것은
임계와 정수 라벨링이 그 흔들림을 흡수하기 때문이고, **임계 경계에 걸린 결함은 흔들릴 수 있다.**

`Phase_correlation_is_not_bit_exact` 테스트가 이 성질을 박아 뒀다.
정합을 쓰지 않는 레시피(`method: None`)는 영향이 없다.
