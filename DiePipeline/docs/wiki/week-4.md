# 4주차 — 웨이퍼 층

> die 하나를 검사하는 것까지는 됐다. 이제 **"누가 이웃인가"를 아는 층**을 얹는다.
> **진행 중인 주차다.**

---

## 계획했던 것

| | 무엇 |
|---|---|
| **격자** | 원점 · 피치 · 행열 → die 하나하나의 위치 |
| **이웃 고르기** | 이 die의 골든을 누구로 만들까 |
| **웨이퍼 러너** | die 목록을 돌리며 엔진을 부른다 |
| **결함 모으기** | die별 결과 → 웨이퍼 전체 목록 |
| **좌표 변환** | die 안 좌표 → 웨이퍼 절대 좌표 |
| **샘플링** | 전수 검사 대신 일부만 볼 때 어느 die를 볼까 |
| **정렬** | 웨이퍼가 어떻게 놓였는지 찾아내기 |

### 왜 이 층이 필요한가

**die 한 장만으로는 검사가 성립하지 않는다.** 골든을 만들려면 이웃이 필요한데,
**"누가 이웃인가"는 웨이퍼 격자만 아는 정보**다.

> **비유** — 주방(die 검사) 하나로는 식당이 안 굴러간다.
> **홀 매니저**가 "3번 테이블, 7번 테이블…" 하고 주문을 넣어줘야 한다.

---

## 먼저 정한 설계 — die 반복은 **엔진 밖**에 둔다

```
엔진 안에 넣을 수 있는 것    ①→②→③→…    순서가 미리 정해진 것
엔진 안에 못 넣는 것          die N개 반복   N이 실행할 때 정해진다
```

JSON 레시피는 **노드를 몇 개 어떤 순서로** 놓을지를 적는 파일이다.
그런데 die 개수는 **웨이퍼를 열어 봐야 안다.**

> **비유** — 레시피에 "양파를 볶는다 → 고기를 넣는다" 는 적을 수 있다.
> 그런데 **"손님 수만큼 반복한다"** 는 못 적는다. 손님 수는 그날 정해진다.
> 그건 **홀 매니저가** 한다.

```
Wafer 층 (바깥)     die 목록을 만들고, 하나씩 돌린다
    │
    └─ 각 die 마다 ─→  Core 엔진 (안쪽)   레시피대로 ①→②→…→⑦
```

**Lesson16도 교수님 구현도 같은 결론이었다.** 우연이 아니라 문제의 성질이다.

## ✅ 한 일 — 격자

```
Wafer/
 ├ Domain/Wafer.cs               WaferZone · DieOrigin · DieGrid · WaferAlignment
 ├ Config/WaferSpec.cs           웨이퍼 형상
 └ Execution/DieGridBuilder.cs   형상 + 정렬 → die 원점 격자
```

### E1 / E0 존 — 가장자리를 따로 본다

| | |
|---|---|
| **E1** | 온전한 die. 이웃이 다 있다 → **die-to-die 로 검사** |
| **E0** | 변두리 die. 이웃이 모자라다 → **골든을 못 만든다** |

#### ⚠ E0 는 "이미지 테두리" 가 아니다

**웨이퍼 원판의 가장자리**를 말한다. 웨이퍼는 둥근 원판인데 die 는 네모로 찍히니,
**가장자리에서는 die 가 원판 밖으로 삐져나간다.** 그런 die 가 E0 다.

> **비유** — 피자를 네모로 잘랐다. **가장자리 조각은 둥근 테두리가 걸쳐 모양이 이상하다** — 이게 E0 다.
> 그런데 피자 **가운데를 네모로 사진 찍어 놓고** "사진 테두리 조각은 이상할 것" 이라고 하면 **틀린다.**
> 사진 안은 전부 멀쩡한 조각이다.

교수님도 여기서 한 번 틀렸다가 고쳤다 — *"이미지 테두리 ≠ 웨이퍼 가장자리."*

**우리 원본은 웨이퍼 안쪽을 부분 촬영한 것이라 E0 가 없다. 지금은 전부 E1 로 둔다.**

#### 몇 겹을 가장자리로 볼지는 정할 수 있다

```
rings 0        rings 1        rings 2
11111          00000          00000
11111          01110          00000
11111          01110          00100
11111          01110          00000
11111          00000          00000
        1 = E1 (온전)   0 = E0 (변두리)
```

`rings 0` 이 지금 우리 설정이다. 교수님도 같은 상태다.

> 이건 **근사**다. 제대로 하려면 웨이퍼 **중심과 반지름**으로 "이 die 가 원 밖으로 나가나" 를 재야 한다.
> 검증할 데이터가 없어 미뤄 뒀다.

#### E0 die 는 골든 없이 검사한다

```
E1   이웃과 비교해서 "얘가 더 어둡네"        →  die-to-die
E0   "이 정도로 새까만 건 정상일 리 없다"    →  단일 임계
```

배경이 **0.33 아래로 안 내려가니** 0.15 로 자르면 배경과 안 겹친다.
**밝은 결함은 못 잡는다** — 패턴과 구분이 안 된다. 그건 E1 소관이다.

### 웨이퍼가 삐뚤게 놓였을 때

웨이퍼는 장비에 **정확히 반듯하게** 놓이지 않는다. 그래서 격자를 두 단계로 만든다.

```
①  이상적인 자리          원점 + 열×피치, 원점 + 행×피치
②  실제로 놓인 대로 변환   회전 + 확대/축소 + 이동
```

**1도만 기울어도 300px 떨어진 끝에서는 5px이 밀린다.**
2~3px만 어긋나도 모든 경계에 띠가 남으니 반드시 보정해야 한다.

### 값이 이상하면 멈춘다

| 거부 | 왜 |
|---|---|
| 열·행이 0 이하 | 격자가 아니다 |
| 피치가 0 이하 | 모든 die가 같은 자리에 겹친다 |
| die 크기 > 피치 | ROI가 서로 겹친다 |
| 확대율 0 | **모든 좌표가 원점으로 무너진다** |

마지막 것이 특히 중요하다. 확대율 0이면 **오류가 안 나고 모든 die가 (0,0)에 놓인다.**
2주차에 겪은 "조용히 틀리는 실패" 바로 그 모양이라 미리 막았다.

### 이름은 교수님 것을 따랐다

`WaferZone` · `DieOrigin` · `DieGrid` · `WaferAlignment` · `WaferDefect` · `DieResult` —
전부 교수님 레포와 같은 이름이다.

> **서로 교차 참조할 수 있어야 하기 때문이다.**
> 2주차에 "서로 코드를 못 읽었다" 를 겪었으니, 이번엔 이름부터 맞춰 둔다.

## ✅ 한 일 — 이웃 고르기 · 러너 · 모으기 · 좌표

### 이웃 고르기에는 3주차 측정이 그대로 들어갔다

**이웃 고르는 법과 합치는 법이 짝**이라는 것을 쟀으니, 둘을 **같이** 정할 수 있는 모양으로 뽑아냈다.
이웃은 **E1 die 에서만** 고른다. 변두리(E0)는 골든을 못 만드니 애초에 요청하면 거부한다.

### 러너는 이미지를 안 만진다

자리(네모)만 계산해서 **바깥에서 받은 검사 함수**에 넘기고, 돌아온 결함 목록을 모은다.

> **비유** — 홀 매니저는 요리를 안 한다. "3번 테이블, 파스타" 만 주방에 넘긴다.

덕분에 이 층은 OpenCV 를 모르고, **사진 한 장 없이** 웨이퍼 전체 흐름을 테스트할 수 있다.

### 골든은 밀어 넣고, 검사 자리는 잘라 낸다

둘의 처리가 반대다. 검사 자리는 이미지 밖에 픽셀이 없으니 **잘라 내는 게** 맞다.
골든을 같이 자르면 **크기가 달라져서 합치는 단계가 통째로 거부**하고,
그러면 그 die 가 **조용히 건너뛰어진다** — 결과는 "결함 0개" 인데 사실은 안 본 것이다.

### 좌표는 세 단계, 변환은 한 곳에서만

```
① die 안 좌표     검사 결과 그대로
② die 자리를 더함
③ 웨이퍼 절대     정렬(원점·회전·확대)로 변환
```

원본은 안 지우고 **절대 좌표를 덧붙인다.** 변환하는 코드가 여러 군데로 흩어지면
반드시 한 군데가 어긋나고, 증상은 "지도의 점이 살짝 밀렸다" 뿐이라 원인을 못 찾는다.

> ⚠ die 를 **반듯하게 펴서 읽는 것**과 **원래 각도로 되돌리는 것**은 짝이다.
> 한쪽만 하면 두 배로 돌거나 안 돈다. 펴서 읽는 건 정렬 단계에서 할 일이라,
> 그때까지는 **기울기가 크면 멈추는 가드**를 달아 뒀다.

### 웨이퍼 한 장이 처음부터 끝까지 돈다

명령행 `wafer` 를 붙였다. 이미지 열기 → 격자 → die마다 이웃 골라 검사 → 결함 모으기
→ 웨이퍼 좌표 → 지도 출력까지 한 번에 간다.

끝값을 셋으로 나눴다 — 결함 없음 · 결함 있음 · **검사가 터진 die 있음.**
마지막이 제일 위험하다. 결함 0개로 보이지만 **안 본 것**이다.

### ★ 짝이 깨지면 이제 멈춘다

돌려 보다 사고가 났다. 시험용 웨이퍼에 흠집 **3개**를 심었는데 **9개**가 나왔다.

```
레시피는 골든 3장을 전제하는데   명령행 기본값이 1~2장을 줬다
2장이면 중앙값이 평균이 되어  →  이웃의 결함이 골든에 섞이고  →  내 die 에 되비친다
```

**짝을 정하는 자리가 떨어져 있었다** — 합치는 법은 레시피에, 이웃 고르는 법은 명령행에.
사람이 매번 맞춰 넣어야 하면 언젠가 틀리고, **틀려도 안 터진다.**

그래서 **레시피에서 필요한 장수를 읽어내게** 했다. 사람이 따로 적는 값이 아니라
합치는 법에서 유도하므로 틀릴 수가 없다. 이제 모자라면 조용히 틀린 답 대신
**시끄러운 실패**가 난다.

### 시험용 웨이퍼를 코드로 그린다

실데이터는 레포에 안 넣는다. 그러면 돌려볼 게 없어서, 그림을 **코드로 그리는** 명령을 만들었다.
데이터를 한 톨도 안 쓴다. 심은 자리를 같이 출력하니 **정답과 맞춰 볼 수 있다.**

> **비유** — 시력검사표를 만들면서 **정답표도 같이** 인쇄하는 것이다.

### 결함이 너무 많을 때 추리기

실제 웨이퍼에서는 결함이 수천 개 나올 수 있다. 전부 화면에 띄우면 하류가 감당을 못 한다.
그래서 **검사는 다 하고 결과만 추리는** 단계를 붙였다 — 큰 순서로 · 면적대로 · 무작위로.

> **비유** — 답안지 1,000장을 다 못 본다. 목적에 따라 고르는 법이 다르다.

**전부 "같은 입력이면 같은 출력" 이어야 한다.** 무작위는 씨를 고정하고,
면적 정렬은 동률을 끝까지 가른다. 하나라도 흔들리면 "어제와 결과가 다르다" 가
프로그램 탓인지 운 탓인지 알 수 없어지고, 회귀 시험이 무너진다.

두 가지를 조심했다.

| | |
|---|---|
| **덜어낸 개수를 반드시 말한다** | 조용히 줄이면 "결함이 이것뿐" 으로 읽힌다 |
| **끝값은 추리기 전 기준** | 화면은 줄여도 **판정은 못 줄인다.** 끝값은 스크립트가 읽는다 |

### ✅ 정렬 — 웨이퍼가 어떻게 놓였는지 역산한다

지금까지는 웨이퍼가 반듯하게 놓였다고 가정했다. 실제로는 매번 조금씩 다르게 놓인다.
**1도만 기울어도 300px 끝에서 5px 이 밀리고**, 2~3px 만 어긋나도 모든 경계에 띠가 남는다.

웨이퍼에 찍힌 표식을 찾아 각도와 원점을 역산한다. 표식은 **둘 이상 · 멀리 · 비대칭**이어야 한다.

> **비유** — 못 자국 **하나**로는 액자가 비뚤었는지 알 수 없다. 두 개, 그것도 **멀리** 있어야 한다.

#### ★ 점수가 높다고 맞는 게 아니다

실데이터로 재 보니 **작은 조각에서 제일 높은 점수가 틀린 자리**였다(오답 0.98 · 정답 0.93).
2주차의 그 실패가 그대로 재현됐다 — *"재는 도구가 엉뚱한 답을 자신 있게 낸다."*

**문턱을 올려도 못 막는다.** 대신 **표식 둘 사이 거리**를 본다 —
웨이퍼는 돌아가고 밀릴 뿐 **찌그러지지 않는다.** 거리가 변했다면 엉뚱한 자리를 찾은 것이다.

#### ★ 반 칸이 각도 오차가 된다

찾기는 **한 칸 단위**로만 답하는데, 두 점으로 각도를 풀면 그 반 칸이 각도 오차가 된다.
점수판의 봉우리 모양을 보고 소수점 자리까지 잡게 했더니 **각도 오차가 4배 줄었다.**

#### 못 믿으면 검사를 시작조차 안 한다

정렬이 틀리면 **웨이퍼 전체가 밀린 자리를 검사**하고, 결과는 "오검 천 개" 로만 보여서
원인을 못 찾는다. 2주차 정합 사고의 웨이퍼판이라, 믿을 수 없으면 아예 시작하지 않는다.
